## 問1 Webアプリケーションプログラムの開発（Q社 WebアプリQ / 格納型XSS）

| 設問 | 自作解答 |
|---|---|
| 設問1(1) | イ（格納型XSS） |
| 設問1(2) | レビューの出力時に，HTMLの特殊文字をエスケープ処理する。 |
| 設問2 | スクリプトを分割して複数のレビュータイトルに投稿し，間に入るHTMLを/*と*/でコメント化した。 |
| 設問3(1) | プロフィール設定ページのトークンを取得し，cookieを中身とするファイルをアイコン画像としてアップロードする。 |
| 設問3(2) | レビューページ等に表示される被害会員のアイコン画像をダウンロードし中身を読む。 |
| 設問3(3) | 取得したセッションIDを使って被害会員になりすまし，商品を購入する。 |
| 設問4 | 同一オリジンポリシーで別オリジンのレスポンスを読み取れない仕組み |

### 解説
- **設問1(1)**：攻撃スクリプトはレビューとしてサーバに保存され，ページVを閲覧した全員のブラウザで実行される。保存→表示型なので**格納型（Stored）XSS**。
- **設問1(2)**：会員Bのレビューでは `>` `<` が `&gt;` `&lt;` に変換されている一方，レビュータイトルの `<script>` はそのまま出力されている。レビュータイトル（および全出力箇所）で特殊文字（`< > & " '`）を文字参照に置き換えるエスケープ処理を行えばよい。
- **設問2**：タイトルは50字制限なので，1件目のタイトルを `Good<script>xhr=new XMLHttpRequest();/*` とし，2件目以降を `*/…;/*` の形で続け，最後を `*/xhr2.send(form);}</script>` で閉じている。レビューの間に挟まる `</div><div class="description">a</div></div><div class="review">…` などのHTMLは，JavaScriptのブロックコメント `/* … */` の中に入るのでスクリプトとして無害になり，15件分がつながって1本のスクリプトになる。会員Aが15件投稿していたのはこのため。
- **設問3(1)**：6行目以降はprofileページのレスポンス受信後に動く。8行目でDOMからトークンを取り出し，13〜16行目で `document.cookie`（HttpOnlyが付いていないのでセッションIDを含む）を中身とする `a.png` を作り，17〜19行目で `uploadfile` と `token` を付けて `/user/upload` にPOSTしている。つまり**被害者自身のアイコン画像をcookie入りファイルに差し替える**処理。
- **設問3(2)**：アップロードしたアイコン画像は会員プロフィール設定ページやレビューページに表示され，`/users/<ID>/icon.png` という固定的なURLで公開されている。画像形式もチェックされないので，攻撃者は被害者のアイコン画像（レビューページなどで表示されるもの）のURLにアクセスしてダウンロードし，中のテキスト（cookie）を読めばよい。
- **設問3(3)**：cookieにはログイン時に払い出されたセッションIDが入っているので，セッションハイジャックで被害会員になりすませる。ログイン済み会員だけが使える商品購入（登録済みクレジットカードでの購入）などが可能。
- **設問4**：攻撃者ドメインのページ上のスクリプトからXHRで `□□□.co.jp/user/profile` を取得しても，同一オリジンポリシー（CORSで許可されていない）によりレスポンスを読めずトークンを取得できない。また `document.cookie` も攻撃者ドメインのcookieしか読めない。

## 問2 セキュリティ対策の見直し（M社 Bサービス / 無線LAN）

| 設問 | 自作解答 |
|---|---|
| 設問1(1) a / b | a：利用者ID　b：パスワード |
| 設問1(2) c | このサーバ証明書は，信頼された認証局から発行されたものではない |
| 設問1(2) d | このサーバ証明書のサーバ名が，アクセスしたサイトのドメイン名と一致しない |
| 設問1(3) | 過去に受信したHSTSの情報に基づき，httpをhttpsに置き換えて偽サイトにHTTPSで接続する。 |
| 設問2(1) | 外部の共有者のメールアドレスに自分の私用メールアドレスを指定する。 |
| 設問2(2) e | MACアドレス |
| 設問3(1) | RADIUS |
| 設問3(2) f | 秘密鍵（クライアント証明書の秘密鍵） |
| 設問3(3) g | 業務PCから取り出せないように |
| 設問3(4) | 秘密鍵をTPMから取り出せず，個人所有PCで証明書を使えないから |
| 設問3(5) | 表4項番1のNATで，来客用無線LANからの通信の送信元IPアドレスを，a1.b1.c1.d1以外のグローバルIPアドレスに変換する。 |
| 設問3(6) h | DNS |
| 設問3(7) | 表3：項番1　表4：項番1，4 |

### 解説
- **設問1(1)**：表1より，Bサービスは従業員ごとの**利用者IDとパスワード**でログインする。送信元IPアドレス制限（a1.b1.c1.d1）は，来客用無線LANもFWでa1.b1.c1.d1にNATされる（表4項番1）ので攻撃者も満たしてしまう。よって残る障壁は利用者IDとパスワード。
- **設問1(2)**：偽サイトのサーバ証明書は，(ア)攻撃者が自己署名などで作ったもの（信頼できるCAが発行していない），(イ)CAから取得できたとしても攻撃者のドメイン用で，BサービスのURLのドメイン名と一致しない，のどちらかになる。図2に既にある「失効」「有効期限切れ」以外の代表的なエラーとしてこの2つを挙げた。
- **設問1(3)**：HSTSを受け取ったブラウザは，有効期間中そのドメインへは必ずHTTPSで接続する。従業員が `http://` と入力しても，ブラウザが内部で `https://` に書き換えてから接続するので，結局偽サイトとのTLSハンドシェイクで証明書検証に失敗し，同じエラーになる（業務PCは日常的にBサービスを使うのでHSTS情報を保持している前提）。
- **設問2(1)**：上長が宛先とファイルを確認しないなら，外部共有者として**自分の私用メールアドレス**を入力すれば，外部共有リンクが私用アドレスに届き，社外からログインせずにダウンロードできる。
- **設問2(2)**：従業員用無線LANはMACアドレスフィルタリングだけで端末を制限している。PSKは業務PCに設定されているので従業員は知り得る（またはSSID非通知でも設定から分かる）。個人所有PCのMACアドレスを業務PCのものに偽装すれば接続できる。
- **設問3(1)**：EAP-TLSの認証サーバはRADIUS（UDP 1812）でAPと通信する。
- **設問3(2)〜(4)**：クライアント証明書に対応する**秘密鍵**をTPMに格納し，**エクスポートできない（業務PCから取り出せない）**ようにしておけば，秘密鍵を個人所有PCにコピーできないため，MACアドレスを偽装してもEAP-TLS認証を通らない。従業員にインストールさせない（ディレクトリサーバから配布）のも同じ趣旨。
- **設問3(5)**：Bサービスは送信元a1.b1.c1.d1だけを許可している。来客用無線LAN（192.168.10.0/24）からの通信もa1.b1.c1.d1にNATされているため方法2が成立する。WAN-IF1は/29（255.255.255.248）なので他のグローバルアドレスも使える。来客用無線LANの変換先を別アドレスにすれば，そこからはBサービスにログインできなくなる。
- **設問3(6)**：表4項番4で来客用無線LANからDNSサーバへのDNSが許可されていた。Dルータが自前でDHCP・DNSキャッシュを提供するので，DHCPサーバとDNSサーバへの通信が不要になる。
- **設問3(7)**：来客用無線LAN（VLAN10, 192.168.10.0/24）自体が不要になる。表3は VLAN10 の**項番1**，表4は送信元192.168.10.0/24の**項番1（インターネット向け）と項番4（DNS）**を削除。

## 問3 継続的インテグレーションサービスのセキュリティ（N社 Nサービス）

| 設問 | 自作解答 |
|---|---|
| 設問1 | ウ，エ |
| 設問2(1) | 偽サイトに入力されたID，パスワード及びTOTPを即座に正規サイトに入力してログインした。 |
| 設問2(2) | ア |
| 設問2(3) | イ |
| 設問2(4) | 管理者権限でビルドスクリプト実行シェルの環境変数を読み取る。 |
| 設問2(5) | 認証器がオリジンに紐付いた鍵で署名し，偽サイトでの署名は正規サイトで通らない。 |
| 設問2(6) a | ア（CAA） |
| 設問3(1) | 漏えいした署名鍵で署名した不正なPアプリをJストアで配布する攻撃 |
| 設問3(2) | J社サイトで認証用APIキーを削除する |
| 設問3(3) | 署名鍵をHSMの外に取り出されない。 |
| 設問3(4) 影響 | インストール済みのPアプリが起動しない。 |
| 設問3(4) 対応 | Jストアから最新のPアプリを入れ直す。 |

### 解説
- **設問1**：コンテナは特権なしで起動されるが，バックエンドはインターネットへ通信可能（表2）。したがってコンテナ内からでも，**ウ（インターネット上のWebサーバへの不正アクセス）**や**エ（攻撃者サイトから命令を取得して実行＝C&C）**はコンテナ脱出なしで成功する。ア（ホスト上のCIデーモン停止），イ（バックエンド上の全プロセス列挙），オ（別コンテナのビルド出力取得）はコンテナの隔離を破らないとできない。
- **設問2(1)**：TOTPを設定していても，Uさんが偽サイトに入力したID・パスワード・TOTPを攻撃者が即座に本物へ中継すれば（中間者型フィッシング，リアルタイムフィッシング），TOTPの有効期間内にログインできる。Uさんの「一度失敗した」は偽サイト側でエラーを返されたことを示す。
- **設問2(2)**：RFC 9162 は Certificate Transparency v2.0。発行された証明書をログサーバに記録し，第三者が検索できる。
- **設問2(3)**：SNIには無害なドメイン，HTTP Hostヘッダーには本当の接続先を入れ，CDNの中で振り分けさせる手法は**ドメインフロンティング**。
- **設問2(4)**：シークレットはビルドスクリプトを実行するシェルの環境変数として設定される（表1）。プロセスYは被害バックエンド上で管理者権限を持つので，各コンテナのプロセスの環境変数（/proc/<pid>/environ 等）や，CIデーモンが受け取ったデータを読み取れる。
- **設問2(5)**：WebAuthnでは，認証器がRP ID（ドメイン）ごとに鍵ペアを作り，ブラウザがオリジンを含めたデータに署名させる。偽サイトのドメインでは正規サイト用の鍵が使われず，得られた署名を中継しても正規サイトで検証に通らないため，リアルタイムフィッシングが成立しない。
- **設問2(6)**：証明書を発行できるCAを限定するDNSレコードは**CAA**。攻撃者は `/.well-known/pki-validation/` にファイルを置くHTTP検証でCA Rから証明書を取得していたが，CAAで正規CAだけに限定すればCA Rは発行を拒否する。
- **設問3(1)**：Kさんの二つの対応は「APIキーへの対応」と「コード署名証明書の失効・再発行」。漏えいしたAPP_SIGN_KEYで不正なアプリ（マルウェア入りPアプリ）に正規の署名を付け，STORE_API_KEYでJストアにアップロードすれば，Pアプリ利用者に正規アップデートとして配布されてしまう。
- **設問3(2)**：認証用APIキーは契約者がJ社のWebサイトから取得・削除できる。漏えいしたキーを**削除（無効化）**し，新しいキーを取得する。
- **設問3(3)**：FIPS 140-2 Level 3のHSMは鍵を内部で生成・保管し，署名もHSM内で行う。署名鍵が外部に出ないので，今回のような鍵の窃取を防げる。
- **設問3(4)**：旧コードサイニング証明書を失効させたので，スマートフォンOSの起動前検証で旧署名のPアプリは検証に失敗し**起動しなくなる**。利用者は新しい署名が付いた最新版をJストアから**インストール（更新）し直す**必要がある。

## 問4 リスクアセスメント（G百貨店 / W社 Z情報）

| 設問 | 自作解答 |
|---|---|
| 設問1 ア | 8，11，13 |
| 設問1 イ | 大 |
| 設問1 ウ | C |
| 設問1 エ | G百貨店で，貸与アカウントのログインを許可するアクセス元IPアドレスを，W社のIPアドレスだけに限定する。 |
| 設問2(1) あ | 新種のマルウェアを添付したメールを，配送管理課員宛てに送信する。 |
| 設問2(2) い | 配送管理用PCがマルウェアに感染して遠隔操作され，Sサービスに不正にアクセスされて，Z情報がW社外に送信される。 |
| 設問2(2) う | 2，5，6，9 |
| 設問2(2) え | 大 |
| 設問2(2) お | 低 |
| 設問2(2) か | C |
| 設問2(2) き | W社で，標的型攻撃メールの訓練を実施する。 |
| 設問3 a | 5，10，12 |
| 設問3 b | 2，3，4 |

### 解説
- **設問1 ア**：1-1は「従業員がID/PWをメモに書き写して持ち出す」。関連するのは，PWを書いた付箋が机上に貼ってある（13），本社事務所内では誰でも配送管理用PCに近づける（8），従業員の倫理意識が高く動機付けが低い（11：発生頻度を下げる要因）。
- **設問1 イ・ウ**：持ち出したID/PWでW社外からログインできる（表1項番3で全IPアドレス許可）うえ，一括出力機能も全アカウントに許可（表1項番4）なので，ほぼ全てのZ情報が持ち出され得る→**大**。発生頻度は低なので表3より**C**。
  - ※ 本文の「リスク番号1-1及び2-4については総合評価にかかわらず管理策を検討する」という条件からすると，1-1の総合評価はDである（被害が中以下）可能性もある。ただ，1-2（同じくID/PWの持出し）が「大」とされていることとの整合を優先して「大・C」とした。
- **設問1 エ**：データの流れを変えずに，持ち出されたID/PWが**W社外から**使われるのを防ぐ管理策。表1項番3の機能で，貸与アカウントのログイン元をW社のグローバルIPアドレス（プロキシサーバ経由の送信元）に限定する。
- **設問2(1)(2)**：“二重の脅迫”（ランサムウェア）がきっかけなので，W社外の第三者のサイバー攻撃として，マルウェア付きメールによる配送管理用PCの感染を想定した。
  - う：パターンマッチング型の対策ソフト（2）とメールSaaSのパターンマッチング型検査（5）だけでは新種のマルウェアを検知できない。プロキシはHTTPS復号機能がなく，URLフィルタリングもアダルト・ギャンブルのみ（6）なので，HTTPSでのC&C通信や持出しを止められない。訓練は未実施（9）。
  - え／お／か：感染したPCからSサービスにログインされ一括出力されればほぼ全てのZ情報が漏れる→大。表4の他のサイバー攻撃と同様に低→C。
  - き：標的型攻撃メールへの耐性を上げる人的対策（訓練）を挙げた（データの流れは変えない）。
- **設問3 a**：1-5は「誤ってID/PWを社外にメール送信する」。メール送信時の注意事項の研修（10），キーワードによる送信ブロックが未有効（5），課長がPWをメールで周知していて，メールにPWが含まれている（12）が関連。
- **設問3 b**：2-2は「脆弱性を悪用してインターネットから不正操作し，キーロガーを埋め込む」。脆弱性修正の遅滞ない適用（3），インターネットからの通信を全て禁止するFW（4），マルウェア対策ソフト（2）が関連する。
