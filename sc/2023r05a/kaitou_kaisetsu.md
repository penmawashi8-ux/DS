## 問1 Webアプリケーションプログラムの開発（Q社 WebアプリQ / 格納型XSS）

| 設問 | 解答 |
|---|---|
| 設問1(1) | イ |
| 設問1(2) | レビュータイトルを出力する前にエスケープ処理を施す。 |
| 設問2 | HTMLがコメントアウトされ一つのスクリプトになるような投稿を複数回に分けて行った。 |
| 設問3(1) | XHRのレスポンスから取得したトークンとともに，アイコン画像としてセッションIDをアップロードする。 |
| 設問3(2) | 会員のアイコン画像をダウンロードして，そこからセッションIDの文字列を取り出す。 |
| 設問3(3) | ページVにアクセスした会員になりすまして，WebアプリQの機能を使う。 |
| 設問4 | スクリプトから別ドメインのURLに対してcookieが送られない仕組み |

### 解説

#### 設問1(1)　［読解］＋［知識］
> 本文：図3「<div class="review-title">Good**<script>**xhr=new XMLHttpRequest();/*</div>」（投稿したレビューがページに保存され，そのまま出力されている）
> 本文：「ページVに**アクセスしたときに**生じる影響」

**知識**：XSSの種類。
- **格納型**：スクリプトがサーバに保存され，ページを見た人全員のブラウザで実行される
- **反射型**：リクエストに含めたスクリプトが，そのままレスポンスに返されて実行される
- **DOM Based**：サーバを通らず，ブラウザ側のスクリプトがDOMを書き換えて起きる

**考え方**：会員Aが投稿したレビューに入っていて，ページVを開いた人で実行されるので格納型。

**答え**：イ

#### 設問1(2)　［読解］＋［知識］
> 本文：図3 会員Bのレビュー詳細「(**&gt;**_**&lt;**)」（詳細はエスケープされている），レビュータイトル「Good<script>…」（**タイトルはそのまま**）

**知識**：XSSの根本対策は，出力するときに `<` `>` `"` `&` などを実体参照に置き換える**エスケープ処理**。

**考え方**：レビュー詳細はエスケープされているのに，レビュータイトルはされていない。タイトルの出力にエスケープを加える。

**答え**：レビュータイトルを出力する前にエスケープ処理を施す。

#### 設問2　［読解］
> 本文：図1「レビュータイトルとレビュー詳細の欄は…それぞれ**50字**と300字の入力文字数制限」
> 本文：図3「Good<script>xhr=new XMLHttpRequest();**/***</div>…」→次のレビュー「***/**url1=…;/*</div>」→最後「*/xhr2.send(form);}**</script>**」，「会員Aによって**15件**のレビューが投稿されている」

**考え方**：スクリプトを50字以内に分けて15回投稿している。各タイトルの最後を `/*`，次のタイトルの先頭を `*/` にして，間に挟まるHTML（`</div>` や次のレビューの日付など）をJavaScriptのコメントにしてしまう。ブラウザから見ると，最初の `<script>` から最後の `</script>` までが一つのスクリプトになる。

**答え**：HTMLがコメントアウトされ一つのスクリプトになるような投稿を複数回に分けて行った。

#### 設問3(1)　［読解］
> 本文：図4 8行目「token = page.getElementById("**token**").value」，13行目「cookie = **document.cookie**」，16行目「file = new File([cookie], "a.png", {type: "image/png"})」，17〜19行目「uploadfile…token…xhr2.send(form)」（送り先は /user/upload）
> 本文：図1「アイコン画像のアップロードは…画像ファイル…トークン」，「cookieに**HttpOnly属性を付与していない**」「画像ファイルの**形式をチェックしていない**」

**考え方**：1回目のXHRで会員プロフィール設定ページを読み，アップロードに必要なトークンを取り出す。次に，閲覧者のcookie（＝セッションID）を中身にした偽の画像ファイルを作り，トークンと一緒にアイコン画像としてアップロードする。HttpOnlyがないのでcookieを読め，形式チェックがないので画像でなくても受け付けられる。

**答え**：XHRのレスポンスから取得したトークンとともに，アイコン画像としてセッションIDをアップロードする。

#### 設問3(2)　［読解］
> 本文：図1「アップロードしたアイコン画像は，会員プロフィール設定ページや，**レビューページに表示**される」
> 本文：図3「<img src="**/users/dac6c8f12f867ed5/icon.png**">」（アイコンはURLで取得できる）

**考え方**：被害者がレビューを書けば，そのアイコン（中身はセッションID）がレビューページに出る。攻撃者はそのアイコン画像のファイルをダウンロードし，中の文字列を読めばよい。

**答え**：会員のアイコン画像をダウンロードして，そこからセッションIDの文字列を取り出す。

#### 設問3(3)　［読解］
> 本文：図1「ログインした会員には，**セッションIDをcookieとして払い出す**」「商品の購入機能：ログイン済み会員だけが利用できる」「クレジットカード情報を登録するページ」

**考え方**：セッションIDがあれば，ログインしなくてもその会員としてアクセスできる。購入やプロフィール変更など，WebアプリQの機能をその会員になりすまして使える。

**答え**：ページVにアクセスした会員になりすまして，WebアプリQの機能を使う。

#### 設問4　［知識］
> 本文：図4 13行目「cookie = **document.cookie**」，3行目「xhr.open("get", "https://□□□.co.jp/user/profile")」

**知識**：cookieはドメインごとに管理される。攻撃者のドメインのページで document.cookie を読んでも，攻撃者ドメインのcookieしか取れない。さらに別ドメイン（□□□.co.jp）へのXHRでは，既定ではcookieが送られない（送らせる設定にしても，CORSで許可されなければレスポンスを読めない）。

**考え方**：ログイン済みの状態はcookieで判断されるので，cookieが送られなければ /user/profile は未ログイン扱いになり，トークンもセッションIDも手に入らない。

**答え**：スクリプトから別ドメインのURLに対してcookieが送られない仕組み

## 問2 セキュリティ対策の見直し（M社 Bサービス / 無線LAN）

| 設問 | 解答 |
|---|---|
| 設問1(1) | a：利用者ID　b：パスワード（順不同） |
| 設問1(2) | c：このサーバ証明書は，信頼された認証局から発行されたサーバ証明書ではない　d：このサーバ証明書に記載されているサーバ名は，接続先のサーバ名と異なる（c・d順不同） |
| 設問1(3) | HTTPのアクセスをHTTPSのアクセスに置き換えてアクセスする。その後，偽サイトからサーバ証明書を受け取る。 |
| 設問2(1) | 外部共有者のメールアドレスに自身の私用メールアドレスを指定する。 |
| 設問2(2) | e：MACアドレス |
| 設問3(1) | RADIUS |
| 設問3(2) | f：秘密鍵 |
| 設問3(3) | g：業務PCから取り出せないように |
| 設問3(4) | EAP-TLSに必要な認証情報は，業務PCにしか格納できないから |
| 設問3(5) | 来客用無線LANからインターネットにアクセスする場合の送信元IPアドレスをa1.b1.c1.d1とは別のIPアドレスにする。 |
| 設問3(6) | h：DNS |
| 設問3(7) | 表3：1　表4：1，4 |

### 解説

#### 設問1(1)　［読解］
> 本文：表1 Bサービス「従業員ごとに割り当てられた**利用者ID**と**パスワード**でログインし，利用する」「a1.b1.c1.d1 からだけ，Bサービスにログイン可能」

**考え方**：来客用無線LANからも送信元はa1.b1.c1.d1になる（表4 項番1でNAT）ので，IPアドレス制限は通ってしまう。残る壁は利用者IDとパスワードだけ。

**答え**：a：利用者ID　b：パスワード

#### 設問1(2)　［知識］
> 本文：図2「このサーバ証明書は，失効している」「このサーバ証明書は，有効期限が切れている」（残りの2つを答える）

**知識**：ブラウザがサーバ証明書で確かめることは主に4つ。
- **信頼された認証局**から発行されているか（自己署名などではないか）
- 証明書の**サーバ名がアクセス先と一致**するか
- 失効していないか
- 有効期限内か

攻撃者は正規のBサービスの証明書（秘密鍵）を持てないので，偽サイトでは前の2つのどちらかで必ずエラーになる。

**答え**：c：このサーバ証明書は，信頼された認証局から発行されたサーバ証明書ではない　d：このサーバ証明書に記載されているサーバ名は，接続先のサーバ名と異なる

#### 設問1(3)　［読解］＋［知識］
> 本文：表1 Bサービス「HTTP Strict Transport Security（**HSTS**）を有効にしている」「業務PC：日常業務のほか，**Bサービスへのアクセス**」
> 本文：下線①「**先ほどと同じ**エラーメッセージが表示されます」

**知識**：HSTSを一度受け取ったブラウザは，そのサイトへの http:// のアクセスを，通信する前に自分で **https:// に置き換える**。

**考え方**：業務PCは普段Bサービスを使っていてHSTSを覚えている。http:// と打っても HTTPS で偽サイトにつなぎに行き，偽サイトのサーバ証明書を受け取った時点で検証に失敗して，さっきと同じエラーになる。

**答え**：HTTPのアクセスをHTTPSのアクセスに置き換えてアクセスする。その後，偽サイトからサーバ証明書を受け取る。

#### 設問2(1)　［読解］
> 本文：表1「共有したいファイルの指定，**外部の共有者のメールアドレスの入力**及び上長承認申請」「外部共有リンクが…外部の共有者宛てに電子メールで自動的に送信される」「Bサービスに**ログインせずに**ファイルをダウンロード可能」
> 本文：Yさん「（宛先を）**確認できていない上長もいる**」

**考え方**：宛先に自分の私用メールアドレスを入れて申請すれば，上長が確認せずに承認したとき，リンクが私用アドレスに届く。社外からログインなしでダウンロードできる。

**答え**：外部共有者のメールアドレスに自身の私用メールアドレスを指定する。

#### 設問2(2)　［読解］
> 本文：表1 AP「従業員用無線LANだけに**MACアドレスフィルタリング**が設定されており，事前に…登録された業務PCだけが接続できる」
> 本文：表5「m-employee」の事前共有キー（**PSK**は全員共通）

**考え方**：PSKは従業員なら知っている。MACアドレスは自由に書き換えられるので，個人所有PCのMACアドレスを業務PCと同じにすれば，従業員用無線LANに入れる。

**答え**：e：MACアドレス

#### 設問3(1)　［知識］
> 本文：下線③「認証サーバ」，設問「EAPで使う**UDP上**のプロトコル」

**知識**：IEEE 802.1X（EAP）の認証サーバとAP（オーセンティケータ）の間は **RADIUS**（UDP 1812番）でやり取りする。

**答え**：RADIUS

#### 設問3(2)(3)　［知識］
> 本文：「クライアント証明書とそれに対応する［ f ］」「［ f ］は［ g ］しておくために業務PCの**TPM**に格納し，保護します」

**知識**：
- クライアント証明書には公開鍵が入っている。EAP-TLSでは，それに対応する**秘密鍵**で署名して本人であることを示す。
- **TPM**は鍵を内部で生成・保管し，**外に取り出せない**ようにするチップ。署名などの処理もTPMの中で行う。

**答え**：f：秘密鍵　g：業務PCから取り出せないように

#### 設問3(4)　［読解］
> 本文：「従業員が自身の業務PCにインストールするのではなく，**ディレクトリサーバの機能で業務PCに格納**」「秘密鍵は…業務PCの**TPMに格納**」

**考え方**：方法1はMACアドレスをまねるだけで入れた。EAP-TLSでは証明書と秘密鍵が必要になる。証明書は従業員の手を通らずに業務PCに入り，秘密鍵はTPMから取り出せないので，個人所有PCにコピーして使うことができない。

**答え**：EAP-TLSに必要な認証情報は，業務PCにしか格納できないから

#### 設問3(5)　［読解］
> 本文：表4 項番1「192.168.10.0/24（来客用）→全て　HTTP，HTTPS　許可　NAT有効」，注1「送信元IPアドレスが**a1.b1.c1.d1**に変換される」
> 本文：表1 Bサービス「a1.b1.c1.d1 **からだけ**，Bサービスにログイン可能」，表3「WAN-IF1：a1.b1.c1.d1　サブネットマスク **255.255.255.248**」（ほかのグローバルIPアドレスも使える）

**考え方**：来客用無線LANから出た通信もa1.b1.c1.d1になるので，Bサービスにログインできてしまう。来客用だけ別のグローバルIPアドレスに変換すれば，Bサービスは受け付けない。

**答え**：来客用無線LANからインターネットにアクセスする場合の送信元IPアドレスをa1.b1.c1.d1とは別のIPアドレスにする。

#### 設問3(6)　［読解］
> 本文：表1「DHCPサーバ：業務PC，**来客持込端末**にIPアドレスを割り当てる」「DNSサーバ：業務PC，**来客持込端末**が利用するDNSキャッシュサーバ」
> 本文：「Dルータでは，DHCPサーバ機能及び**DNSキャッシュサーバ機能**を有効にする」

**答え**：h：DNS

#### 設問3(7)　［読解］
> 本文：「来客持込端末は，**M社のネットワークを経由せずに**…インターネットに接続」「プロジェクターについては，来客用無線LANを利用せず，HDMIケーブルで接続」
> 本文：表3 項番1「VLAN10　192.168.10.1」，表4 項番1「192.168.10.0/24→WAN-IF1」，項番4「192.168.10.0/24→192.168.30.0/24　DNS」

**考え方**：来客用無線LAN（VLAN10，192.168.10.0/24）はもう誰も使わない。これに関係する設定を全部消す。表3は項番1，表4は項番1と4。

**答え**：表3：1　表4：1，4

## 問3 継続的インテグレーションサービスのセキュリティ（N社 Nサービス）

| 設問 | 解答 |
|---|---|
| 設問1 | ウ，エ |
| 設問2(1) | 偽サイトに入力されたTOTPを入手し，そのTOTPが有効な間にログインした。 |
| 設問2(2) | ア |
| 設問2(3) | イ |
| 設問2(4) | /procファイルシステムから環境変数を読み取った。 |
| 設問2(5) | 認証に用いる情報に含まれるオリジン及び署名をサーバが確認する仕組み |
| 設問2(6) | a：ア |
| 設問3(1) | 有効なコード署名が付与された偽のPアプリをJストアにアップロードする攻撃 |
| 設問3(2) | J社のWebサイトから削除する。 |
| 設問3(3) | 秘密鍵が漏れないという利点 |
| 設問3(4) | 影響：Pアプリを起動できない。　対応：Pアプリをアップデートする。 |

### 解説

#### 設問1　［読解］
> 本文：「CIデーモンは…**特権を付与せずに**新しい**コンテナ**を起動し，当該コンテナ内で…実行する」
> 本文：表2 バックエンド「**インターネットへの通信が可能**である」
> 本文：下線①「コンテナによる仮想化の脆弱性を悪用しなくても成功してしまうもの」

**考え方**：コンテナの中からは，外のプロセス（CIデーモンやほかの利用者のビルド）には手を出せない。インターネットへの通信はできるので，それだけで済む処理を選ぶ。
- ア CIデーモンの中断，イ 全プロセスの列挙，オ ほかの利用者の出力取得：コンテナの外に出ないとできない
- ウ 外のWebサーバへの不正アクセス，エ 攻撃者サイトから命令を取ってきて実行：コンテナ内から通信できれば成功する

**答え**：ウ，エ

#### 設問2(1)　［読解］＋［知識］
> 本文：「アプリに表示される，**時刻を用いたワンタイムパスワード（TOTP）**を…入力する」
> 本文：「Uさんは社内で同日**10時**にログインを試み，一度失敗した」「同日**10時**の国外IPアドレスからのログイン」「URL中のドメイン名は…異なっており…**偽サイト**だった」

**知識**：TOTPは一定時間（例えば30秒）だけ有効。その間なら誰が入力しても通る。

**考え方**：Uさんが偽サイトにID・パスワード・TOTPを入力した同じ時刻に，攻撃者がそれをすぐに正規サイトへ入力してログインした（リアルタイムフィッシング）。Uさん側は偽サイトなので「失敗」に見えた。

**答え**：偽サイトに入力されたTOTPを入手し，そのTOTPが有効な間にログインした。

#### 設問2(2)　［知識］
> 本文：「RFC 9162に規定された**証明書発行ログ**」

**知識**：**Certificate Transparency（CT）**は，認証局が発行したサーバ証明書を公開ログに記録させる仕組み。ドメインの持ち主は，自分の知らない証明書が発行されていないかを検索できる。

**答え**：ア

#### 設問2(3)　［知識］
> 本文：「**SNI**には，著名なOSS配布サイトのドメイン名が指定」「HTTP **Hostヘッダー**では別のドメイン名」「特定の**CDN事業者**のIPアドレス」

**知識**：**ドメインフロンティング**は，CDNの上で，TLSのSNI（外から見える）には無害なドメインを書き，暗号化された中のHostヘッダーに本当の接続先を書いて，フィルタや監視をすり抜ける手法。

**答え**：イ

#### 設問2(4)　［読解］＋［知識］
> 本文：表1 シークレット機能「ビルドスクリプトを実行するシェルに設定される**環境変数**」
> 本文：「**管理者権限**をもつ不審なプロセス（プロセスY）」がバックエンドで稼働

**知識**：Linuxでは，各プロセスの環境変数が **/proc/<PID>/environ** に入っている。管理者権限なら，どのプロセスのものでも読める。

**考え方**：シークレットはビルドを実行するシェルの環境変数として渡される。管理者権限のプロセスYなら，/procからほかの利用者のビルドの環境変数を読める。

**答え**：/procファイルシステムから環境変数を読み取った。

#### 設問2(5)　［知識］
> 本文：図2 3「偽サイトでログインを試みてしまっても，クラウド管理サイトに不正ログインされることのないよう…**WebAuthn**」

**知識**：WebAuthnでは，認証器が秘密鍵で署名する。署名するデータには，ブラウザが入れた**アクセス先のオリジン**が含まれる。サーバは署名とオリジンを確かめるので，偽サイトで作られた署名（偽サイトのオリジン入り）は正規サイトでは通らない。TOTPのように値を横流しできない。

**答え**：認証に用いる情報に含まれるオリジン及び署名をサーバが確認する仕組み

#### 設問2(6)　［知識］
> 本文：図2 4「サーバ証明書を**発行できる認証局を限定**するために…権威DNSサーバに…［ a ］レコード」
