## 問1 インシデント対応体制の整備（N社 / CSIRT・開発サーバへの侵入）

| 設問 | 解答 |
|---|---|

| 設問1(2) | 他のサービスで利用したパスワードとは別のものを設定すること |
| 設問1(3) | IPアドレスから分かる地理的位置について，過去のログインのものとの違いを確認する。（又は，WebブラウザのCookieを利用し，過去にログインした端末かを判定する。） |

| 設問3(1) | c：オ |
| 設問3(2) | d：イ　e：カ（順不同）　f：ウ |
| 設問4(1) | 5 |
| 設問4(2) | 脆弱性Mを悪用しても一般利用者権限での操作であるが，“/etc/shadow”ファイルの閲覧には管理者権限が必要であるから |

| 設問4(5) | FW2において，インターネットからのインバウンド通信はN社とV社からの通信だけを許可する。 |
| 設問5 | 複数の脆弱性が同時に悪用される可能性の観点（又は，対応を見送った脆弱性の影響の観点） |

### 解説

#### 設問1(1)(2)　［知識］
> 本文：図5「16名の利用者IDが不正ログインされ」「①**パスワードリスト攻撃**と推定された」「攻撃の接続元IPアドレスは五つ」

**知識**：**パスワードリスト攻撃**は，他のサービスから漏れた「利用者IDとパスワードの組」のリストを使って，別のサービスにログインを試す攻撃。総当たりではなく，同じパスワードを使い回している人だけが狙われる（採点講評：ブルートフォースやパスワードスプレーと区別できていない解答が多い）。防ぐには，サービスごとに違うパスワードにする。

**答え**：(1) 外部から入手した利用者IDとパスワードの組みのリストを使ってログインを試行する攻撃　(2) 他のサービスで利用したパスワードとは別のものを設定すること

#### 設問1(3)　［知識］
> 本文：下線③「ログインが**普段と異なる環境**から行われた場合，会員が事前に登録した電子メールアドレスにその旨を通知する」

**知識**：いわゆるリスクベース認証。普段と比べる手がかりとして，接続元IPアドレスから推定される**地理的位置**，ブラウザに残した**Cookie**（前にログインした端末か），ブラウザの種類などを使う。

**答え**：IPアドレスから分かる地理的位置について，過去のログインのものとの違いを確認する。（又は，WebブラウザのCookieを利用し，過去にログインした端末かを判定する。）

#### 設問1(4)(5)　［知識］
> 本文：図5「記録されていた時刻情報の［ a ］が**日本標準時**であり，**協定世界時**に対し時刻情報が［ b ］時間進んだ値で記録」「［ a ］を示す情報が記録されていなかったログも存在した」

**知識**：日本標準時（JST）は協定世界時（UTC）より**9時間**進んでいる（UTC+9）。ログの時刻がどの**タイムゾーン**かが分からないと，複数のログを突き合わせるときにずれる。

**答え**：a：タイムゾーン　b：9

#### 設問2　［読解］
> 本文：図2 注記2「店舗管理システムと社内LANとは，ネットワークが分離されている。…店舗管理システムと社内LANとの間でデータの受渡しが必要な場合は，**USBメモリ**を用いる」「N社の関係部門は，**管理用PC**を操作して店舗管理サーバを利用する」

**考え方**：ネットワークはつながっていなくても，USBメモリでデータを運んでいる。社内LANのPCで感染したUSBメモリを管理用PCに挿せば，そこから店舗管理サーバに広がる。

**答え**：マルウェアに感染したUSBメモリを介して管理用PCに侵入し，さらに店舗管理サーバへ侵入する。

#### 設問3(1)　［読解］
> 本文：表2「［ c ］：**基本方針の策定**やN社インシデント対応ポリシの**承認**を担当する」，「N社は，**情報セキュリティ委員会**を設置している。同委員会は，経営陣が委員となり，情報セキュリティについての**基本方針**…を取り扱う」

**答え**：c：オ（情報セキュリティ委員会）

#### 設問3(2)　［知識］
> 本文：図7「準備」→「［ d ］［ e ］」→「封じ込め，［ f ］，復旧」→「事後活動」

**知識**：NIST SP 800-61 のインシデント対応ライフサイクルは，①準備，②**検知と分析**，③封じ込め・**根絶**・復旧，④事後活動の4段階。

**答え**：d：イ（検知）　e：カ（分析）　f：ウ（根絶）

#### 設問4(1)　［読解］
> 本文：図2 注記4「N社：**x1.y1.z1.0/28**」「V社：**x2.y2.z2.128/30**」，図8「N社でもV社でもない複数のIPアドレスから**SSH接続**があり」「N社及びV社からの通信は正規のものだけ」
> 本文：図9 インバウンド通信（SSH）：x2.y2.z2.130，x2.y2.z2.129，x1.y1.z1.100，**x2.y2.z2.60**，x1.y1.z1.240，**x2.y2.z2.58**，**a2.b2.c2.d2**

**考え方**：/30 のV社は .128〜.131 だけなので，x2.y2.z2.60 と .58 はV社ではない。不正ログインはSSHなので，N社（x1.y1.z1.0〜15）でもV社でもないSSHの接続元を数える。x1.y1.z1.100，x1.y1.z1.240 は /28（0〜15）の範囲外なのでN社でもない。

- x1.y1.z1.100，x1.y1.z1.240，x2.y2.z2.60，x2.y2.z2.58，a2.b2.c2.d2 → 5個

（採点講評でも正答率が低かった。アドレス範囲の確認がポイント。）

**答え**：5

#### 設問4(2)　［読解］
> 本文：図3(2)「開発支援ツールJは，OSの**一般利用者権限**…で動作」，表3 脆弱性M「開発支援ツールJを実行している**利用者アカウントの権限**で任意のコマンドを実行できる」，脆弱性L「一般利用者権限で…指定したプログラムを**管理者権限**で起動できる」
> 本文：図3(3)「認証情報は，“/etc/shadow”ファイルに格納」（パスワードハッシュが入っている）

**知識**：/etc/shadow はパスワードのハッシュ値を持つので，**管理者（root）しか読めない**。

**考え方**：脆弱性Mだけでは一般利用者の権限でしかコマンドを動かせないので読めない。脆弱性Lと組み合わせて管理者権限を得たので読めた。

**答え**：脆弱性Mを悪用しても一般利用者権限での操作であるが，“/etc/shadow”ファイルの閲覧には管理者権限が必要であるから

#### 設問4(3)　［読解］
> 本文：図3(3)「R1サーバの“/etc/hosts.allow”ファイルの設定において，SSH接続の接続元を**N社とV社に限定**している。このファイルの変更には，**管理者権限**が必要」
> 本文：図10(2)「⑦R1サーバをインターネット経由で操作するために設定を変更した」→「AC-Xを利用して**SSH接続**でR1サーバにログインした」

**考え方**：攻撃者のIPアドレスからSSHでログインできたのは，管理者権限で hosts.allow に自分の接続元を書き加えたから（採点講評：正答率がやや低い）。

**答え**：攻撃の接続元IPアドレスを“/etc/hosts.allow”ファイルに追加する。

#### 設問4(4)　［読解］（計算）
> 本文：図10「F1ファイルは…IPアドレス**a1.b1.c1.d1**のサーバにアップロード」「サイズは**320kバイト**」「ツールXが**8個**のIPアドレスをスキャンした結果」「IPアドレスごとの出力結果は**固定長**」
> 本文：図9 アウトバウンド「R1サーバ→a1.b1.c1.d1　HTTP　**320**」「R1サーバ→**a2.b2.c2.d2**　HTTP　**960**」

**考え方**：F1は320kバイトで8個なので，1個当たり40kバイト。もう一つのアップロード先 a2.b2.c2.d2 への960kバイトがF2と考えられ，960 ÷ 40 ＝ 24個。

**答え**：24

#### 設問4(5)　［読解］
> 本文：図3(1)「インターネットからのインバウンド通信は，FW2において，**各サーバへのSSH接続及びHTTP接続を許可**し」，(3)「HTTP接続で開発支援ツールJを操作できる。**接続制限は行っていない**」
> 本文：図3(1)「N社及びV社はインターネットを介して…テスト…開発業務を行う」

**考え方**：脆弱性MはHTTPで誰でも突けた。hosts.allowは管理者権限があれば書き換えられる。開発用システムを使うのはN社とV社だけなので，その手前のFW2で，インターネットからの通信をN社とV社のアドレスだけに絞る（採点講評：正答率がやや低い）。

**答え**：FW2において，インターネットからのインバウンド通信はN社とV社からの通信だけを許可する。

#### 設問5　［読解］
> 本文：表3 脆弱性L「…R1サーバに**SSH接続してログインする必要**があり，脆弱性Lが悪用される可能性は低い」，脆弱性M「…**一般利用者権限**で動作しており…影響は小さい」（それぞれ単独で評価）
> 本文：図10(1)「⑥脆弱性Lと脆弱性Mを**悪用して**」

**考え方**：Lだけ，Mだけで見ると低リスクに見えたが，Mでコマンドを実行し，Lで管理者になる組合せで大きな被害になった。複数の脆弱性を組み合わせた悪用を考える，又は，見送った脆弱性が残っていることがほかの脆弱性の影響を大きくしないかを見る。

**答え**：複数の脆弱性が同時に悪用される可能性の観点（又は，対応を見送った脆弱性の影響の観点）

## 問2 クラウドセキュリティ（C社 / BYOD・DHCP・IDaaS・CASB）

| 設問1(1) | オ |
| 設問1(2) | 多くの個人所有機器をC社内LANに接続することによって，IPアドレスが枯渇するという問題が引き起こされた。 |
| 設問1(3) | 稼働させたまま：L2SWにミラーポートを設定し，そのポートにLANモニタを接続してDHCP OFFERの数を確認する。　停止させて：DHCPによるIPアドレスの配布がないことを確認する。 |
| 設問2 | 企画部の部員がアクセスできるチャットエリアで共有されている情報 |

| 設問3(2) | c：エ |
| 設問4(1) | インターネットを使って情報収集する業務（又は，事業部や企画部の顧客への提案や企画の立案） |

| 設問6(2) | 管理者が，Pソフトを，一般利用者権限では変更できないように設定する。 |

### 解説

#### 設問1(1)(2)　［読解］＋［知識］
> 本文：下線①「上位2オクテットが**169.254**に設定されたIPアドレス」，Kさん「DHCPサーバが**正常に動作していない**場合にしばしば確認される」
> 本文：「APに接続する機器に**192.168.1.20〜192.168.1.240**の範囲のIPアドレスを配布」（221個），「**多くの従業員**は，個人所有機器をAPに接続して使用」「新入社員が配属されたある日」「13時に…起動したところ」

**知識**：DHCPでアドレスをもらえなかった機器は，自分で 169.254.0.0/16 の**リンクローカルアドレス**を付ける。同じセグメントの中でしか通信できない。

**考え方**：従業員150名がC-PCとスマートフォンなど個人所有機器を何台もつなぐと，221個のアドレスでは足りない。新入社員でさらに増え，後から接続した機器はアドレスをもらえなかった。

**答え**：(1) オ　(2) 多くの個人所有機器をC社内LANに接続することによって，IPアドレスが枯渇するという問題が引き起こされた。

#### 設問1(3)　［知識］
> 本文：コメント2「③UTM以外にDHCPサーバが稼働しているかどうかも調査する」，「C社内LANのネットワークセグメントは**一つだけ**」

**知識**：DHCPは，クライアントがDISCOVERをブロードキャストし，サーバが**OFFER**で答える。
- 稼働させたまま：L2SWのミラーポートにLANモニタをつないで，DISCOVERに対するOFFERがいくつ返ってくるか（UTM以外からも来ていないか）を見る。
- 止めて：UTMのDHCPを止めても誰かがアドレスを配っていれば，ほかにDHCPサーバがある。

（採点講評：不正なAPの検出と混同した解答が多かった。）

**答え**：稼働させたまま：L2SWにミラーポートを設定し，そのポートにLANモニタを接続してDHCP OFFERの数を確認する。　停止させて：DHCPによるIPアドレスの配布がないことを確認する。

#### 設問2　［読解］
> 本文：状況1「企画部の部員がサービスRに開設した**チャットエリア**」，状況2「Vさんを含む部員の**数名**は…同じパスワードを設定」，E部長「仮に情報漏えいがあった場合，**最大で**どの程度の被害となり得るか」

**考え方**：ログがないので何を見られたかは分からない。乗っ取られた可能性のある企画部の部員のアカウントで見られる範囲，つまり企画部の部員がアクセスできるチャットエリアに何が共有されていたかを調べれば，最大の被害が分かる（採点講評：正答率がやや低い）。

**答え**：企画部の部員がアクセスできるチャットエリアで共有されている情報

#### 設問3　［知識］
> 本文：「APへの接続時にIEEE 802.1X…でのディジタル証明書による認証を行う」，図2「4.認証の成功を通知」→「5.暗号鍵を生成するための情報」→「6.暗号鍵の配布」

**知識**：802.1Xでは，接続する端末が**サプリカント**，APやスイッチが**認証装置**（オーセンティケータ），RADIUSサーバが**認証サーバ**。認証が終わって暗号鍵が配られるまでは，端末は普通の通信（DHCPを含む）ができない。

**答え**：a：C-PC　b：AP　c：エ（“6.”より後に）

#### 設問4(1)　［読解］
> 本文：「事業部及び企画部では，顧客への提案や企画の立案時に**インターネット上にある多くの情報を収集**，取捨選択，加工することによって付加価値を生み出すことが不可欠」，要件4「ただし，**業務での情報収集は妨げない**ようにする」

**考え方**：許可するサイトを限ると，事業部・企画部の幅広い情報収集ができなくなる。

**答え**：インターネットを使って情報収集する業務

#### 設問4(2)(3)　［読解］
> 本文：要件4「業務で利用するSaaSは，総務Gが契約したSaaSだけに制限する。また，**業務に不要なWebサイトへのアクセスを制限**する」，表3 番号2 URLフィルタリング「“ショッピング”…“オンラインストレージ”…などの分類…**管理者が選択**」
> 本文：要件5「総務Gが契約したSaaSには，**総務Gが管理するアカウント**でアクセスする。C-PCからは，従業員が**個人で管理するアカウント**でのアクセスができないようにする」，表3 番号1「SaaSへのログイン時に，**許可された利用者IDの場合だけ**通信を許可」

**考え方**：URLを分類で絞るのが番号2。同じSaaSでも会社のアカウント以外ではログインさせないのが番号1。

**答え**：(2) 2　(3) 1

#### 設問4(4)　［読解］
> 本文：表2 サービスQ「ディジタル証明書による**TLSクライアント認証**」，要件2「業務で利用する…SaaSへのアクセスの際，**機器をクライアント認証**する」
> 本文：図3「5.認証要求」「6.**利用者の認証**」（サービスQ）

**考え方**：会社の機器かどうかは，その機器に入れたクライアント証明書で分かる。サービスQで認証する5〜6の段階で，証明書を持たない機器ははじかれる。

**答え**：記号：ウ　方法：TLSクライアント認証による検証

#### 設問5(1)　［知識］
> 本文：下線⑦「SaaS又はSaaS事業者が何らかのセキュリティ規格に準拠していることの**第三者による認証**」

**知識**：例として，情報セキュリティマネジメントの **ISMS認証**（ISO/IEC 27001），クラウドの ISO/IEC 27017（ISMSクラウドセキュリティ認証），委託先の内部統制を保証する **ISAE3402/SSAE16**（SOC2など）などがある。

**答え**：ISMS認証（又は，ISAE3402/SSAE16）

#### 設問5(2)　［読解］
> 本文：要件7「SaaSからの**情報漏えいを防ぐ**ための技術的対策」，「サービスNを**経由しない不正アクセス**によるSaaSからの情報漏えいを防ぐ」，表3 番号4「SaaSが提供するAPIを使って，特定フォルダに保管するファイルを**自動的に暗号化**」

**考え方**：サービスNを通らずに直接SaaSにアクセスされても，ファイルが暗号化されていれば中身は読まれない。

**答え**：d：4

#### 設問6　［読解］
> 本文：要件2「業務での**個人所有機器の利用を禁止**」，表2 注1「ディジタル証明書は，**クレデンシャル**とともに検証する」（証明書と秘密鍵で機器を認証）
> 本文：「管理者は，Pソフトを，**一般利用者権限では動作の停止やアンインストールができない**ように設定することができる」，「持出C-PC」はオフィスの外で使う

**考え方**：
- (1) 機器の認証は証明書と秘密鍵で行う。秘密鍵を書き出せると，個人のPCにコピーして使えてしまうので，書き出しできないようにする（採点講評：正答率が低い）。
- (2) 要件4・5はPソフトでサービスNを経由させて実現している。従業員がPソフトを止めたり設定を変えたりできないよう，管理者だけが変更できる設定にする。

**答え**：(1) 秘密鍵を書き出しできないように設定する。　(2) 管理者が，Pソフトを，一般利用者権限では変更できないように設定する。
