## 問2 ドメイン名変更（A社→Z社，SPF/DKIM/DMARC）

| 設問 | 自作解答 |
|---|---|
| 設問1(1) a | A社ドメイン名 |
| 設問1(2) b | 全て |
| 設問2 c | STARTTLS |
| 設問3(1) | エ |
| 設問3(2) d | イ |
| 設問4(1) | 工作機械管理用アプリケーションプログラムやソフトウェア修正プログラムをマルウェアに置き換えて，顧客にダウンロード・実行させる |
| 設問4(2) 受信するメール | 社外サービスのパスワード再設定用のメール |
| 設問4(2) 続きの攻撃 | パスワードを再設定して社外サービスに不正ログインし，業務情報を窃取する |
| 設問4(3) e | ア |
| 設問5(1) | Z社ドメイン名のSPFレコードに，Tサービスのメール送信サーバを追加する |
| 設問5(2) SPF | エンベロープFromはZ社ドメイン名だが，送信するのはYサービスのサーバであり，Sサービスに登録したSPFレコードにはUサービスしか含まれていないため |
| 設問5(2) DKIM | Uサービスが付与したDKIM署名はSubjectを署名対象（hタグ）に含むが，YサービスがSubjectに通番情報を付加して改変するため，Sサービスに登録した公開鍵での検証に失敗するため |

### 解説
- **設問1**：メールサーバはA社ドメイン名宛てのメールをメールボックスに格納する。第三者中継防止としては，インターネット→自社ドメイン宛てだけ許可（項番1 = A社ドメイン名），社内のPC-LANからは任意宛先へ送信可（項番2 = 全て）。業務サーバは社内宛てのみ（項番3）。
- **設問2**：SMTPのセッション内でTLSに切り替える拡張は STARTTLS。
- **設問3(1)**：DKIM公開鍵は `<セレクタ>._domainkey.<dタグのドメイン>` に置く。s=z2024，d=z-sha.co.jp → エ。
- **設問3(2)**：Mail-Step1 は「特定のアクションを要求しない」＝ p=none（イ）。隔離は quarantine，拒否は reject。
- **設問4(1)**：A-Webサイトは顧客向けにアプリと修正プログラムを提供している。見た目を同じにしたまま配布物をマルウェア入りにすれば，顧客は正規サイトと信じて導入してしまう。
- **設問4(2)**：社外サービスに登録した連絡先がA社ドメイン名のままなら，第三者がそのドメインでメールを受信できる。パスワードリセットのメールを受け取れば，アカウントを乗っ取れる。
- **設問4(3)**：A社ドメイン名からはメールを送らないので，送信許可ホストを一つも書かず `-all`（全て不合格）にする。DMARC側で p=reject とすれば受信側が拒否できる。
- **設問5(1)**：Tサービスは Z社ドメインの From で各宛先へ個別送信するので，Mail-Step3 以降 DMARC（隔離・拒否）で落とされる。SPFレコードにTサービスの送信サーバを含める（include 等）。DKIMについてもTサービスでZ社ドメインのDKIM署名ができるならDKIMレコードの追加も考えられる。
- **設問5(2)**：ヘッダーFrom設定1ではヘッダーFromはZ社従業員のアドレスのまま。エンベロープFromはML管理者（Z社従業員）のアドレスなのでSPFはZ社ドメインのレコードで評価されるが，実際の送信元はYサービス→不一致。DKIMは h タグに Subject を含むため，Subject設定2で改変されると署名が壊れる。ARC非対応なので救済もない。両方失敗でDMARC fail→隔離・拒否。

## 問3 クレジットカード情報の漏えい（J社ECサイト）

| 設問 | 自作解答 |
|---|---|
| 設問1 a | 5 |
| 設問1 b | クロスサイトスクリプティング |
| 設問1 c | 格納 |
| 設問1 d | 2 |
| 設問1 e | SQLインジェクション |
| 設問2(1) | 下図 |
| 設問2(2) パラメータ名 | order[Payment] |
| 設問2(2) 値 | 1 |
| 設問2(3) | “次へ”ボタンでフォームが送信される際に，偽フォームに入力されたカード番号，有効期限，名義，セキュリティコードを取得し，それらをクエリ文字列に含めたGETリクエストで https://i-sha.com/ に送信する |
| 設問3(1) | 攻撃者のWebサーバのアクセスログに記録されたリクエストURIのクエリ文字列から取得する |
| 設問3(2) f | 支払手続画面（/payment）にアクセスしたアカウント名 |

設問2(1)の図（書換え後の配送先・支払方法選択画面）：
```
 /shopping
┌──────────────────────┐
│        配送先・支払方法選択              │
│ 配送先                                   │
│  [                          |▽]         │
│                                          │

```
（ラジオボタン“クレジットカード決済／銀行振込”が消え，カード情報入力欄に置き換わる）

### 解説
- **設問1 a〜c**：5行目 `/cart?add="><script>document.getElementById(…` はタグを閉じてスクリプトを注入するXSSの試行。XSSならHTMLを書き換えて偽フォームを出せる。スクリプトがサーバに保存される格納型（持続型）なら，1回の攻撃でそのページを見る全利用者に影響する。
- **設問1 d, e**：2行目 `pw=' UNION select 1 FROM…` はSQLインジェクション。DBの内容を改ざんでき，そのDB内容でページを動的生成していれば偽フォームを埋め込める（Gさんの回答と整合）。6行目の `green's` は通常の検索語の可能性が高い。
- **設問2(1)**：図2の2〜3行目は `#shopping-form … div.order_payment > div.radio` の innerHTML を，カード番号・有効期限・名義・セキュリティコードの入力欄＋hidden の order[Payment]=1 に置き換える。図3を見ると div.radio はラジオボタン2個とラベルを含む部分なので，“お支払方法”見出しは残り，ラジオボタンが消えてカード入力欄になる。
- **設問2(2)**：hidden で `name="order[Payment]" value="1"` を入れ，値1はクレジットカード決済（Payment_1）。これが /payment にPOSTされるので，支払方法がクレジットカードに固定され，支払手続画面で本物の入力フォームが再表示される（＝2回表示される）。
- **設問2(3)**：submit イベントのリスナーで値を取り出し，XMLHttpRequest で i-sha.com へ GET 送信している。
- **設問3(1)**：データは GET のクエリ文字列に含まれるので，404を返していても Web サーバのアクセスログにリクエストURIとして記録される。攻撃者はログを読むだけで入手できる。
- **設問3(2)**：送信は配送先・支払方法選択画面で“次へ”を押した瞬間（submit 時）に起こり，その結果 /payment に遷移する。したがって影響期間中に支払手続画面へアクセスした利用者（アカウント）が「送信直前までの操作をした」利用者であり，漏れなく，かつ /shopping を表示しただけの利用者は含まない。

## 問4 セキュリティ診断（B社によるMサイト診断）

| 設問 | 自作解答 |
|---|---|
| 設問1(1) a | (イ) |
| 設問1(2) b | https://test.△△△.jp/ |
| 設問1(3) c | メール受信者による画面01でのログイン |
| 設問1(4) d | ログインに成功したときにsessionIDを新たに生成し直し，それまでのsessionIDを無効にする |
| 設問1(5) e | WebブラウザにMサイトへのアクセスを常にHTTPSで行わせ，HTTP通信の盗聴や改ざんを防ぐ |
| 設問1(5) f | WebブラウザによるMIMEタイプの推測（スニッフィング）を禁止し，Content-Typeと異なる解釈によるスクリプト実行を防ぐ |
| 設問2 g | 画面09で，会社名に“●●株式会社%0D%0ATo:攻撃者のメールアドレス%0D%0A%0D%0A”を入力して変更ボタンをクリックする |
| 設問2 h | 画面07で再設定後のPWを入力してAPIkeyを発行する |
| 設問3 i | WebAPIで取得できる求職者属性情報を，当該企業に問合せ又は応募した求職者のものに限定する |
| 設問3 j | 求職者IDは登録年月日と連番で推測が容易であり，任意の求職者IDを指定して全求職者の求職者属性情報を取得できてしまうため |
| 設問3 k | 画面09でメールアドレスを変更する際に，PWの再入力を求める |
| 設問3 ℓ | セッションを乗っ取った攻撃者でもPWを知らなければメールアドレスを変更できず，PW再設定やAPIkey発行につなげられないため |

### 解説
- **設問1(1)〜(4)**：sessionID は画面01表示時からログイン成功（イ）後も同じ。ログイン前に攻撃者が取得した sessionID を被害者に使わせ（罠サイトから https://test.△△△.jp/ にPOST → 被害者のブラウザが攻撃者の sessionID 付きの画面01を表示），被害者がそのままログインすれば，攻撃者は同じ sessionID でログイン後の画面02にアクセスできる。対策はログイン成功時（イ）のセッションID再生成。
- **設問1(5)**：HSTS は以後のアクセスを HTTPS に強制（SSLストリップ等の防止）。X-Content-Type-Options: nosniff は MIME スニッフィングを止める。
- **設問2 g**：4.1 に「不審なメールが求人企業に届かない」とある。メール(あ)は変更前アドレスに送られる確認メールだが，図B・表Cのとおり会社名にヘッダーインジェクションすると To が上書きされ，攻撃者だけに届く。(3) の前に会社名を細工しておけば，確認メールを攻撃者が受けて変更を確定でき，求人企業は気付かない。
- **設問2 h**：(5) で攻撃者はPWを知った状態でログインできる。APIkey発行には画面07でのPW再確認が必要だが，今は突破できるので APIkey を発行し，(7) で WebAPI を使う。
- **設問3 i, j**：図2の 2(3)「任意の求職者IDを指定して，求職者属性情報を取得する」が利用契約の範囲（問合せ・応募の対応だけ）を超えている。求職者IDは「年月日8桁＋日ごとの連番6桁」で容易に列挙できる。
- **設問3 k, ℓ**：図Dの連鎖はメールアドレス変更→PW再設定→APIkey発行。メールアドレス変更にPW再入力を必須にすれば，セッション乗っ取りだけでは連鎖の入口に進めない。
