## 問1 ソフトウェアサプライチェーンのセキュリティ（K社 / SBOM・VEX・脆弱性管理）

| 設問 | 解答 |
|---|---|
| 設問1 | a：SPDX　b：CPE |
| 設問2(1) | ソースコードをコピーして組み込んでおり，マニフェストに記載されていないから |
| 設問2(2) | 直接依存するOSSが依存しているOSS |
| 設問2(3) | SBOMが，どのファームウェアに対応するものかを確認できるようになる。 |
| 設問3(1) | c：VEX |
| 設問3(2) | libtlsはTLSクライアントとしてだけ使用しており，脆弱性はTLSサーバとして動作するときだけ悪用されるから |
| 設問3(3) | 保守モードを有効にするとtelnetdが起動し，脆弱性が悪用され得るから |
| 設問3(4) | 実際に悪用されたことが確認されているから |
| 設問4(1) | 攻撃者が，未修正の脆弱性を含む構成要素を使っている製品を容易に特定できてしまうリスク |
| 設問4(2) | d：デジタル署名 |

### 解説

#### 設問1　［知識］
> 本文：「Linux Foundationが策定し，ISO/IEC 5962として国際標準化された［ a ］」
> 本文：「NVDでは，影響を受ける製品やソフトウェアを，［ b ］と呼ばれる構造化された名称で表している」

**知識**：
- SBOMの代表的な形式は **SPDX**（Linux Foundation，ISO/IEC 5962）と **CycloneDX**（OWASP）。ISO化されているのはSPDX。
- NVDは，影響を受ける製品を **CPE**（Common Platform Enumeration，例：cpe:2.3:a:ベンダ:製品:バージョン…）で表す。SBOMで使われるPURL（例：pkg:npm/名前@バージョン）とは書き方が違うので，照合するには対応付けが要る。

**答え**：a：SPDX　b：CPE

#### 設問2(1)　［読解］
> 本文：「KC-100の開発当時，libimgのソースコードを入手して一部を改変し，K社のソースコードの中に**コピーして組み込んでいた**」
> 本文：図1 手順1「パッケージ管理ツールの依存関係定義ファイル（**マニフェスト**）を解析し」

**考え方**：手順1はマニフェストに書かれた依存しか拾えない。ソースをコピーして取り込んだOSSはマニフェストに出てこないので漏れる。S氏が「ビルド成果物を解析して，OSSのコードが含まれていないかを検出するツール」を勧めているのはこのため。

**答え**：ソースコードをコピーして組み込んでおり，マニフェストに記載されていないから

#### 設問2(2)　［読解］＋［知識］
> 本文：図1 手順1「K社のプログラムが**直接依存している**OSSの名称とバージョンの一覧」，S氏「依存関係をたどれるツールを使ってください」

**知識**：OSSは別のOSSに依存していることが多い。K社のプログラム→OSS A→OSS B のように間接的に取り込まれる依存（**推移的依存**）も，ファームウェアに含まれる。

**答え**：直接依存するOSSが依存しているOSS

#### 設問2(3)　［読解］
> 本文：S氏「ファームウェアは同じ製品でも頻繁に更新されるので，製品名ごとのフォルダに保存するだけでは，**どのSBOMがどのファームウェアのものか分からなくなります**」，表2「ハッシュ値：SBOMの対象である**ファームウェアイメージ**のSHA-256によるハッシュ値」

**考え方**：手元のファームウェアのハッシュ値を計算し，SBOMに書かれた値と比べれば，そのSBOMがそのファームウェアのものかを確かめられる。

**答え**：SBOMが，どのファームウェアに対応するものかを確認できるようになる。

#### 設問3(1)　［知識］
> 本文：S氏「製品が個々の脆弱性の影響を受けるかどうかを**機械可読な形式**で伝える文書を［ c ］といいます。SBOMと組み合わせて使われています」

**知識**：**VEX**（Vulnerability Exploitability eXchange）。脆弱性ごとに「影響なし（not_affected）」「影響あり」「修正済み」「調査中」などの状態と根拠を記す。SBOMだけだと「含まれている＝影響あり」と誤解されやすいので，VEXで補う。

**答え**：c：VEX

#### 設問3(2)　［読解］
> 本文：表3 V1「**TLSサーバとして動作しているとき**に，細工されたハンドシェイクメッセージを受信すると…」
> 本文：表4 libtls「録画データをクラウドストレージに送信する際の，**TLSクライアントとしてだけ**使用している。Web管理画面のHTTPS通信は…**別のTLSライブラリ**で処理」

**考え方**：脆弱な機能（TLSサーバ）をKC-200は使っていない。HTTPSの管理画面も別のライブラリなので，libtlsがサーバとして動く場面がない。CVSS 9.8でも影響なしと判断できる。

**答え**：libtlsはTLSクライアントとしてだけ使用しており，脆弱性はTLSサーバとして動作するときだけ悪用されるから

#### 設問3(3)　［読解］
> 本文：表4 busybox「telnetdも含まれているが，出荷時設定では起動しない。ただし，Web管理画面で“**保守モード**”を有効にすると，保守作業用に**telnetdが起動**する」

**考え方**：出荷時は動かなくても，設定一つで起動する。保守作業中や，管理画面を乗っ取られて保守モードにされた場合に悪用される。V1と違い，脆弱な機能そのものが製品に含まれていて動く可能性がある。

**答え**：保守モードを有効にするとtelnetdが起動し，脆弱性が悪用され得るから

#### 設問3(4)　［読解］＋［知識］
> 本文：表3 V3「KEVへの掲載：**あり**」，注1「実際に**悪用されたことが確認された**脆弱性のカタログ」

**知識**：CVSS基本値は脆弱性そのものの深刻さで，実際に狙われているかは表さない。優先度は，KEVへの掲載（実際の悪用）やEPSS（今後悪用される確率）など，悪用の状況も合わせて決める。

**考え方**：V3は管理者がアップロードする画像ファイルを読む処理で使われており（表4），影響がある。そのうえで実際に悪用されているので，最も急ぐ。

**答え**：実際に悪用されたことが確認されているから

#### 設問4(1)　［読解］
> 本文：Nさん「各製品のSBOMをK社のWebサイトで**誰でもダウンロードできる**ように公開する」，表2「構成要素名」「バージョン」

**考え方**：SBOMを見れば，どの製品がどのOSSのどのバージョンを使っているかが分かる。新しい脆弱性が公表されたとき，攻撃者もSBOMを見て，修正前のカメラを狙い撃ちできる。だから契約顧客に限って提供する。

**答え**：攻撃者が，未修正の脆弱性を含む構成要素を使っている製品を容易に特定できてしまうリスク

#### 設問4(2)　［知識］
> 本文：「T社などの顧客が，SBOMが**K社によって作成され**，**改ざんされていない**ことを確認できるようにした」

**知識**：作成者の確認（真正性）と改ざんの検知（完全性）の両方ができるのは**デジタル署名**。ハッシュ値だけでは，攻撃者がSBOMとハッシュ値を一緒に差し替えられる。

**答え**：d：デジタル署名
