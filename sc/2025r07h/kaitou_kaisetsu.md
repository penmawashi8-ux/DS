### 解説
- **設問1**：図1より article は**数値型**として扱われる（SQL中でクォートで囲まれない）。
  - a `20250401'`：余分なクォートで構文エラー → “コンテンツがありません”（ア）。
  - b/c `20250401' and 'a'='a`：数値の直後にクォートが来るので、条件の真偽にかかわらず構文エラー → どちらもア。（文字列型なら b がイ、c がアになるところだが、数値型なので効かない。）
  - d `20250401 and 1=0`：構文は正しく条件が偽 → 該当なし → ア。
  - e `20250401 and 1=1`：真 → 通常どおり（イ）。d と e で応答が変わることから、真偽の差で情報を1ビットずつ抜くブラインドSQLインジェクションが成立する。
- **設問2**：サイトに変更がなく、診断員による差異もない、とされているので、変わったのは「外の世界」：診断後に**新しい脆弱性が公表された**こと、P社の**診断ツール（シグネチャ）や診断手順が更新された**こと。だから定期診断が必要。
- **設問3(1)**：TLS暗号設定ガイドラインの推奨セキュリティ型では、ECDHEは128ビットセキュリティ以上の**曲線**（P-256等）、DHEは112ビットセキュリティ以上の**鍵長**（2048ビット）を求める → ウ。
- **設問3(2)**：本文に、攻撃時は「Timeout before authentication」というメッセージが多数出力され、成功まで3〜4時間かかるとある。したがって**ログを監視して当該メッセージの大量出力を検知**すれば、成功前に気付いて遮断できる。
- **設問3(3)**：送信元IP制限は在宅・外出先からの管理者アクセスがあり運用が難しい。代わりにPC自体を認証する＝**クライアント証明書**を管理者PCに入れ、証明書を持つPCからだけログイン画面に到達できるようにする。
- **設問4(1)**：AC（攻撃元の複雑さ）は、攻撃者の制御の及ばない条件が必要かどうか。WA-1 はリクエスト中の item の数字を書き換えるだけで再現でき、条件は不要 → L。WB-1 は `administrator0001/order_history` という管理者用URLを知っていなければならず、推測困難なので攻撃成立に条件が要る → H。
- **設問4(2)**：OSコマンドはWebアプリのプロセスの権限で実行される。図2の3「一般利用者権限の専用アカウントでプロセスを実行」が管理者操作ができなかった理由。
- **設問5(1)**：CVSS現状値は、攻撃コードの成熟度や修正の有無、報告の信頼性を自分で調べて評価し、状況が変わるたびに見直す必要があり手間が掛かる。EPSSはFIRSTが日々算出して公開している確率値なので、検索して参照するだけで済む。
- **設問5(2)**：EPSS値は日々更新され変動するので、一度評価して終わりにせず**EPSS値を定期的に確認し直す**（再評価する）ことが被害防止に役立つ。
- **設問5(3)**：EPSSは「悪用される確率」の予測値。P社は脆弱性が**実際に悪用できることを確認した上で**報告するので、悪用可能性は高いとみなせる → しきい値B（1%）より高い、と扱うのが妥当。
- **設問6**：しきい値A＝7.0（基本値）、B＝1%（EPSS）。基本値は表3／表5から。
  - PB-1：基本値8.1・EPSS39% → 領域Ⅰ、環境値8.1 → A
  - PC-1：基本値5.9・EPSS96.54% → 領域Ⅲ、環境値7.7 → A
  - PD-1：基本値7.2・EPSS0.0% → 領域Ⅱ、環境値5.7 → C
  - PD-2：基本値9.8・EPSS2.6% → 領域Ⅰ、環境値8.0 → A
  - PE-1：基本値6.5・EPSS8.7% → 領域Ⅲ、環境値6.5 → B
  - Webアプリ診断分は全て領域ⅠかⅢ扱い：WA-1 環境値5.0 → B、WB-1 7.1 → A、WC-1 9.8 → S

## 問3 スマホアプリの開発（A社 Fアプリ / Cサービス / WebView）

| 設問 | 自作解答 |
|---|---|
| 設問1(1) | 攻撃者がプロキシや偽アクセスポイントで通信を中継し，偽のサーバ証明書でHTTPSを復号して，Cサービスへのリクエストのパスからストレージ名を，Authorizationヘッダーからアクセスキーを読み取る |
| 設問1(2) | Fアプリを解析（逆コンパイル）してコード中の定数からAES-CBCの共通鍵と初期ベクトルを取り出し，リソース内の暗号化されたアクセスキーを復号する |
| 設問1(3) | Authorizationヘッダーに取得したアクセスキーを指定し，GET /e-service/00000001.zip から注文番号を1ずつ増やしながら順にリクエストする |
| 設問1(4) | f-app://campaign?url=https://www.a-sha.co.jp.k-sha.co.jp/ |
| 設問2(1) | www.a-sha.co.jp |
| 設問2(2) a〜h | a：オ　b：ケ　c：ウ　d：コ　e：ア　f：イ　g：カ　h：キ |
| 設問2(3) | 通信解析ツールのプライベート認証局のルート証明書を，信頼する認証局の証明書として開発用スマホにインストールする |
| 設問3 i | (い) |
| 設問4(1) | 表示中のWebページのURLを確認できない（18字） |
| 設問4(2) | F-URLのurlクエリパラメータのURLのホスト名がwww.a-sha.co.jpである場合（https://www.a-sha.co.jp/ で始まる場合）だけWebViewで表示し，それ以外は表示しない機能 |

### 解説
- **設問1(1)**：脆弱性1は証明書検証エラーを無視する作り。攻撃者が中間者（悪性プロキシ、偽Wi-Fi等）となって自分の証明書でTLSを終端すれば、Fアプリはそのまま通信を続ける。Cサービスへのアップロード要求は `PUT /e-service/nnnnnnnn.zip` ＋ `Authorization: Bearer <アクセスキー>`（方式a）なので、パスからストレージ名、ヘッダーからアクセスキーが平文で読める。
- **設問1(2)**：アクセスキーは暗号化してリソースに保存されているが、復号に必要な共通鍵とIVが同じアプリのコード中に定数で書かれている。アプリを入手して逆コンパイルすれば鍵とIVが取れ、アクセスキーを復号できる（ストレージ名も定数）。
- **設問1(3)**：方式aのアクセスキーはストレージ内の全ファイルを操作できる。ファイル名は注文番号（00000001からの十進連番）.zipなので、番号を順に変えてGETすれば全利用者の写真を取れる。
- **設問1(4)**：図7は「先頭が `https://www.a-sha.co.jp` か」だけを見ている。末尾にスラッシュがないため、`https://www.a-sha.co.jp.k-sha.co.jp/`（攻撃者が k-sha.co.jp のサブドメインとして用意）も先頭一致で通過する。F-URLのurlに指定すればWebViewが攻撃者サイトを開き、さらにgetTokenが認証トークンを返してしまう。
- **設問2(1)**：プロキシは接続先FQDNに合わせて証明書を動的に生成する。SANには `www.a-sha.co.jp`（DNS名）を入れる。
- **設問2(2)**：明示的プロキシ経由のHTTPS。スマホ→ツールへ `CONNECT www.a-sha.co.jp:443`（a=オ、ホスト名指定。IPアドレスのエはツール自身のアドレスなので誤り）→ ツールが `200 OK`（b=ケ）→ TLS1.3ハンドシェイク：Client Hello（c=ウ）、ツールが Server Hello（d=コ）・Encrypted Extensions・Certificate（e=ア）・Certificate Verify（f=イ）・Finished（g=カ）をまとめて返し、クライアントも Finished（g）→ `GET /campaign/□□□`（h=キ）。最後にA社Webサーバの200 OK（b）がツール経由で返る、という流れで b の再使用とも整合する。
- **設問2(3)**：検証を無効化するのでなく、検証が成功するようにする：ツールのプライベートCAのルート証明書を開発用端末の信頼済みCAとして登録する。OS-αではテスト（デバッグビルド）時だけユーザ追加のCAを信頼するようアプリ側設定も加えた、という本文と整合する。
- **設問3**：方式bならアクセスキーを持つのはサーバ側だけで済み、アプリには特定ファイル用の短期の署名付きURLだけを渡せばよい。ファイル名＝注文番号なので、A社Webサーバが注文番号を採番した直後の(い)で `PUT /e-service/nnnnnnnn.zip` 用の署名付きURLを生成し、注文番号と一緒に通知するのが自然。
- **設問4(1)**：Webブラウザならアドレスバーで表示中のURL（ドメイン）や鍵マークを確認できるが、FアプリのWebViewにはURL表示がないので、偽サイトでも見分けられない。
- **設問4(2)**：図7の修正（`https://www.a-sha.co.jp/` で判定）はトークン窃取への対策。フィッシングサイト自体を開かせないためには、F-URL処理時にurlパラメータを検証し、自社ドメイン（www.a-sha.co.jp）のURLだけをWebViewで開く許可リスト方式にする。

### 解説
- **設問1**：ニュース(2)はCDN解約後もDNSにCDN向けのCNAMEが残り（ダングリングレコード）、第三者が同じCDN上で当該ホスト名を登録して乗っ取る「サブドメインテイクオーバー」。V社も同じ経緯なので、v-sha.co.jp を管理する**権威DNSサーバ**から当該CNAMEを削除する。
- **設問2(1)**：表1のIT資産管理5(3)で「他社データセンター，クラウドサービス又はレンタルサービスを契約して」利用するサーバは台帳に未登録。クラウドは図2に既にあるので、残りの二つ。
- **設問2(2)**：レジストラ／レジストリへの登録情報問合せの標準プロトコルで RFC 3912 は **WHOIS**。
- **設問2(3)(4)**：
  - 手順1：組織名で検索でき、GIPとFQDNが得られるのはZ（注記3）。キーワードは組織名「V社」（d=オ）、結果は FQDN（e=ア）と GIP（f=イ）。
  - 手順2-1/2-2：FQDNから得たドメイン名（g=ク）でXを検索 → 組織名と担当者識別番号（h=キ）→ 担当者識別番号で部署名・担当者名。注記1の「“.jp”ドメインのものについて」や表3注2（.jpだけ担当者識別番号で検索可能）とも合う。い=X。
  - 手順3-1/3-2：GIP（f）でYを検索 → 組織名とGIPの担当者識別番号 → 部署名・担当者名。う=Y。
  - これでFリストに必要な GIP、ドメイン名、各組織名・部署名・担当者名、FQDN がすべてそろう。
- **設問3(1)**：「SSHでは接続できなかったが公開サービスはWebだけが稼働」＝どのポートが開いているかの確認 → **ポートスキャン**。
- **設問3(2)**：OSやSWのバージョン、内在する脆弱性 → **脆弱性診断（スキャン）**やバナー（Serverヘッダ等）の確認。
- **設問3(3)**：継続利用なら、業務継承部門のK事業部が管理部門として最新版への更新・脆弱性修正を行い台帳に登録する。継続しないなら、停止・撤去し、DNSレコード削除、ドメイン名やGIPの返却まで行う（放置すると(2)(3)のニュースと同じ被害になる）。
- **設問4(1)**：CVSSの最新は v4.0（2023年公開）。
- **設問4(2)(3)**：KEV＝Known Exploited Vulnerabilities（米CISAが公開）。掲載条件の主なものは「実際に悪用が確認されている（CVE番号があり、修正方法が明確）」。
- **設問4(4)**：現状は「ニュースを見て確認」「話題の脆弱性を全部門に全部連絡」「各部門任せ」で、K-3（修正したかを情シ部が確認）ができない。項番1はK-2で一元管理した導入SW情報と脆弱性情報を突合して該当サーバ・部門を特定する方式に、項番2は判断ルールで対応要としたものを該当部門に絞って連絡し、修正結果を報告させる方式に改める。
