## 問1 協力会社とのファイルの受渡し（U社 / XSS・CSP・SaaS移行・FIDO）

| 設問 | 解答 |
|---|---|
| 設問1(1) | a：`&lt;`　b：`&gt;` |
| 設問1(2) | c：エ |
| 設問2(1) | http://又はhttps://で始まるURLだけを出力するようにする。 |
| 設問2(2) | URLと同じオリジンであるスクリプトファイル |
| 設問2(3) | スクリプト：HTMLファイル中に記載されたスクリプト　呼出し方法：スクリプトを別ファイルとして同一オリジンに保存して，HTMLファイルから呼び出す。 |
| 設問3(1) | d：ウ　e：ア |
| 設問3(2) | ファイルをU社が管理する鍵で暗号化してからアップロードする。 |
| 設問4(1) | f：同一利用者IDでのログイン失敗 |
| 設問4(2) | アクセス元IPアドレスを変えながら，不正アクセスを続けた場合 |
| 設問5(1) | g：メッセージをKサービスとの間で中継 |
| 設問5(2) | h：生体認証　i：Kサービス　j：アカウントを削除　k：アカウントを無効に |
| 設問5(3) | Gサービスへのアクセスを，ファイル受渡し用PCからのアクセスだけに限定できるから |

### 解説

#### 設問1(1)　［知識］
> 本文：図4「description=**<script>**alert('XSS!')**</script>**」，図3(3)「descriptionパラメタの値を画面Bの備考に出力する際には，**エスケープ処理が正しく行われており**」
> 本文：図5「備考：［ a ］script［ b ］alert('XSS!')［ a ］/script［ b ］<br>」，設問「それぞれ**4字**」

**知識**：HTMLのエスケープでは `<` → `&lt;`，`>` → `&gt;`，`"` → `&quot;`，`&` → `&amp;` に置き換える。

**答え**：a：`&lt;`　b：`&gt;`

#### 設問1(2)　［読解］＋［知識］
> 本文：図3(4)「参考URLの**リンクをクリック**すると，“XSS!”という内容のダイアログボックスが表示された」，図7「<a href="［ c ］">［ c ］</a>」

**知識**：href属性に `javascript:` で始まるURLを入れると，リンクをクリックしたときにその後ろのスクリプトが実行される。`<` や `"` を使わないので，エスケープしていても防げない。

**考え方**：クリックで初めて実行されたのでjavascriptスキーム。ア（onmouseover）は `"` で属性を閉じないと働かず，イ・ウは `<` がエスケープされるので動かない。

**答え**：c：エ

#### 設問2(1)　［読解］
> 本文：図9「<a href="**&quot;** onmouseover=alert('XSS!') foo=**&quot;**">」（`"` はエスケープされている）
> 本文：図3(6)「XSSを防ぐための基本的な処理はしているが，**HTMLタグの属性値の出力時に必要な処理**が行われていない」

**考え方**：図9から，`"` などのエスケープはできている（2つ目の誤り）。足りないのは，URLを属性に出すときに `javascript:` などのスキームを許してしまう点。出力するURLを http:// か https:// で始まるものだけにする。

**答え**：http://又はhttps://で始まるURLだけを出力するようにする。

#### 設問2(2)(3)　［知識］
> 本文：「“Content-Security-Policy: **script-src 'self'**;”…Webブラウザに対して②指定したスクリプトファイルの実行だけを許可する」，下線③「実行が制限されてしまうスクリプトの有無を確認し，もしあれば，当該箇所の呼出し方法を変更する」

**知識**：CSPの `script-src 'self'` は，**ページと同じオリジン**から読み込んだスクリプトファイルだけを実行させる。'unsafe-inline' を付けない限り，HTMLの中に直接書いたスクリプト（`<script>…</script>` や onclick などのイベントハンドラ，javascript: URL）は実行されない。XSSで差し込まれるのは普通この形なので，被害を防げる。

**考え方**：Dシステム自身がHTMLの中に直接スクリプトを書いていると，それも止まってしまう。別のファイルにして同じオリジンに置き，`<script src="…">` で読み込むように変える（採点講評でも仕組みの理解不足が指摘されている）。

**答え**：(2) URLと同じオリジンであるスクリプトファイル　(3) スクリプト：HTMLファイル中に記載されたスクリプト／呼出し方法：スクリプトを別ファイルとして同一オリジンに保存して，HTMLファイルから呼び出す。

#### 設問3(1)　［知識］
> 本文：「クラウドサービスのための［ d ］の実践の規範である**ISO/IEC 27017**」「パブリッククラウドにおける［ e ］の実践の規範である**ISO/IEC 27018**」

**知識**：ISO/IEC 27017はクラウドサービスの**情報セキュリティ管理策**のガイドライン，ISO/IEC 27018はパブリッククラウドでの**個人情報（PII）保護**の実践の規範。

**答え**：d：ウ　e：ア

#### 設問3(2)　［読解］
> 本文：表2「ファイルを…保存するときの暗号化：…自動的に暗号化され，**暗号鍵はG社が管理**」「ファイルや管理情報が，日本国内と**F国**の両方のデータセンタに保存」
> 本文：Tさん「F国では…F国内に保存されているデータを，F国政府に**強制的に提出させる**国内法」

**考え方**：G社が鍵を持っていると，G社に提出命令が出れば復号して出されてしまう。U社だけが持つ鍵で暗号化してからアップロードすれば，提出されても中身は読まれない。

**答え**：ファイルをU社が管理する鍵で暗号化してからアップロードする。

#### 設問4(1)(2)　［読解］
> 本文：表4 項番1「**利用者IDを固定**して，パスワードを総当たりする」，項番2「一定時間当たりの**同一IPアドレスから**の異なる利用者IDによるログイン失敗の回数がしきい値を超えたら」
> 本文：表3の後「ログには…**実行した利用者ID，アクセス元IPアドレス**，及び結果（成功又は失敗）が記録される」

**考え方**：
- (1) 項番1は同じ利用者IDに対する攻撃なので，同じ利用者IDのログイン失敗を数える。
- (2) 項番2は送信元IPアドレスごとに数えるので，攻撃者が多数のIPアドレス（ボットなど）を使い分けると，一つ一つはしきい値を超えず見逃す。

**答え**：(1) f：同一利用者IDでのログイン失敗　(2) アクセス元IPアドレスを変えながら，不正アクセスを続けた場合

#### 設問5(1)　［読解］＋［知識］
> 本文：図10(5)「IDc，H（ドメイン），**オリジンb**，署名M」→「**オリジンbがKサービスのものであることの確認**」，「オリジンb：Webブラウザがアクセスしている**Webサイトのオリジン**」
> 本文：Tさん「攻撃者が，［ g ］するための特別なサーバをインターネット上に用意し，何らかの方法で被害者をそのサーバに誘導し，認証情報を不正に入手して悪用する」

**知識**：FIDOでは，ブラウザが**実際にアクセスしているサイトのオリジン**を署名の対象に入れる。偽サイトを経由して認証のやり取りを中継しても（中間者攻撃・リアルタイムフィッシング），オリジンが偽サイトのものになるので，Kサービスで検証に失敗する。

**答え**：g：メッセージをKサービスとの間で中継

#### 設問5(2)　［読解］
> 本文：表5 スマートフォン・OS内蔵「認証器使用時の利用者確認：…**生体認証**」，USB接続外部認証器「なし」
> 本文：表6 スマートフォン「所有者：**各協力会社又は利用者個人**」，USB「U社から必要個数を各協力会社に配布」

**考え方**：
- h：スマートフォンもOS内蔵も使うたびに生体認証が要るので，拾った人には使えない。
- i・j：個人のスマートフォンは会社が回収できない。退職者が使えないよう，認証サービス（Kサービス）側でその人のアカウントを削除する。
- k：USB認証器は利用者確認がないので，拾われたらそのまま使われる。すぐにアカウントを無効にする。

**答え**：h：生体認証　i：Kサービス　j：アカウントを削除　k：アカウントを無効に

#### 設問5(3)　［読解］
> 本文：「Dシステムには，**ファイル受渡し用PCからだけアクセス**することを求めている」（利用規約），表2「協力会社以外からのアクセス禁止：Gサービスで，送信元IPアドレスの制限を行うことができないので**否**」
> 本文：表5 OS内蔵の生体認証機能「組合せ：**限定される**」（KサービスにアクセスするPCと認証器の組合せ），表6「**ファイル受渡し用PCが認証器を兼ねる**」

**考え方**：OS内蔵の生体認証は，そのPC自体が認証器なので，登録したファイル受渡し用PCからしかログインできない。IPアドレス制限ができないGサービスでも，「ファイル受渡し用PCからだけ」という要件を技術的に守れる。

**答え**：Gサービスへのアクセスを，ファイル受渡し用PCからのアクセスだけに限定できるから

## 問2 マルウェア感染への対処（A社 / テレワーク・ローカルブレイクアウト・インシデント対応）

| 設問 | 解答 |
|---|---|
| 設問1(1) | a：ア　b：イ　c：イ　d：ウ |
| 設問1(2) | e：CRYPTREC |
| 設問2(1) | エ |
| 設問2(2) | Bサービスのアクセス制限機能によって通信が拒否されたから |
| 設問3(1) | マルウェア内にFQDNで指定したC&CサーバのIPアドレスの変更 |
| 設問3(2) | C&Cサーバとの通信時にDNSへの問合せを実行しない場合があるから |
| 設問3(3) | f：イベントログの消去を示すログ |
| 設問3(4) | 横展開機能と待機機能だけを実行していた場合 |
| 設問3(5) | UTMのIDS機能によって攻撃が検知でき，システム管理者に連絡がされるから |
| 設問4(1) | g：7月14日 |
| 設問4(2) | h：IPリストに登録されたIPアドレス |
| 設問4(3) | 連携端末以外のIPアドレスを送信元とする通信記録 |
| 設問4(4) | 連携端末を一時的にネットワークから切り離した対応 |

### 解説

#### 設問1(1)　［読解］
> 本文：図5「経営者：…テレワークセキュリティ全般を考え，**必要なリソースを確保**する」「システム管理者：…インシデント発生時の対処のルールを定める」「テレワーク勤務者：定められたルールを**遵守**し…」

**考え方**：
- a 予算を割り当てる → 経営者
- b 技術的対策を講じて点検する → システム管理者
- c システムに強度の低いパスワードを使えない制限を掛ける → システム管理者
- d 自分でパスワードを設定する → テレワーク勤務者

**答え**：a：ア　b：イ　c：イ　d：ウ

#### 設問1(2)　［知識］
> 本文：図5 5「電子政府における調達の際にも参照される［ e ］暗号リスト」

**知識**：総務省・経済産業省が作る，電子政府推奨暗号などのリストが **CRYPTREC** 暗号リスト。

**答え**：e：CRYPTREC

#### 設問2(1)　［知識］
> 本文：図6 下線①「Bサービスへのアクセスだけ，拠点VPNサーバから，**DCを経由させずに支社に敷設したインターネット接続回線**を経由させる」

**知識**：特定のクラウドサービスへの通信だけを，本社やデータセンタを経由せず，各拠点から直接インターネットへ出す構成を**ローカルブレイクアウト**という。

**答え**：エ

#### 設問2(2)　［読解］
> 本文：表1 Bサービス「アクセス制限機能によって，アクセス元IPアドレスが**UTMのグローバルIPアドレス**の場合だけアクセスが許可される」

**考え方**：支社の回線から出ると送信元は支社のIPアドレスになり，UTMのアドレスではないので，Bサービスに拒否された。設定変更とは，この制限を変えたこと（攻撃の一因にもなった）。

**答え**：Bサービスのアクセス制限機能によって通信が拒否されたから

#### 設問3(1)(2)　［読解］
> 本文：「C&Cサーバの**IPアドレス及びFQDN**のリストが埋め込まれていた」，Gさん「そのIPアドレス，及びそのFQDNのDNSの正引き結果のIPアドレス…を**手作業で作成**しておき，…UTMで拒否」
> 本文：表1 DNSシンクホール機能「DNSクエリをチェックし，危険リストに登録されているFQDNの場合は，正規の名前解決を行わずに…」

**考え方**：
- (1) 攻撃者はFQDNの指すIPアドレスをいつでも変えられる。手作業で作ったIPリストはすぐ古くなる。DNSシンクホールならFQDNで止められる。
- (2) 一方，マルウェアにはIPアドレスが直接書かれているものもあり，その場合はDNSを使わないのでシンクホールでは止められない。だからIPでの拒否も残す。

**答え**：(1) マルウェア内にFQDNで指定したC&CサーバのIPアドレスの変更　(2) C&Cサーバとの通信時にDNSへの問合せを実行しない場合があるから

#### 設問3(3)　［読解］
> 本文：図8「一部の業務PCでは，**全てのイベントログが消去**された痕跡があった。全てのイベントログが消去された後，イベントログに**イベントログの消去を示すログ**が記録されていた」

**考え方**：αログ・βログが消されていても，消去したこと自体の記録は残る。それも感染の疑いとして調べる。

**答え**：f：イベントログの消去を示すログ

#### 設問3(4)　［読解］
> 本文：表2 マルウェアβ「いずれかの機能を…ランダムに実行する」「(3)遠隔操作機能…このとき，イベントログに**βログが記録**される」（(1)待機，(2)横展開ではログが出ない）

**考え方**：遠隔操作機能をまだ実行していない感染PCは，βログが無いので確認ツールでは問題なしになる。それでも横展開機能でほかの機器に感染を広げる。

**答え**：横展開機能と待機機能だけを実行していた場合

#### 設問3(5)　［読解］
> 本文：表1 UTM「IDS機能：**全てのインバウンド通信をチェック**し，不審な通信を検知した場合は，システム管理者に通知する」
> 本文：図3 連携サーバは研究部が管理する**連携FW**経由でインターネットに直接つながっている（UTMを通らない）

**考え方**：DCのDMZに移せば，連携サーバへの通信もUTMのIDSで見張られ，攻撃があればシステム管理者にすぐ通知される。

**答え**：UTMのIDS機能によって攻撃が検知でき，システム管理者に連絡がされるから

#### 設問4(1)　［読解］
> 本文：図8「7月14日：…Fさん（**研究部**）の業務PCがマルウェアαに感染した。同日中に…マルウェアβにも感染した」
> 本文：図4「連携サーバの共有フォルダは**研究部セグメントの業務PCから**認証なしでアクセス可能」，表2 横展開機能「アクセス可能な共有フォルダを発見すると，**細工された文書ファイルを生成し，その共有フォルダに置く**」

**考え方**：Fさんの業務PCがマルウェアβに感染した7月14日から，連携サーバの共有フォルダに細工されたファイルが置かれた可能性がある。ログは7月19日分からしか残っていないが，それより前からが対象。

**答え**：g：7月14日

#### 設問4(2)(3)　［読解］
> 本文：表5 調査2「会員FWのログに，次に該当する送信元から宛先への通信記録…送信元：任意のIPアドレス　宛先：［ h ］」，Gさん「C&CサーバのIPアドレス…を併せたIPアドレスのリスト（**IPリスト**）」
> 本文：P氏「⑦**連携端末からほかのPCやサーバへの感染拡大**が明らかな会員に絞るのであれば，調査2に使う通信記録から絞る」

**考え方**：
- (2) 会員の中で感染した機器があれば，C&Cサーバに通信しようとする。IPリストのアドレスへの通信が会員FWに記録されていないかを見る。
- (3) その通信の送信元が連携端末以外なら，連携端末から会員内のほかの機器に広がっている。

**答え**：(2) h：IPリストに登録されたIPアドレス　(3) 連携端末以外のIPアドレスを送信元とする通信記録

#### 設問4(4)　［読解］
> 本文：「化学コンの全会員に**連携端末を一時的にネットワークから切り離して**もらうように連絡し，全ての会員で対応が完了したことを即日確認した」

**考え方**：連携端末だけが感染している会員は，連携端末が切り離されているので，そこから広がるおそれは小さい。

**答え**：連携端末を一時的にネットワークから切り離した対応
