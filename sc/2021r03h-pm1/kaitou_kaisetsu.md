## 問1 認証システムの開発（S社 / OAuthによるID連携）

| 設問 | 解答 |
|---|---|
| 設問1(1) | 多要素認証の実装をSサービス側に用意しなくてよい。 |
| 設問1(2) | Tサービスの障害時にSサービスを利用できない。 |
| 設問1(3) | a：ア　b：イ　c：ウ |
| 設問1(4) | α：（え） |
| 設問2(1) | d：ウ　e：ア |
| 設問2(2) | アップロード：攻撃者　ダウンロード：攻撃者 |
| 設問2(3) | β：（い）　γ：（か） |
| 設問3(1) | （エ） |
| 設問3(2) | S認証モジュールに利用者IDとパスワードを登録していないS会員 |
| 設問4 | Tサービスで認証されたS会員のT-IDが，Sサービス内に登録されていることを確認する。 |

### 解説

#### 設問1(1)(2)　［読解］
> 本文：「S認証モジュールの認証方式を，**多要素認証**にする方がよいとのアドバイスを受けたが，**その対処が課題**であった」「多要素認証などの機能をもつT社のTサービスとSサービスとをID連携する」

**考え方**：
- (1) 社員10名で多要素認証を自前で作るのが課題だった。Tサービスに認証を任せれば，Tサービスの多要素認証をそのまま使える。
- (2) 認証をTサービスに頼るので，Tサービスが止まるとSサービスにもログインできなくなる（採点講評：ID連携しない場合にも当てはまる欠点は不適）。

**答え**：(1) 多要素認証の実装をSサービス側に用意しなくてよい。　(2) Tサービスの障害時にSサービスを利用できない。

#### 設問1(3)(4)　［読解］＋［知識］
> 本文：図1「Sサービス：Tサービスでのアカウント名を**要求**する」「Tサービス：…図3に示す**権限を提供**する」，図2（え）「**認証，権限付与の確認**」（利用者↔Tサービス）
> 本文：「［ a ］は，［ b ］が提供するリソースにアクセスできる。それは［ c ］が，図3に示す権限を［ a ］に与えるからである」

**知識**：OAuthでは，**利用者**（リソースの持ち主）が，**クライアント**（Sサービス）に，**リソースサーバ**（Tサービス）の自分のデータへのアクセス権限を与える。どの権限を与えるかは，認可サーバの画面で利用者が確認・同意する。

**答え**：a：ア（Sサービス）　b：イ（Tサービス）　c：ウ（利用者）　α：（え）

#### 設問2(1)(2)　［読解］
> 本文：図4「攻撃者→Tサービス：認証，権限付与の確認」「Tサービス→攻撃者：認可コード」→「攻撃者→利用者：［ d ］」→（リダイレクト）「利用者→Sサービス：［ d ］」→「Sサービス→Tサービス：［ e ］」→「アクセストークン」
> 本文：図2 注記「Sサービスは…ログイン中のTサービスから取得したアカウント名（T-ID）をSサービス内に登録」

**考え方**：攻撃者は自分のTサービスアカウントで認可コードを取り，それを利用者のブラウザに送り込んでSサービスに渡させる。Sサービスは攻撃者の認可コードでアクセストークンを取るので，利用者のブラウザは攻撃者のアカウントでSサービスにログインした状態になる（CSRFの一種）。利用者が気付かずアップロードしたファイルは攻撃者のフォルダに入り，攻撃者が自分のアカウントでダウンロードできる（採点講評でも「利用者のアカウント」と答えた誤りが多かった）。

**答え**：d：ウ（認可コード）　e：ア（アクセストークンの要求）　アップロード：攻撃者　ダウンロード：攻撃者

#### 設問2(3)　［知識］
> 本文：「Sサービスはstateパラメタを［ β ］を送信する際に付与する。Sサービスは［ γ ］を受信する際に，そのセッションが…同一であるか否かを確認する」

**知識**：stateは，Sサービスが利用者を認可要求に向かわせる（い）のリダイレクトで付け，認可コードと一緒に戻ってくる（か）で照合する。自分が始めた認可の流れでなければ止められる。

**答え**：β：（い）　γ：（か）

#### 設問3(1)　［読解］
> 本文：図1「Sサービス：Tサービスでの**アカウント名**を要求する」，図2（け）「アカウント名の要求」，図3（エ）「利用者の**アカウント名**，電子メールアドレスなど登録情報を取得する権限」

**答え**：（エ）

#### 設問3(2)　［読解］
> 本文：「今回の改修でのID連携では，既存のS会員は対象とせず，**新規登録のS会員だけ**を対象とする」「**S認証モジュールを用いない**S会員の登録」，三つ目の問題「TサービスとのID連携を一時的に停止し，**S認証モジュールだけで認証**」

**考え方**：Tサービス経由で新規登録した会員は，S認証モジュールにIDとパスワードを持っていない。ID連携を止めるとログインする手段がなくなる。

**答え**：S認証モジュールに利用者IDとパスワードを登録していないS会員

#### 設問4　［読解］
> 本文：図2 注記「初回に…**T-ID**を**Sサービス内に登録**する。…2回目以降のSサービスの利用の場合，初回に登録された**T-IDを確認**する」，図1 注記「Tサービスのアカウント名は**変更できない**」

**考え方**：利用者の本人確認はTサービスが行う。Sサービスは，Tサービスから受け取ったアカウント名（T-ID）が自分の会員として登録されているかを見て，誰が来たかを判断している。

**答え**：Tサービスで認証されたS会員のT-IDが，Sサービス内に登録されていることを確認する。

## 問2 ネットワークのセキュリティ対策（A社 / DNS）

| 設問 | 解答 |
|---|---|
| 設問1(1) | A社公開Webサーバの名前解決ができなくなる。 |
| 設問1(2) | DNSリフレクション攻撃 |
| 設問1(3) | a：ア　b：イ |
| 設問1(4) | c：A |
| 設問1(5) | d：ランダム化 |
| 設問1(6) | e：DNSSEC |
| 設問1(7) | f：オ　g：カ（順不同） |
| 設問2(1) | 権威DNSサーバがサービス停止になるリスク |
| 設問2(2) | h：カ　i：ク |
| 設問2(3) | j：拒否　k：許可　l：拒否　m：拒否 |
| 設問2(4) | n：オ　o：ア　p：カ（n・p順不同） |

### 解説

#### 設問1(1)　［読解］
> 本文：表1 外部DNSサーバ「**A社ドメインの権威DNSサーバ**及び…フルサービスリゾルバ」

**考え方**：外部DNSサーバが止まると，インターネットの利用者は www.a-sha.co.jp のIPアドレスを調べられず，公開Webサーバにたどり着けない。

**答え**：A社公開Webサーバの名前解決ができなくなる。

#### 設問1(2)(3)　［読解］＋［知識］
> 本文：下線②「**送信元のIPアドレスを偽装**した名前解決要求を外部DNSサーバに送ることによって，外部DNSサーバを踏み台とし，攻撃対象となる第三者のサーバに対し大量のDNSパケットを送り付ける」
> 本文：表2 項番6「インターネット→外部DNSサーバ　DNS　許可」（外から再帰問合せも受ける）

**知識**：**DNSリフレクション攻撃**（DNSアンプ攻撃）は，送信元を被害者に偽った問合せをオープンリゾルバに送り，大きな応答を被害者に浴びせる攻撃。

**考え方**：分けたあとは，インターネットへ問い合わせに出るのはフルサービスリゾルバのDNS-F（a），インターネットから問合せを受けるのは権威DNSのDNS-K（b）だけにする。DNS-Fは外から問合せを受けないので踏み台にならない。

**答え**：(2) DNSリフレクション攻撃　(3) a：ア（DNS-F）　b：イ（DNS-K）

#### 設問1(4)　［知識］
> 本文：「メールサーバの［ c ］レコードの**IPアドレス**が…書き換えられてしまい」

**知識**：メールの配送先は，まずMXレコードでメールサーバのホスト名を調べ，そのホスト名の**Aレコード**でIPアドレスを得る。IPアドレスを持つのはAレコード（採点講評：正答率が低い）。

**答え**：c：A

#### 設問1(5)(6)　［知識］
> 本文：「送信元ポート番号を［ d ］する対策」，「［ e ］という技術…リソースレコードに付与された**ディジタル署名**を利用して…送信者の正当性とデータの完全性を検証」

**知識**：
- キャッシュポイズニングでは，偽の応答が問合せのIDとポート番号に一致しないと受け入れられない。**送信元ポートをランダム化**すると，当てるのが非常に難しくなる。
- 応答に署名を付けて検証するのが **DNSSEC**。

**答え**：d：ランダム化　e：DNSSEC

#### 設問1(7)　［知識］
> 本文：「DoTは，［ f ］と［ g ］間の通信を暗号化するために開発された」

**知識**：DoT（RFC 7858）は，PCなどの**スタブリゾルバ**と**フルサービスリゾルバ**の間の通信を暗号化する（採点講評：正答率が低い）。

**答え**：f：オ　g：カ（順不同）

#### 設問2(1)　［読解］
> 本文：下線③「プライマリの権威DNSサーバの機能をDNS-Kに，**セカンダリ**の権威DNSサーバの機能を**DNS-S**（X社のホスティングサービス上）に移行」

**考え方**：権威DNSが社内の1台だけだと，その回線やサーバが止まればA社ドメインの名前解決ができない。別の場所にセカンダリを置けば，片方が止まっても答えられる。

**答え**：権威DNSサーバがサービス停止になるリスク

#### 設問2(2)　［読解］
> 本文：「X社のホスティングサービスに用いるドメイン名は**x-sha.co.jp**，DNS-Sのホスト名は**dns-s**」，図2「mail IN A x1.y1.z1.t3」（a-sha.co.jp のゾーン），「メールサーバのホスト名はmail」

**考え方**：NSにはDNS-SのFQDN（dns-s.x-sha.co.jp.）。MXにはA社のメールサーバのFQDN（mail.a-sha.co.jp.）。末尾の「.」がない名前はゾーン名が補われるので，完全な名前に「.」を付ける。

**答え**：h：カ　i：ク

#### 設問2(3)　［知識］
> 本文：「ゾーン転送では，ゾーン情報が流出するリスクがある」「ゾーン転送要求に対する許可を必要最小限にする」

**知識**：ゾーン転送は，セカンダリがプライマリからゾーン情報をコピーする仕組み。要求してよいのはセカンダリ（DNS-S）からプライマリ（DNS-K）へだけ。DNS-SはDNS-Kから受け取るだけなので，誰からの転送要求にも応じる必要はない（採点講評：全問正解が少なかった）。

**答え**：j：拒否　k：許可　l：拒否　m：拒否

#### 設問2(4)　［読解］
> 本文：表1 注2「フルサービスリゾルバとしては，**プロキシサーバとメールサーバ**が使用している」，二つ目の案「フルサービスリゾルバの機能を**DNS-HF**（X社のホスティング）に移行」

**考え方**：社内からDNSで外に出るのは，DNS-HFに問い合わせるプロキシサーバとメールサーバだけ。権威DNSも社外に移るので，インターネットから社内へのDNSは不要。

**答え**：n：オ（プロキシサーバ）　o：ア（DNS-HF）　p：カ（メールサーバ）

## 問3 セキュリティ運用（G社 / パッチ配信・WoL・EDR）

| 設問 | 解答 |
|---|---|
| 設問1 | a：PCの動作に問題がないこと |
| 設問2 | L2SW1 |
| 設問3(1) | b：エ |
| 設問3(2) | c：イ |
| 設問3(3) | 起動パケットを他のセグメントに転送するように変更する。 |
| 設問4(1) | (2)の活動：IPアドレス　(4)の活動：MACアドレス |
| 設問4(2) | エージェントによって，夜間にarpコマンドの実行を検知したら，当該PCをネットワークから隔離する。 |

### 解説

#### 設問1　［読解］
> 本文：図2(2)「セキュリティパッチを**検証LAN**のPCに適用し，社内で利用しているアプリケーションプログラムを2日間動作させて［ a ］を確認する」

**考え方**：全社に配る前に，パッチで業務アプリや PC が不具合を起こさないか（副作用がないか）を確かめる。

**答え**：a：PCの動作に問題がないこと

#### 設問2　［読解］
> 本文：表1 FW「インターネットとの間の通信を許可しているのは**DMZだけ**」，図1 DMZのL2SW1配下に**プロキシサーバ**，外部メールサーバ

**考え方**：どのLANのPCも，外に出るにはDMZのプロキシサーバや外部メールサーバを経由する。DMZのサーバ自身の通信も含めて，全てがL2SW1を通る。

**答え**：L2SW1

#### 設問3(1)(2)　［知識］
> 本文：「［ b ］に続けて，起動したいPCの［ c ］を16回繰り返したデータを含む起動パケット」

**知識**：WoLのマジックパケットは，**FF:FF:FF:FF:FF:FF**（6バイト）の後に，起動したいPCの**MACアドレス**を16回並べたもの。電源の切れたPCはIPアドレスを持たないので，MACアドレスで指定する。

**答え**：b：エ　c：イ

#### 設問3(3)　［知識］
> 本文：「検証LAN内のPC-XからPC-Yは起動した」「資産管理サーバ（内部システムLAN）からPC-Yの起動を試みたが，起動しなかった」「②L3SWの設定を変更する」

**知識**：マジックパケットは通常ブロードキャストで送られ，ルータ（L3SW）を越えない。L3SWで，起動パケット（ディレクテッドブロードキャストなど）を別のセグメントへ転送するよう設定する必要がある（採点講評：正答率が低い）。

**答え**：起動パケットを他のセグメントに転送するように変更する。

#### 設問4(1)　［読解］
> 本文：図5(2)「ARPテーブル中のPC全てに**pingコマンド**を送信し」，(4)「起動していないPCを発見したら，**WoL**を使ってそれらのPCを起動」

**考え方**：ARPテーブルにはIPアドレスとMACアドレスの対応がある。pingにはIPアドレス，WoLには（設問3で見たとおり）MACアドレスが要る。

**答え**：(2)の活動：IPアドレス　(4)の活動：MACアドレス

#### 設問4(2)　［読解］
> 本文：表1 エージェント「PC上で起動する全てのプロセスを監視する。**指定した時間帯に指定したコマンドが実行された**場合，EDR管理サーバとの間の通信を除き，当該PCの**全ての通信を遮断**する機能」
> 本文：図5(1)「自身が動作するPCの**ARPテーブル**から…読み取って」

**考え方**：導入済のEDRのエージェントには，時間帯とコマンドを指定して隔離する機能がある。夜間に普通は誰も使わない arp コマンド（ARPテーブルの読取り）が動いたら，そのPCを隔離すればよい（採点講評：EDRの具体的な使い方まで書く必要がある）。

**答え**：エージェントによって，夜間にarpコマンドの実行を検知したら，当該PCをネットワークから隔離する。
