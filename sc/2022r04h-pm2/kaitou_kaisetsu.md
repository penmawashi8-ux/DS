### 解説

#### 設問1(1)　［読解］
> 本文：図1「out.println("<meta property=\"og:url\" content=\"https://"+serverName+"/"+scriptName+"?"+**queryString**+"\">");」，注記「queryStringには，URLの**クエリ文字列**以降の値が**URLデコード**されて格納」

**考え方**：出力されるのはURLのクエリ文字列なので，診断用の文字列はGETのクエリに入れる（ボディのウ・エは関係ない）。content="…" の属性値の中に出力されるので，まず `"` で属性値を閉じ，`>` でタグを閉じてから `<img … onerror=…>` を入れる。`"` がないイでは属性の外に出られない。

**答え**：ア

#### 設問1(2)　［読解］
> 本文：「開発部のメンバ**それぞれ**が，開発時に利用可能なライブラリを収集」「安全性が確認できているライブラリを公開しているWebサイトから…ダウンロード」，「今回使われていたライブラリMは，**既知のXSS脆弱性の対策をしていないバージョン**」

**考え方**：各自がばらばらに集めているので，古いバージョンが紛れ込んだ。ダウンロード時に既知の脆弱性がないか確認する，又は入手先を決めてルールにする。

**答え**：ダウンロードするライブラリに既知の脆弱性がないかを確認する。（又は，特定のWebサイトからの入手をルール化し，明文化する。）

#### 設問2　［読解］＋［知識］
> 本文：(2)「利用者Bの利用者IDでサイトXにログインし…csrftokenの値に，**図2（利用者A）のcsrftoken**の値を設定して送信したところ，**利用者Bとして処理**された」

**知識**：CSRFトークンは，サーバ側で**セッション（利用者）にひも付けて**保存し，送られてきたトークンがそのセッションのものか確かめる必要がある。

**考え方**：他人（利用者A）のトークンでも通るのは，トークンが利用者IDやセッションと結び付いていないから。

**答え**：a：利用者ID　b：セッションオブジェクト

#### 設問3(1)　［知識］
> 本文：「クリックイベントは，利用者から見て**手前にある画面上**で発生する」，図3 画面α（サイトXの公開範囲設定），画面β（罠の「ここをクリック」）

**知識**：クリックジャッキングは，罠ページの上に正規サイトのページを**透明**にして重ね，利用者に罠の部分をクリックしたつもりで正規サイトのボタンを押させる攻撃。

**考え方**：利用者に見せるのは画面β（可視，奥），実際にクリックさせたいのはサイトXの画面α（透明，手前）。

**答え**：c：イ（β）　d：ア（奥）　e：ア（可視の）　f：ア（α）　g：イ（手前）　h：イ（透明な）

#### 設問3(2)　［知識］
> 本文：「クリックジャッキング脆弱性の対策には，レスポンスヘッダに［ i ］を含める方法と［ j ］を含める方法がある。**後者は標準化**されている」

**知識**：自分のページを他サイトのフレームに表示させない指定。
- **X-Frame-Options**（DENY / SAMEORIGIN）：広く使われるが，標準仕様としては後発のものに置き換えられた
- **Content-Security-Policy** の frame-ancestors：W3Cで標準化されている

**答え**：i：エ　j：イ

#### 設問4　［読解］
> 本文：図4「GET /news?**topic=https://www.a-sha.co.jp/news/20220417.html**」（topicのURLをサーバが取得する）
> 本文：表2 注1「DBサーバには，B社のシステム担当者と，それぞれのサイトの**Webサーバとがアクセスできる**」「サイトYのDBサーバ：**https://db-y.b-sha.co.jp/**」

**考え方**：サイトYのWebサーバはtopicに書かれたURLを取りに行く。これをDBサーバのメンテナンス画面のURLにすれば，外からは届かない画面にWebサーバ経由でアクセスできる（SSRF）。

**答え**：topicの値をhttps://db-y.b-sha.co.jp/に変更した。

#### 設問5(1)　［読解］
> 本文：図5 注2「サイトZは，(1)の**Hostヘッダの値**を，returnURL中のホスト名として指定する」，図6(3)「301 MOVED PERMANENTLY」→(4)サイトZがそのURLへアクセス
> 本文：表4 1「Hostヘッダの値を，**V氏が用意したサイトのFQDN**に変更して，サイトZにリクエストを送る」

**考え方**：Hostを書き換えると，returnURLが V氏のサイト/error になる。P社宿泊サイトは登録されていない駅名なのでそのURLへリダイレクトし，サイトZは（Authorizationヘッダを付けたまま）V氏のサイトにアクセスしてしまう。

**答え**：k：V氏が用意したサイト

#### 設問5(2)　［読解］
> 本文：図5 注2「サイトZは，(1)のHostヘッダの値を，returnURL中のホスト名として指定する」，D社の提案「レスポンスに含まれるURLが想定されたものかを調べて…アクセスしないようにする」，下線④「別の対策」

**考え方**：問題の根本は，利用者が送ってきたHostヘッダからreturnURLを作っていること。returnURLは常に自分のエラーページなので，固定値にすれば，Hostを書き換えられても影響しない（採点講評でも正答率が低かった）。

**答え**：returnURLの値を固定値にする。

#### 設問6(1)　［読解］
> 本文：表1 項番2〜4（ソースコードレビュー，ツールによる脆弱性診断）「セッション管理の脆弱性は，**一部だけ**が対象」「認可・アクセス制御の脆弱性は，**対象外**」，項番5（専門技術者）「セッション管理の脆弱性は，対象」「認可・アクセス制御の脆弱性は，対象」

**答え**：①一部のセッション管理の脆弱性　②認可・アクセス制御の脆弱性

#### 設問6(2)　［読解］
> 本文：図7 注記2「改良フェーズにおいて，半年に1回，**1か月の休止期間**を設けている。その間，開発部のメンバは…**Webサイトの点検**などを実施」
> 本文：表1 項番5「期間は，10日間くらいが目安」，設問「改良リリースの実施に**影響を与えない**ことを前提に」

**考え方**：休止期間なら改良リリースを止めずに10日間の診断ができる。半年ごとに必ず来るので，長期間診断しないことも避けられる。

**答え**：改良フェーズにおける1か月の休止期間

#### 設問6(3)　［読解］
> 本文：図7 注記1「2週間周期での改良リリース…およそ20回に1回は大規模な改修があり，**改良リリース間隔を1か月**とすることがある」
> 本文：E課長「改良リリースの周期は2週間程度です。専門技術者による脆弱性診断には，その周期の**大半を費やしてしまう**」

**考え方**：診断が入る余裕がない周期を見直す。診断が必要なときはその回のリリースを次に持ち越す，あるいは定期的に期間の長い改良リリースを作って，そこで診断する。

**答え**：専門技術者による脆弱性診断が必要なときは，改良リリースを次回に持ち越す。（又は，半年に一度，改良リリースの期間を長くする。）

#### 設問6(4)　［知識］
> 本文：下線⑧「（フレームワークには）脆弱性対策が組み込まれていて，それがデフォルトで有効になっているものもある」，設問「CSRF脆弱性の場合」

**知識**：多くのWebフレームワークは，CSRF対策として，**トークンを発行し，フォームのHTMLに自動で埋め込み，セッションにひも付けて，送信時に検証する**処理を標準で備えている（採点講評でも正答率が低かった）。設問2で見た「ひも付け」の漏れも防げる。

**答え**：CSRF対策用トークンの発行，HTMLへの埋め込み，必要なひも付け，及びこれを検証する処理

## 問2 クラウドサービスへの移行（X社 / CDN・Kerberos・SAML・OAuth・OIDC）

| 設問 | 解答 |
|---|---|
| 設問1(1) | a：キャッシュ |
| 設問1(2) | b：DDoS |
| 設問1(3) | c：Host |
| 設問1(4) | Y-CDN-U-FQDNを名前解決したIPアドレスと同じIPアドレスをもつWebサイト |
| 設問1(5) | d：TLSの接続先サーバ名 |
| 設問2(1) | STは認証サーバに送られないから |
| 設問2(2) | 総当たり攻撃はオフラインで行われ，ログインに失敗しないから |
| 設問3(1) | e：ウ |
| 設問3(2) | f：ア |
| 設問3(3) | g：偽造 |
| 設問3(4) | h：1　i：3　j：4（i・j順不同） |
| 設問4(1) | k：ウ　l：イ　m：ア |
| 設問4(2) | n：エ |
| 設問4(3) | o：(2)　p：(6) |
| 設問4(4) | q：ウ |
| 設問5(1) | r：オ　s：エ　t：ウ |
| 設問5(2) | u：(8) |
| 設問5(3) | v：イ |
| 設問5(4) | w：認証要求　x：IDトークン |

### 解説

#### 設問1(1)(2)　［知識］
> 本文：F氏「インターネット上に［ a ］サーバというサーバを分散配置して…要求された動画を保持していれば**代理応答**し…」，Cさん「その仕組みによって，［ b ］攻撃への耐性も向上しますね」

**知識**：CDNは，元のサーバ（オリジン）の内容を複製して持つ**キャッシュサーバ**（エッジサーバ）を各地に置く。大量のアクセスは分散したキャッシュサーバが受けるので，**DDoS**攻撃にも強くなる。

**答え**：a：キャッシュ　b：DDoS

#### 設問1(3)　［知識］
> 本文：図4(4)「TLSの接続先サーバ名にはRFC 6066に基づいて，HTTPリクエストの［ c ］ヘッダにはRFC 7230に基づいて，X-FQDNが指定される」

**知識**：RFC 6066はTLSのSNI（接続先サーバ名），RFC 7230はHTTP/1.1。HTTPで接続先ホスト名を示すのは**Hostヘッダ**。CDNは同じIPアドレスで多数のサイトを扱うので，Hostヘッダでどのサイトか見分ける。

**答え**：c：Host

#### 設問1(4)　［読解］
> 本文：図5(1)「CDN-Uが，X社内から頻繁にアクセスする**他社のWebサイトの複数**で利用されている」，下線①「Y-CDN-U-FQDNを名前解決したIPアドレスを宛先とする通信をFWで拒否すると，**複数のWebサイトが閲覧できなくなる**」

**考え方**：CDNのキャッシュサーバは，同じIPアドレスで多くの利用企業のサイトを配信している。そのIPアドレスを止めると，Y社だけでなく，同じIPアドレスで配信されている全てのサイトが見られなくなる。

**答え**：Y-CDN-U-FQDNを名前解決したIPアドレスと同じIPアドレスをもつWebサイト

#### 設問1(5)　［読解］
> 本文：図5(3)「Y-CDN-U-FQDNを名前解決したIPアドレスのサーバと…**TLS接続を確立**」，(4)「HTTPリクエストを送信する際，［ c ］ヘッダに**Z-FQDN**を指定」

**考え方**：ドメインフロンティングは，TLSのSNIでは正当なY社のFQDNを名乗り，暗号化されたHTTPの中のHostで攻撃者のサーバを指す。通信を復号して，**TLSの接続先サーバ名**とHostヘッダが一致するか確かめれば見破れる（採点講評でもDNSと混同した誤りが多かった）。

**答え**：d：TLSの接続先サーバ名

#### 設問2(1)　［読解］
> 本文：図7「XPC→GrWサーバ：**ST**」→処理3（GrWサーバがSTを復号して検証），注2「STは…アクセス対象のサーバの**サーバ管理者アカウントのパスワードハッシュ値**を鍵として暗号化」

**考え方**：TGTは処理2で認証サーバに戻ってくるので，認証サーバで偽物かどうかを確かめられる。STはXPCからGrWサーバに直接渡され，認証サーバを通らないので，認証サーバは偽造に気付けない。

**答え**：STは認証サーバに送られないから

#### 設問2(2)　［読解］
> 本文：F氏「奪取されたSTに対してサーバ管理者アカウントのパスワードの**総当たり攻撃**が行われ」，注2「STは…サーバ管理者アカウントのパスワードハッシュ値を**鍵として暗号化**」

**考え方**：STはパスワードから作った鍵で暗号化されているので，攻撃者は手元でパスワード候補を試し，STが正しく復号できるかを確かめればよい。サーバにログインを試みないので，連続失敗によるロックは発動しない（いわゆるKerberoasting）。

**答え**：総当たり攻撃はオフラインで行われ，ログインに失敗しないから

#### 設問3(1)　［読解］
> 本文：表2 処理1「SAML Requestを生成し，エンコードする」「エンコード結果とIDaaSのログイン画面の**URLを組み合わせて**，リダイレクト先URLを生成」，図8(2)「SAML Requestを含む**リダイレクト**」→(3)

**考え方**：SAML RequestはリダイレクトのURLに付けられるので，(3)のHTTPリクエストでは**クエリ文字列**に入っている。

**答え**：e：ウ

#### 設問3(2)(3)　［知識］
> 本文：表2 処理3「SAMLアサーションと，それに対する**デジタル署名**を含めたSAML Response」（IDaaSが作る），処理4「デジタル署名が［ f ］のものであること，及びSAMLアサーションの［ g ］がないことを確認」

**知識**：デジタル署名を検証すると，**誰が署名したか**（発行元の真正性）と，**改ざん・偽造されていないか**（完全性）が分かる。

**考え方**：署名したのはIDaaS。SAMLアサーションが偽物でないことを確かめる。

**答え**：f：ア（IDaaS）　g：偽造

#### 設問3(4)　［読解］
> 本文：F氏「事前に共有する情報は，SAMLアサーションで用いる属性，図8中の処理［ h ］で用いる**URL**，図8中の処理［ i ］及び処理［ j ］において必要な**デジタル証明書**など」
> 本文：表2 処理1「IDaaSの**ログイン画面のURL**を組み合わせて，リダイレクト先URLを生成」，処理3「…**デジタル署名**を含めた…」，処理4「**デジタル署名を検証**」

**考え方**：SaaSは処理1でIDaaSのURLを知っている必要がある。署名を作る処理3と検証する処理4には，IDaaSの秘密鍵と，それに対応する証明書をSaaSが持っていることが必要。

**答え**：h：1　i：3　j：4

#### 設問4(1)(2)　［読解］＋［知識］
> 本文：表3 利用手順(2)「**Sサービス**は，**GrW-G**から主催者のスケジュールを取得」，「Sサービス，GrW-G及びIDaaS-Gは，OAuth 2.0をサポート」
> 本文：図9(3)「認可要求」(7)「トークン要求」（l），(9)「利用者情報の問合せ」（m）

**知識**：OAuth 2.0では，利用者の代わりにAPIを使う**クライアント**がアクセストークンを得て，**リソースサーバ**のAPIを呼ぶ。トークンを出すのは**認可サーバ**。

**考え方**：k はクライアントのSサービス，l は認可サーバのIDaaS-G，m は利用者情報やスケジュールを持つGrW-G。スケジュールを取るのはSサービス（k）がGrW-G（m）に対して（エ）。利用者の端末はトークンを持たない。

**答え**：k：ウ　l：イ　m：ア　n：エ

#### 設問4(3)　［知識］
> 本文：F氏「stateパラメタを付与して送信し…送られてきたものと比較する」

**知識**：stateは，クライアントが認可要求の最初に作ってリダイレクトに付け，認可コードと一緒に戻ってきた値と比べる。自分が始めた認可の応答かどうかを確かめ，攻撃者の認可コードを押し付けられるCSRFを防ぐ。

**考え方**：Sサービスがstateを付けて送るのは，端末をIDaaS-Gへ向かわせる(2)のリダイレクト。戻ってくるのは認可コードと一緒の(6)（採点講評でも正答率が低かった）。

**答え**：o：(2)　p：(6)

#### 設問4(4)　［知識］
> 本文：F氏「ランダムな検証コードとその値を基にしたチャレンジコードを作成して，そのチャレンジコードを認可要求に追加し，検証コードをトークン要求に追加」

**知識**：この仕組みが**PKCE**（Proof Key for Code Exchange，RFC 7636）。横取りした認可コードだけではトークンを取れない。

**答え**：q：ウ

#### 設問5(1)(2)　［読解］＋［知識］
> 本文：「T社投稿サイトの**認証サーバを用いた認証機能**，及びT社投稿サイトの**投稿サーバへの自動投稿機能**を**X社動画サーバ**に追加」
> 本文：図10(3)「認証要求」(7)「トークン要求」（s），「APIを使った“動画の概要”の投稿」（r→t）

**知識**：OIDCの認可コードフローでは，IDトークンはアクセストークンと一緒に**トークン応答**で返される。

**答え**：r：オ（X社動画サーバ）　s：エ（T社投稿サイトの認証サーバ）　t：ウ（T社投稿サイトの投稿サーバ）　u：(8)

#### 設問5(3)　［知識］
> 本文：「IDトークンは，**JSON Web Token**形式で表現され，ヘッダ，ペイロード，署名の三つの部分」

**知識**：JWTの各部分は，URLに載せても問題ない **base64url** でエンコードし，「.」でつなぐ。

**答え**：v：イ

#### 設問5(4)　［知識］
> 本文：F氏「まず，nonce値を生成し，［ w ］に含めて送信します。次に，送られてきた［ x ］に含まれるnonce値を検証することで，攻撃者による**IDトークンの不正利用**を防ぐ」

**知識**：OIDCのnonceは，クライアントが**認証要求**に入れて送り，認証サーバがそれを**IDトークン**の中に入れて返す。返ってきたIDトークンのnonceが自分の送った値と同じなら，このログインのために発行されたIDトークンだと分かり，盗んだIDトークンの使い回し（リプレイ）を防げる（採点講評でも正答率が低かった）。

**答え**：w：認証要求　x：IDトークン
