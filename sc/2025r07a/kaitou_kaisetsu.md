## 問1 コンサルティング業務で利用するSaaS（H社 Sサービス / 格納型XSS＋CSRFトークン窃取）

| 設問 | 解答 |
|---|---|
| 設問1 a | できない |
| 設問1 b | できない |
| 設問2(1) | ロール管理 |
| 設問2(2) c | タスク名 |
| 設問2(3) d | `個人タスク<script src="/files/F1234567890.xlsx"></script>` |
| 設問2(4) e | B社の管理者 |
| 設問2(4) f | 締切日を過ぎている |
| 設問2(4) g | ロールを管理者に変更する（is_admin=1を設定する） |
| 設問2(5) | スクリプトをscriptタグ内に直接書く代わりに，スクリプトを記述したファイルをSサービスにアップロードし，そのファイルをscriptタグのsrc属性で読み込むようにした。 |
| 設問3(1) h | ファイルの内容が拡張子に対応したファイル形式であることを検査する処理 |
| 設問3(2) i | プロジェクト進捗管理 |
| 設問3(3) | タスク名を画面に出力する際に，HTMLの特殊文字をエスケープする処理 |
| 設問4 j | 診断員による手動の脆弱性診断（ペネトレーションテスト） |

### 解説
- **設問1**：図1のCSPは `default-src 'self'` だけ。全リソース種別が自オリジンに限定されるので他ドメインからの読込みは**できない**。また `'unsafe-inline'` を指定していないので、インラインスクリプト（scriptタグ内に直接書いたもの）も**実行できない**。
- **設問2(1)**：図3のスクリプトは `/management/role` をGETしてcsrf_tokenを抜き出し、`/management/roleset` に `is_admin=1, user_id=U00331001` をPOSTしている。表1の**ロール管理**機能の処理の流れそのもの。管理者のブラウザ上で動かすことで、CSRFトークン対策を回避している。
- **設問2(2)(3)**：図2の期限切れタスク一覧には「タスク名」と経過日数が出る（表1 プロジェクト進捗管理の備考）。scriptタグは「個人タスク」の直後、「（締切日過ぎ 5日）」の前に入っているので、タスク名として `個人タスク<script src="/files/F1234567890.xlsx"></script>` が登録されたと分かる。
- **設問2(4)**：e は「プロジェクト進捗管理画面にアクセスし、そのブラウザでスクリプトが動いた結果ロールが変更できた」人物＝ロール管理権限をもつ**B社の管理者**（Uさんが確認したのもB社管理者のIDでの画面）。f は表示条件「未完了のタスクのうち締切日を過ぎたもの」から**締切日を過ぎている**。g はスクリプトの効果＝U00331001を**管理者ロールに変更**。その結果、項番8で元従業員Zは割り当てられていないプロジェクトのファイルもダウンロードできた。
- **設問2(5)**：完了済みタスクの類似攻撃は「CSPで防御できていた」。`default-src 'self'` でインラインスクリプトは止まるが、**自オリジンから読み込む外部スクリプトは許可される**。そこで攻撃者は、スレッド投稿機能でスクリプト本体を（拡張子xlsxで）Sサービス上にアップロードし、`<script src="/files/...">` で同一オリジンのファイルとして読み込ませた。
- **設問3(1)**：拡張子チェックだけでは、中身がJavaScriptのファイルを .xlsx としてアップロードできてしまう。**ファイルの中身（マジックナンバー等）が拡張子どおりの形式か**を検査し、不一致なら拒否する。
- **設問3(2)(3)**：項番4の問題は、タスク名をエスケープせずにHTMLへ出力したこと（格納型XSS）。出力箇所は**プロジェクト進捗管理**画面。入力した画面（タスク管理）ではなく、別画面に、しかも締切日経過後という条件付きで出力されるため、リクエストとレスポンスの組で判定する診断ツールXでは検知されない。対策は出力時の**HTMLエスケープ**。
- **設問4**：ツールで検知できない「別画面・時間差で現れる格納型XSS」を見つけるには、SAST（静的解析）に加え、画面遷移や業務の流れを理解した**人手による脆弱性診断**（手動診断／ペネトレーションテスト）が有効と考えた。

## 問2 暗号資産交換業におけるセキュリティ（A社 Bコイン / 署名鍵の保護と移送）

| 設問 | 解答 |
|---|---|
| 設問1 | ウ，エ |
| 設問2 | 鍵管理PCが署名処理中に発する電磁波を施設Kの外部で測定・解析して，署名鍵Sを推定する。 |
| 設問3(1) | (i)と(ii)の間：業務用メディアに攻撃者への移転情報を記録したファイルを追加する。(vi)と(vii)の間：署名済みの不正な移転情報を攻撃者に送信し，業務用メディアからそのファイルを削除する。 |
| 設問3(2) a | メッセージ認証コード（MAC） |
| 設問3(3) | 出庫業務を2名で行い，施設K内での作業を相互に監視させる。 |
| 設問4(1) | 作業2において，パスワードで暗号化した署名鍵Sと紙に書き留めたパスワードを一緒に移送している点 |
| 設問4(2) b / c / あ | b：ウ（署名鍵S）　c：ア（暗号鍵E）　あ：オ（暗号化） |
| 設問4(2) d / い / e | d：エ（復号鍵D）　い：ク（復号）　e：ウ（署名鍵S） |
| 設問4(3) | 移送用メディア上の署名鍵Sは暗号鍵Eで暗号化されており，復号に必要な復号鍵DはHSM内にしか存在しないから。 |
| 設問4(4) | 攻撃者が生成した鍵ペアの暗号鍵（攻撃者が対応する復号鍵をもつ公開鍵） |

### 解説
- **設問1**：楕円曲線を使う署名は **ECDSA** と **EdDSA**。ECDHは鍵共有、AESは共通鍵暗号、RSAは楕円曲線ではない、SHA-256はハッシュ関数。
- **設問2**：施設Kはネットワークから遮断されているが、物理的な漏えい経路は残る。電磁波（TEMPEST）・消費電力・音などから署名処理中の秘密鍵を推定するのがサイドチャネル攻撃。施設に入れない攻撃者が現実的に狙えるのは**外部からの電磁波測定**なので、それを答えた。
- **設問3(1)**：手順3は「移転情報が手順1と一致するか」「署名が検証鍵Vで正しいか」を検査するだけ。そこで、(i)の後にメディアへ**不正な移転情報ファイルを追加**し、当日担当者は内容を確認しないまま全ファイルに署名する。(vi)の後、署名済みの不正ファイルを**攻撃者へ送信して削除**すれば、アップロードされるのは正規ファイルだけになり手順3の検査は通る。攻撃者は受け取った署名済み移転情報を任意のBコインノードに送れば移転が成立する。図5の改修案に「ファイル数と出庫件数の一致確認」「重複がないこと」が入っているのも、この“追加”型の攻撃を想定しているためと読める。
- **設問3(2)**：メッセージダイジェストは鍵がないので誰でも再計算できる。共通鍵を基幹サーバと署名アプリだけがもつ**MAC（HMAC）**にすれば、マルウェアは正しいMACを作れない。
- **設問3(3)**：想定事例(b)は当日担当者一人が施設K内で署名鍵Sをコピーする。**2名体制で作業し相互に監視**させれば、一人で不正を働く機会が減る。
- **設問4(1)**：下線④は図6（パスワードによる暗号化）の時点の問題点。図6では暗号化した署名鍵Sと**パスワードを書いた紙を同じ人たちが一緒に持ち運ぶ**ので，両方を盗まれれば注1の「十分な強度のパスワード」も意味がなくなる。図7で公開鍵暗号に切り替え，パスワードの持運びそのものをなくした（下線⑤「盗難に遭っても漏えいしない」）ことが裏付け。HSM管理サーバのマルウェア感染のリスクは，本文で図7の案を作った**後に**「詳細に検討したところ」気付いたもので，④の答えではない。
- **設問4(2)**：作業3で施設K内の鍵管理PCが**署名鍵Sを暗号鍵Eで暗号化**し、作業6でHSM内で**復号鍵Dで復号**して得た**署名鍵S**をHSMに登録する。署名鍵Sが平文で外に出るのは鍵管理PC内だけになる。
- **設問4(3)**：暗号文だけ盗まれても、復号鍵DはHSMの中で生成されそこから出ないので復号できない。3,072ビットRSAなので総当たりも現実的でない。
- **設問4(4)**：作業1で移送用メディアに保存される「暗号鍵E」を、**攻撃者が生成した鍵ペアの暗号鍵**にすり替えれば、施設Kで署名鍵Sは攻撃者の鍵で暗号化される。作業5でその暗号文を読み取れば、攻撃者は自分の復号鍵で署名鍵Sを得られる（HSMでの復号は失敗するが、そのときには既に漏えいしている）。改良案で「HSMの機能で改ざん検知」としているのは、暗号鍵EにHSMで署名して真正性を確認するなどのため。

## 問3 情報システムのセキュリティ強化（P社 / DNS・IB・Kサービス）

| 設問 | 解答 |
|---|---|
| 設問1(1) a | DNSSEC |
| 設問1(2) b / c | b：DoH　c：TLS |
| 設問2 d / e | d：イ　e：ア |
| 設問3 | Kサービス設定サイトへのアクセスを許可する接続元IPアドレスとして，M-FWのグローバルIPアドレス a1.b1.c1.d1 だけを設定する。 |
| 設問4(1) f | 取引先サービスの接続元IPアドレス制限で，Kサービス用固定グローバルIPアドレスからの接続を許可する |
| 設問4(2) | Z-IB，OSベンダーのOSアップデート配布サイト，認証基盤サービス及びKサービス設定サイトへのHTTPSサービス |
| 設問5(1) g | 認証方式1で使う電話番号として，緊急時に利用する個人所有のスマホの電話番号を登録する |
| 設問5(2) | Kサービス接続時のログからOSがバージョンXの社有PCを抽出し，アカウント名から利用者を特定後，利用者の所属する部の情報セキュリティ推進者に報告し，バージョンYへの移行を促してもらう。 |

### 解説
- **設問1**：応答にデジタル署名＝**DNSSEC**、HTTPSでDNS＝**DoH**（DNS over HTTPS）、DoTは**TLS**で暗号化。
- **設問2**：偽サーバはやり取りを中継しながら、銀行には攻撃者口座、利用者側には元の画面を見せる（MITB/中間者型）。(12)で偽サーバは通常どおりトークン入力を促すので、操作担当者はトークンに**自分が入力した＝書換え前の口座番号**を入れる（d＝イ）。この認証番号は正規口座に対するものなので攻撃者には使えない。そこで(16)で「高額振込みの本人確認」と称して数字1234567（実は**攻撃者口座の口座番号**）を入力させ（e＝ア）、得た認証番号(18)を(19)(20)で銀行に送る。(8)で口座名義人を空白にしているのは、図3の「表示されないことがある」を悪用して名義の違いに気付かせないため。
- **設問3**：図6の項番9より、Kソフトは設定サイトからダウンロードし、インストール時に契約企業のIDを設定する。これを社外から誰でも取得できないよう、**接続元をM-FWのグローバルIP（a1.b1.c1.d1）に限定**する。図7の項番4も「P社内から」アクセスする前提になっている。
- **設問4(1)**：Kサービス経由の通信の送信元は**Kサービス用固定グローバルIP**になる（図8項番5）。取引先サービスはM-FWのIPしか許可していないので、Kサービス用IPを許可してもらう必要がある（W社への依頼(1)も同じ趣旨）。
- **設問4(2)**：M-FWでHTTPSの宛先をKサービスだけにすると，Kサービスを使えない場面で直接出る必要がある宛先が通れなくなる。①経理係のIB（**Z-IB**），②Kソフトを入れる前の新規PCやKソフトが動かないPCが使う**OSベンダーのOSアップデート配布サイト**（図7項番2で「あらかじめダウンロードしておいた」とあるのは直接取りに行けないことの裏返し），③Kソフト導入前に社内からMFAを設定する**認証基盤サービス**（図7項番3），④Kソフトを社内からダウンロードする**Kサービス設定サイト**（図7項番4，VPNのKサービスとは別の宛先）。
- **設問5(1)**：認証方式3は「都度、SMS（方式1）か認証アプリ（方式2）を選ぶ」。社有スマホが壊れたときにSMSで認証できるよう、**SMSの通知先として社有スマホ以外の電話番号**を登録しておく。表1で緊急時は個人所有スマホの利用が許可されているので、その番号を登録する。
- **設問5(2)**：Kサービスは接続時にOSバージョンを含むPC情報をチェックし，ログにアカウント名とシリアル番号を残せる（図6項番3，7）。そこで**ログからバージョンXの社有PCと利用者を特定**する。本文では移行は「各部の情報セキュリティ推進者の管理の下」で行うとされているので，**利用者の部の情報セキュリティ推進者に報告して移行を促してもらう**。いきなり接続を拒否すると，Kサービスの利用が必須なので業務が止まってしまう。

## 問4 製造業におけるセキュリティ管理（L社 / 経営ガイドライン・OTのリスク対応）

| 設問 | 解答 |
|---|---|
| 設問1 a | 未知の |
| 設問1 b | 暗号化 |
| 設問2(1) c / d / e | 回避，移転，受容（保有）（順不同） |
| 設問2(2) | 営業部：読込権限・書込権限，設計課・製造課・品質保証課：読込権限だけ，総務課：権限なし，情報システム課：権限変更権限だけ |
| 設問3 f | (け)の箇所にFWを導入し，SCADAから製造監視用PCへの通信以外を遮断する |
| 設問3 g | 購入したUSBメモリをSCADA操作用PCに接続する前にマルウェア検査を行う専用の検査用PC |
| 設問4(1) h | NCプログラムのバックアップ（ネットワークから切り離した媒体に保管） |
| 設問4(1) i | バックアップからNCプログラムをSCADAに復元する手順 |
| 設問4(2) j | マルウェアに感染した一般PCが，正常な通信を妨害するパケットを大量に送信して，SCADAと工作機械の間の通信ができなくなる。 |
| 設問4(2) k | SCADA，工作機械及び製造監視用PCだけの独立したLANを構成するためのネットワーク機器 |
| 設問4(2) l | SCADA，工作機械及び製造監視用PCをL社のネットワークから切り離す手順 |

### 解説
- **設問1**：パターンマッチング型は既知のシグネチャとの照合なので**未知の**マルウェア（新種・亜種）は検知できず、サンドボックス型は振る舞いで判定するので未知のものも期待できる。どちらも、パスワード付きZIPなど**暗号化**された添付ファイルは中身を検査できない。
- **設問2(1)**：リスク対応は低減・**回避**・**移転**（共有）・**受容**（保有）。図7の「サイバー保険の活用」は移転にあたる。
- **設問2(2)**：図4で設計情報ファイルを扱うのは、保存・確認する営業部（項番2：書込・読込）、参照する設計課（項番3）、適合確認を行う設計課・製造課・品質保証課（項番5：読込）。製造課はNCプログラム作成には設計図ファイルを使うが、項番5で設計情報ファイルとの適合を確認するので読込は必要。総務課は業務がないので不要。権限変更権限は管理を担う情報システム課だけに残し、データ自体の読み書き権限は外す。設計課から権限変更・書込権限を、製造課から書込権限を外すのがポイント。
- **設問3 f**：項番3は一般PCからSCADAへ感染が広がる経路。SCADAが通信する必要があるのは製造監視用PCへの稼働状況送信だけ（表1）。SCADAと工作機械のセグメントの入口である**(け)にFWを置いて通信を最小化**すれば、工作機械も含めて守れる。(し)だとSCADAだけ、(い)(あ)だと内部感染には効かない。
- **設問3 g**：SCADA操作用PCはネットワークにつながっておらず、データはUSBメモリでしか入らない。マルウェア対策ソフトを入れたうえで、**USBメモリを使う前に別の検査用PC（検疫端末）で検査**すれば、SCADA操作用PCに持ち込む前に止められる。SCADA操作用PCの性能や操作に影響しないので業務影響も少ない。
- **設問4(1)**：表6の3行目では、PCとSCADAをリカバリメディア（OS・アプリ）で戻せても、**NCプログラム（特に量産用）**はSCADA内にあり、感染で失われると工作できない。リカバリメディアにはアプリしか含まれないので、NCプログラムのバックアップと、それをSCADAへ戻す手順が要る。2時間以内に戻すには、ネットワークから切り離して保管しておく必要がある。
- **設問4(2)**：表6は「**製造が停止する**被害」の表で，最大許容停止時間2時間は**工作機械**の停止の話。3行目（SCADAへの感染）とは別の経路として，図3でSCADA・工作機械が一般PCと同じL3SW配下にある構成に着目する。一般PCがマルウェアに感染し，大量のパケットで**SCADAと工作機械の間の通信を妨害**すると量産が止まる。対策は，SCADA・工作機械・製造監視用PCだけの**独立したLAN**（そのためのネットワーク機器）と，異常時に**L社のネットワークから切り離す手順**。kは「できるだけ効果の高いもの」なので，2時間以内の復旧に重いバックアップ・復元より，切離しのほうが速くて確実。（公式の備考どおり，本文の状況に沿った被害シナリオと有効な仕組み・手順なら他の解答も可。）
