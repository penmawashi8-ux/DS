## 問1 Webアプリケーションプログラム開発のセキュリティ対策（H社 / Sシステムのアクセス制御）

| 設問 | 解答 |
|---|---|
| 設問1(1) | ア |
| 設問1(2) | プレースホルダ |
| 設問1(3) | a：改行コード |
| 設問2(1) | クエリ文字列のidに，未参加のプロジェクトのプロジェクトIDを指定する。 |
| 設問2(2) | プロジェクトを示すパラメタを外部から指定できないから（又は，セッション情報からプロジェクトIDを取得するから） |
| 設問2(3) | b：ウ |
| 設問2(4) | c：stmt |
| 設問3 | d：情報番号 = ? AND プロジェクトID = ? |

### 解説

#### 設問1(1)　［知識］
> 本文：表1 項番1「利用者の入力を基に**HTTPレスポンスヘッダ**を生成する処理において，①**改行コード**を意味する文字列を入力したときに，HTTPヘッダフィールドが追加されないことを確認」

**知識**：HTTPのヘッダは1行ずつCR LF（改行）で区切られる。URLエンコードではCRが %0D，LFが %0A。これを入力に混ぜて，新しいヘッダ行を足すのがHTTPヘッダインジェクション。`<br>` や `<p>` はHTMLの改行で，HTTPヘッダには関係ない（採点講評でもウの誤答が多かった）。

**答え**：ア（%0D%0A）

#### 設問1(2)　［知識］
> 本文：表1 項番2「SQL文の組立てにおいて，SQL文のひな形の中に②**変数の場所を示す?記号**を置く技法」

**知識**：`?` で値の場所を確保しておき，後から値を入れる仕組みを**プレースホルダ**（バインド機構）という。値はSQL文として解釈されないので，SQLインジェクションを防げる。

**答え**：プレースホルダ

#### 設問1(3)　［知識］
> 本文：表1 項番3 メールヘッダインジェクション「(3) 外部からの入力の全てについて，［ a ］を削除する」

**知識**：メールヘッダインジェクションも，改行を入れてBccなどのヘッダを追加する攻撃。入力から**改行コード**を取り除けば，ヘッダを増やせない。

**答え**：a：改行コード

#### 設問2(1)(2)　［読解］
> 本文：方法1「プロジェクトIDを…GETリクエストの**クエリ文字列**に，“id=プロジェクトID”の形式で指定する。情報選択機能は，クエリ文字列からプロジェクトIDを取得する」，「プロジェクトを識別するプロジェクトIDを**連番**で採番する」
> 本文：方法2「**セッション情報**から利用者情報を取得する。情報選択機能は，当該利用者情報からプロジェクトIDを取得する」

**考え方**：
- (1) クエリ文字列は利用者が自由に書き換えられる。プロジェクトIDは連番なので，idを他のプロジェクトの番号に変えるだけで，そのプロジェクトの情報一覧が見られる。
- (2) 方法2では，プロジェクトIDをリクエストから受け取らず，サーバ側のセッション（ログインした利用者）から引く。利用者がプロジェクトIDを指定する余地がなくなる。

**答え**：(1) クエリ文字列のidに，未参加のプロジェクトのプロジェクトIDを指定する。　(2) プロジェクトを示すパラメタを外部から指定できないから

#### 設問2(3)(4)　［知識］
> 本文：図2 7行目「…WHERE プロジェクトID = **?**」，8行目「java.sql.［ b ］ **stmt** = con.**prepareStatement**(sql);」，9行目「［ c ］.**setInt**(1, projectId);」，10行目「**stmt**.executeQuery()」

**知識**：`con.prepareStatement(sql)` が返すのは **PreparedStatement**。`?` に値を入れる setInt などもこのオブジェクトのメソッド。Statementではプレースホルダを使えない（採点講評でも注意されている）。

**答え**：b：ウ（PreparedStatement）　c：stmt

#### 設問3　［読解］
> 本文：図3 3行目「int **documentNo** = Integer.parseInt(request.getParameter("no"));」，7行目「int **projectId** = …利用者テーブルから取得」，注記「10行目より後の（省略）に，projectId，documentNoを用いた処理はない」
> 本文：図1 情報管理テーブル「**情報番号**，**プロジェクトID**，情報名，情報内容」

**考え方**：情報表示機能でも，表示したい情報番号（no）だけで検索すると，他プロジェクトの情報番号を指定して中身を見られる。情報番号が一致し，かつ自分のプロジェクトIDのものだけを取り出すよう，両方を条件にする。10行目以降で使わないので，ここで2つのプレースホルダとして使う。

**答え**：d：情報番号 = ? AND プロジェクトID = ?

## 問2 セキュリティインシデント対応（Z社 / NASのランサムウェア感染）

| 設問 | 解答 |
|---|---|
| 設問1(1) | a：ア　b：エ |
| 設問1(2) | 外部からLAN側への通信の許可設定が変更される。 |
| 設問1(3) | PCからのファイル操作ではアクセスできない領域のファイルが暗号化されたから |
| 設問2(1) | c：パストラバーサル |
| 設問2(2) | d：OSコマンドインジェクション |
| 設問2(3) | e：ア　f：ウ　g：イ |
| 設問3(1) | POSTメソッドで送信したボディがアクセスログに残っていなかったから |
| 設問3(2) | sudoコマンドの設定ファイルで，tarコマンドのオプションを受け付けないように設定する。 |
| 設問4 | h：noindex（又は none） |

### 解説

#### 設問1(1)　［知識］
> 本文：「ルータ-AのグローバルIPアドレスが変更された場合…ホスト名nas-aに割り当てている**IPアドレス**を変更するために，［ a ］レコードを更新する。そのレコードの［ b ］は，**300秒**に設定」

**知識**：ホスト名にIPv4アドレスを対応させるのは**Aレコード**。キャッシュサーバがその情報を保持してよい時間が**TTL**（Time To Live）。ダイナミックDNSでは，IPアドレスが変わってもすぐ反映されるようTTLを短くする。

**答え**：a：ア（A）　b：エ（TTL）

#### 設問1(2)　［読解］
> 本文：表1 注1「UPnPは…**認証なし**でリクエストを受け付ける仕様のプロトコル」
> 本文：表2 UPnP機能「LAN側の機器から受け付けたリクエストの内容で，**ポートフォワーディングの設定とファイアウォール機能の設定**を行う」，ファイアウォール「インバウンド通信：全て拒否（UPnP機能による設定が優先される）」

**考え方**：WAN側でUPnPが使えると，インターネット上の誰でも認証なしでルータ-Aに「このポートを内側の機器に転送して」と頼める。ファイアウォールよりUPnPの設定が優先されるので，外からLAN側への通信が勝手に許可されてしまう。

**答え**：外部からLAN側への通信の許可設定が変更される。

#### 設問1(3)　［読解］
> 本文：「ファイル共有機能でもWeb操作機能でも**アクセスできない/rootディレクトリ配下**のファイルも暗号化されていた」

**考え方**：PCが感染した場合，暗号化できるのはPCからファイル共有などでアクセスできるファイルだけ。PCからは触れない/rootまで暗号化されているので，NAS-Aの中でランサムウェアが動いたと考えられる。

**答え**：PCからのファイル操作ではアクセスできない領域のファイルが暗号化されたから

#### 設問2(1)(2)　［知識］
> 本文：図2 脆弱性1「`http://192.168.0.1/images/..%2fstatus.cgi`…URLに“..%2f”を使用した［ c ］」，脆弱性2「`addr=127.0.0.1;whoami`」「任意のOSコマンドを実行できてしまう」

**知識**：
- `../`（%2fは「/」）でディレクトリをさかのぼって，本来アクセスできない場所に届く攻撃が**パストラバーサル**（ディレクトリトラバーサル）。
- 入力値に `;` などを混ぜて，別のOSコマンドを実行させる攻撃が**OSコマンドインジェクション**。

**答え**：c：パストラバーサル　d：OSコマンドインジェクション

#### 設問2(3)　［読解］＋［知識］
> 本文：脆弱性1「/images/..%2fstatus.cgi」（/images で始まるので除外リストに当たってしまう）
> 本文：「パス名の正規化とは，相対パスで記述されたパス名を，相対パス記法を含まない形式に変換すること」

**考え方**：%2f のままでは「../」と認識されないので，まず**URLデコード**して「/images/../status.cgi」にする。次に**正規化**して「/status.cgi」にする。最後に**除外リストと比較**すれば，/status.cgi は除外リストにないので認証が求められる（採点講評でも，この順序が大事とある）。

**答え**：e：ア（URLデコード）　f：ウ（パス名の正規化）　g：イ（除外リストとの比較）

#### 設問3(1)　［読解］
> 本文：表3「18　GET /images/shell.cgi?**cmd=whoami**」（URLにコマンドが見える），「89　POST /images/shell.cgi」（URLにコマンドがない）

**考え方**：GETではパラメータがURL（リクエスト行）に入るのでアクセスログに残る。POSTではパラメータがリクエストのボディに入り，通常のアクセスログにはボディは記録されないので，何のコマンドを実行したか分からない。

**答え**：POSTメソッドで送信したボディがアクセスログに残っていなかったから

#### 設問3(2)　［読解］
> 本文：図4「www ALL=NOPASSWD: /bin/tar」（wwwアカウントは，tarをどんな引数でもrootで実行できる）
> 本文：「tarコマンドには，任意のOSコマンドを実行できる**オプション**がある。ただし，ファームウェアのアップデート時に**このオプションは使用していない**」，図5「sudo tar … --checkpoint=1 --checkpoint-action=exec=whoami」

**考え方**：tar自体はアップデートで必要なので消せない。sudoの設定で，tarに渡せる引数を必要なもの（展開用）に限り，コマンド実行のオプションを受け付けないようにする。

**答え**：sudoコマンドの設定ファイルで，tarコマンドのオプションを受け付けないように設定する。

#### 設問4　［知識］
> 本文：「インターネットの検索エンジンで検索されないようにするために…`<meta name="robots" content="［ h ］">`」

**知識**：検索エンジンに，ページを検索結果に載せないよう指示する値は **noindex**。**none** は noindex と nofollow（リンクをたどらない）をまとめた指定（採点講評でも正答率が低かった）。

**答え**：h：noindex（又は none）

## 問3 スマートフォン向けQRコード決済サービスの開発（L社 / 本人確認）

| 設問 | 解答 |
|---|---|
| 設問1 | a：イ　b：ア |
| 設問2(1) | ①漏えいしている口座番号と暗証番号を悪用する方法　②口座番号と暗証番号をだまして聞き出し，悪用する方法 |
| 設問2(2) | c：写真 |
| 設問2(3) | d：ウ　e：イ |
| 設問2(4) | f：署名用電子証明書の有効性（又は，署名用電子証明書の失効の有無） |
| 設問2(5) | g：そのランダムな数字を紙に書き，その紙と一緒に容貌や本人確認書類を撮影 |
| 設問3(1) | スマートフォンを盗まれた場合 |
| 設問3(2) | Qアプリの起動時に，PINコードで利用者を認証する機能 |

### 解説

#### 設問1　［読解］
> 本文：「身元確認は，“**登録する**氏名・住所・生年月日等が正しいことを証明／確認すること”」「当人認証は，“認証の3要素のいずれかの照合で，**その人が作業している**ことを示すこと”」
> 本文：表1 アカウント作成「氏名，生年月日…を**登録**する」，Qサービスへのログイン「利用者IDとパスワードでQサービスにログインする」

**考え方**：登録する情報が本物かを確かめるのはアカウント作成時。毎回その本人が使っているかを確かめるのはログイン時。

**答え**：a：イ（アカウント作成）　b：ア（Qサービスへのログイン）

#### 設問2(1)　［読解］
> 本文：表1 銀行口座とのひも付け「選択された銀行には…アカウント情報の**氏名**が提供される」「利用者は，**口座番号**，キャッシュカードの数字4桁の**暗証番号**を入力」，C課長「キャッシュカードの**所持が確認されず**，暗証番号で照合されるだけ」

**考え方**：攻撃者は他人の氏名でアカウントを作れる（身元確認がない）。あとは他人の口座番号と暗証番号が分かればひも付けできる。手に入れる方法は，すでに漏えいしている情報を使うか，本人をだまして聞き出すか。

**答え**：①漏えいしている口座番号と暗証番号を悪用する方法　②口座番号と暗証番号をだまして聞き出し，悪用する方法

#### 設問2(2)　［知識］
> 本文：表2 項番1「［ c ］付き本人確認書類の画像」「容貌の画像」

**知識**：運転免許証やマイナンバーカードなど**写真付き**の本人確認書類と，本人の顔（容貌）の画像を比べて，本人だと確認する（いわゆるeKYC）。

**答え**：c：写真

#### 設問2(3)　［知識］
> 本文：「マイナンバーカード内の［ d ］でQサービスの申込用のデータに**デジタル署名**し…Qサービス側で…改ざんされていないことを…利用者の［ e ］を用いて確認」

**知識**：デジタル署名は**秘密鍵**で作り，**公開鍵**（署名用電子証明書に入っている）で検証する。秘密鍵はマイナンバーカードのICチップから取り出せない。

**答え**：d：ウ（秘密鍵）　e：イ（公開鍵）

#### 設問2(4)　［知識］
> 本文：「デジタル署名が利用者本人のものであり，改ざんされていないことを…確認した後，**地方公共団体情報システム機構**に［ f ］を確認する」

**知識**：署名が正しくても，カードの紛失などで証明書が**失効**しているかもしれない。発行元（J-LIS）にOCSPやCRLで，証明書が今も有効かを確認する（採点講評でも正答率が低かった）。

**答え**：f：署名用電子証明書の有効性（又は，署名用電子証明書の失効の有無）

#### 設問2(5)　［読解］
> 本文：C課長「項番1では**事前に準備した他人の画像**を用いられないようにする必要がある」「Qアプリが**毎回ランダムな数字**を表示し，利用者が［ g ］して，直ちに送信することによって…事前に準備されたものではないことを確認」

**考え方**：毎回違う数字が写っていれば，その場で撮った写真だと分かる。数字だけを撮っても本人かは分からないので（採点講評の指摘），数字を書いた紙を容貌や本人確認書類と**一緒に**撮影させる。

**答え**：g：そのランダムな数字を紙に書き，その紙と一緒に容貌や本人確認書類を撮影

#### 設問3　［読解］
> 本文：下線②「Qサービスにログインした状態で，**スマートフォンの画面ロックを設定していない**と，Qサービスが不正利用されることがある」，「ログインが成功した場合は，**1か月間**，ログイン状態を保持」

**考え方**：
- (1) ログイン状態が1か月続くので，スマートフォンを盗まれたり拾われたりすると，画面ロックがなければ誰でもすぐQアプリで決済できる。
- (2) ログイン状態は保ったまま，Qアプリを開くたびにPINコードなどで本人を確かめれば，他人は使えない。

**答え**：(1) スマートフォンを盗まれた場合　(2) Qアプリの起動時に，PINコードで利用者を認証する機能
