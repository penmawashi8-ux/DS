## 問1 APIセキュリティ（G社 サービスY / S-API）

| 設問 | 自作解答 |

| 設問2(2) 検証内容 | 想定したRS256であることを確認する（NONEを拒否） |
| 設問2(3) | JWTのペイロードの利用者IDとパラメータmidが一致するか確認する処理 |
| 設問2(4) c | 共通モジュールP |
| 設問2(5) d | 同一利用者IDで連続して認証に失敗したら利用者IDをロックする処理 |
| 設問3(1) | テストサーバへのindex.htmlのHTTPアクセスをログで確認する仕組み |
| 設問3(2) e / f | e：Header　f：Header |
| 設問3(3) | `¥W[jJ][nN][dD][iI]¥W` |
| 設問3(4) 利点 | 誤検知で正常な通信を遮断せずに済む |
| 設問3(4) 実施内容 | アラートを受けたら直ちに該当の通信元を遮断する |

### 解説
- **設問1**：RESTはサーバがクライアントのセッション状態を保持しない「ステートレス」性を原則とする。状態はリクエスト（ここではJWT）側で持ち運ぶ。
- **設問2(1)**：数字4桁＝10,000通り。正解は一様ランダムなので、総当たりで当たるまでの平均試行回数は約 10,000/2 = 5,000回（厳密には(10,000+1)/2）。1秒10回なので 5,000/10 = **500秒**。有効期限10分（600秒＝6,000回）以内に平均的に突破できるので「突破される可能性が高い」。
- **設問2(2)**：ライブラリQは「JWT内のヘッダに指定されたアルゴリズムに基づいて」検証していたため、攻撃者が `alg` を `NONE` にすると署名検証そのものがスキップされた（いわゆる alg=none 攻撃）。修正後はヘッダのalgをそのまま信用せず、**サーバ側で決めたRS256であることを検証**（＝想定外のalgは拒否）し、そのうえで公開鍵で署名を検証する。
- **設問2(3)**：項番2はIDOR（オブジェクト単位の認可不備）。midはリクエストパラメータなので改ざんできる。P呼出し処理で、**検証済みJWTから得た利用者IDとmidが一致する場合だけ**共通モジュールPを呼び出すようにする。
- **設問2(4)**：パラメータを検証せずに丸ごと渡していた先＝利用者ステータスも管理している**共通モジュールP**（Mass Assignment）。
- **設問2(5)**：しきい値10で総当たりを止める仕組み＝**アカウントロック**（一定回数失敗で文字列Xを無効化する、でも同趣旨）。さらに6桁化で1回あたりの成功確率を1/1,000,000にする。
- **設問3(1)**：注記2より、コマンドCは `wget http://a2.b2.c2.d2/index.html`。Sシステム上で実行されればテストサーバ（攻撃用HTTPサーバを兼ねる）にindex.htmlへのGETが来る。したがって**HTTPサーバのアクセスログでSシステムからのindex.html要求を確認**すればよい。システムに影響しない無害なコマンドである点も条件に合う。
- **設問3(2)**：攻撃コードは `x-api-version` **ヘッダ**に入る（図6(3)）。`jndi` も `ldap` も同じ攻撃コード中の文字列なので、両ルールとも検証対象は **Header**。
- **設問3(3)**：図5の正規表現には大文字小文字を無視するフラグがないので、`[xyz]` を使って各文字の大文字・小文字の両方を許す。前後の `¥W` は `${` や `:` などの非英数字。
- **設問3(4)**：暫定ルールは誤検知で正常なリクエストまで遮断し、サービスYを止めてしまうおそれがあるため、まず“検知”で影響を見極める。その間は攻撃が通過してしまうので、**アラートを常時監視して即応（通信元の遮断やルールを遮断に切替え）**する運用が必要。

## 問2 サイバー攻撃への対策（H社 VPN-GW / DDoS）

| 設問 | 自作解答 |
|---|---|
| 設問1(1) a | 公開Webサーバや取引先向けWebサーバに，大量のHTTP GETリクエストを送り付ける。 |
| 設問1(2) | 正常な通信まで異常として検知・遮断してしまう。 |
| 設問1(3) b / c | b：DNS-K　c：DNS-F |
| 設問2(1) d | 攻撃者が，入手した利用者IDとパスワードを正規のVPN-Hに入力し，正規利用者のスマートフォンにSMSでセキュリティコードを送信させる。 |
| 設問2(1) e | 罠のWebサイトでセキュリティコードを正規利用者に入力させて入手し，攻撃者がVPN-Hのセキュリティコード入力画面に入力する。 |
| 設問2(2) | VPN接続はVPNクライアントソフトウェアのVPNダイアログからだけ行い，Webブラウザ上では利用者ID・パスワード・セキュリティコードを入力しない。 |
| 設問3(1) | 盗聴したパケットと同じ順番でポートに通信要求を送る。 |
| 設問3(2) | SPAパケットは毎回異なるワンタイムパスワードとランダムデータを含み，再送しても破棄されるから。 |
| 設問4(1) | 通信事業者が提供するDDoS攻撃対策サービス |
| 設問4(2) | 取引先向けWebサーバには，SPAで認証された取引専用PCからのVPN通信しか届かなくなるから。 |

### 解説
- **設問1(1)**：HTTP GET Floodはアプリケーション層のDDoS。H社でHTTP(S)を公開しているのは**公開Webサーバ**と**取引先向けWebサーバ**なので，これらに大量のGETを送ってサーバ資源を枯渇させる例を書く。
- **設問1(2)**：アノマリ型でしきい値が低すぎると，繁忙時などの正常トラフィックも異常と判定する（**誤検知**）。高すぎると攻撃を見逃す（検知漏れ）。
- **設問1(3)**：DNSリフレクションの踏み台にされるのは，インターネットから再帰問合せを受け付けるオープンリゾルバだから。権威サーバ（DNS-K）とフルサービスリゾルバ（DNS-F）を分離し，**外→内はDNS-K宛てだけ**（自社ドメインの問合せに応答），**内→外はDNS-Fからだけ**（社内向け再帰問合せ）を許可する。
- **設問2(1)**：リアルタイム型フィッシング（中間者型）。罠サイトで取ったID/パスワードを攻撃者が即座に本物のVPN-Hへ入力→SMSは正規利用者に届く→罠サイトに「セキュリティコード入力画面」を出して利用者に入力させ→攻撃者がそれを本物に転送，という流れ。SMS OTPはこの中継に弱い。
- **設問2(2)**：URLリンクを踏むこと自体は止められない前提なので，「**VPN接続はVPNクライアントソフトのダイアログからしか行わない＝ブラウザでVPNの認証情報やコードを求められたら罠**」という誰でも判断できるルールを周知する。「自分で接続操作をしていないのに届いたSMSのコードは入力しない」も同趣旨。
- **設問3(1)**：設定Pはポートノッキング。ノックの順番は平文のパケットに表れるので，盗聴できれば**同じ順番でノックを再送（リプレイ）**するだけで開いてしまう。
- **設問3(2)**：SPAは表6のとおり，HMACベースの**ワンタイムパスワード**で真正性を検証し，**ランダムデータ**で同一パケットの再送を破棄し，ハッシュで改ざんも検知する。秘密情報を知らない攻撃者は新しい正当なSPAパケットを作れず，盗聴したものを再送しても破棄される。
- **設問4(1)**：回線帯域を飽和させる攻撃は自社設備の手前で止める必要があるので，**ISP／通信事業者やクラウド事業者のDDoS対策（スクラビング）サービス**，あるいはCDNを使う。
- **設問4(2)**：UTMでインターネットから取引先向けWebサーバへの直接通信を拒否し，S-APPLのSPAとVPNを通った取引専用PCからだけ到達できるようにする。SPAは検証に失敗したパケットを応答なしで破棄するので，**不特定多数からのDDoSトラフィックが取引先向けWebサーバに届かなくなる**。

| 設問4(3) | 方法Gで，WebサーバYからトークン発行URLにPUTメソッドでアクセスさせてトークンを入手し，次にそのトークンをリクエストヘッダに含めて /meta-data/credential にアクセスさせ，クレデンシャル情報を取得する。 |

### 解説
- **設問1(1)**：問合せ機能（項番5）で入れたnameは，そのレスポンスには出ないが，D社管理者が見る**問合せ管理機能（項番9）**に出力される＝格納型（蓄積型）XSS。設計書（表1）を見て「入力が別画面に出る」流れを追うのがポイント。
- **設問1(2)**：SESSIONIDには値とSecure属性だけで **HttpOnly属性が無い**ため，JavaScriptから `document.cookie` で読める。管理者のSESSIONIDを窃取すればサーバ側セッションは24時間有効なので，サイト管理機能（接続元制限なし）にそのままアクセスでき，**会員管理機能（項番8）**で全会員の情報を取れる。
- **設問2(1)**：手順3で「別アカウントで取ったcsrf_tokenでも通る」＝トークンがセッションと紐付いて検証されていない。攻撃者は自分のトークンを罠ページに埋め込めばCSRFが成立する。メールアドレスを書き換えられると，パスワード再設定などを経てアカウント乗っ取りにつながる。
- **設問2(2)**：Strictはクロスサイトからの遷移では一切送らない（GET/POSTとも×）。Laxはトップレベル遷移のGET（リンククリック等）だけ送り，クロスサイトのPOSTは送らない（GET○，POST×）。
- **設問3(1)**：注文管理番号は「注文年月6桁（推測容易）＋英大文字6桁」。後半は26^6 ≒ 3億通りだが，月1万件の注文があるので，ランダムに試しても他人の番号に当たる確率は無視できない。**総当たり（ブルートフォース）／推測攻撃**で他人の番号を見つけられる。
- **設問3(2)**：根本対策は番号を推測困難にすることではなく**認可チェック**。サーバ側でセッションのログイン利用者と注文の所有者を照合する。
- **設問4(1)**：SSRFでは，攻撃者が制御できるのはWebサーバYが送るリクエストの**宛先URL（GET）**だけ。CMSのログインはPOSTでしか許可されないので，ログインフォームの送信まではできない。
- **設問4(2)**：IMDSはインターネットからは届かないが，VPC内のWebサーバYからは届く。方式1はURLにGETするだけで情報が返るので，`page` をIMDSのcredential URLにするだけで，WebサーバYが取得した内容が攻撃者へのレスポンスに含まれる。
- **設問4(3)**：方式2（トークン必須）でも，方法Gでメソッドとヘッダを自由に指定できれば，①PUTでトークン発行URLにアクセスしてトークン取得 → ②トークンをヘッダに付けてcredential URLにGET，の2段階を再現できる。
- **設問4(4)**：サーバ側で取りに行く先を**許可リスト（サイトPのFQDN／URL）で制限**する。ネットワーク側のアクセス制御（WebサーバYからIMDSへの通信制限など）と組み合わせる。

## 問4 Webアプリケーションプログラム（A社 Web受注システム）

| 設問 | 自作解答 |
|---|---|
| 設問1(1) a | ア（システム運用担当者） |
| 設問1(2) b | personal |
| 設問1(3) c | 4 |
| 設問2(1) d | 5 |
| 設問2(2) e | NoSuchAlgorithmException |
| 設問2(3) システム運用担当者 | 情報：パスワード，氏名，住所，電話番号，メールアドレス／場所：エ（※IPA追記により不成立） |
| 設問2(3) システム開発者 | 情報：パスワード，氏名，住所，電話番号，メールアドレス／場所：オ |
| 設問2(4) f | SHA-256 |
| 設問2(5) g | `throw new RuntimeException(e)`（例外を送出して処理を中断し，ユーザー登録を行わない） |
| 設問2(6) h | `finally` |
| 設問2(7) | ア |

### 解説
- **設問1(1)**：CSVファイルは本番バッチサーバの `/var/data` に，オーナーbatchappuser・グループoperation，ディレクトリ770・ファイル660で出力される。operationグループには**operator（システム運用担当者）**も属するので，重要情報（銀行口座情報など）を含むCSVを読めてしまう。表1 No.18(2)で運用担当者は重要情報へのアクセス禁止。システム開発者（develop）は本番バッチサーバにアクセス権が無い。
- **設問1(2)**：batchappuserの所属を**personal**にすると，CSVを読めるのはオーナーとpersonalグループ（重要情報取扱運用者）とrootだけになる。personalは本番環境へのアクセス権があるので本番バッチサーバでの実行にも支障がない。
- **設問1(3)**：No.3（Web受注側で出力）で暗号化したCSVは，No.7で送信→No.10で業務システム側に保存→**No.4（注文データCSV取込み）**で読み込んでDB更新する。復号するのは取り込む直前のNo.4。
- **設問2(1)(2)**：`MessageDigest.getInstance()` は指定したアルゴリズムが実行環境で使えないと **NoSuchAlgorithmException** を投げる。catch節はログを出すだけで処理を続行するので，7行目の代入が行われず `this.password` は**平文のまま**残り，addUserでそのままINSERTされる。
- **設問2(3)**：`this.toString()` はインスタンス変数（ユーザーマスターの各列）を出力するので，重要情報（表1 No.5）のうち **パスワード（ハッシュ値または上記の場合平文）・氏名・住所・電話番号・メールアドレス** が出る。
  - システム開発者：23,24行目の `log.debug` により**本番ログサーバのAPログ（オ）**に出力され，開発者は障害調査で本番ログサーバを見られる。
  - システム運用担当者：21,22行目の `System.out.println` が**本番APサーバの /var/log/serverlog 配下（エ）**に出る。ファイル664・ディレクトリ775でotherに読み取り権があり，operationグループは本番APサーバにアクセスできるので読める……という想定だったと思われるが，IPAが「不備により成立しない」と追記している（正誤表で774→775に直したことと関係していると推測。詳細は照合ファイル参照）。
- **設問2(4)**：要件19はCRYPTREC電子政府推奨暗号リストのハッシュ関数。SHA-1は推奨リストに無い（運用監視暗号リスト扱い）。推奨はSHA-256／SHA-384／SHA-512（SHA3系も可）。代表として **SHA-256**。
- **設問2(5)**：「回復不能な例外発生」なので，握りつぶさず**例外を送出して処理を中断**し，平文パスワードが保存されないようにする。
- **設問2(6)**：例外の有無にかかわらず必ず `psObj.close()` するための **finally**（メモリリーク対策）。
- **設問2(7)**：レインボーテーブル対策は**ソルト付きハッシュ**。ソルトはユーザーごとに異なるので検証時に必要＝どこかに保存する必要があるが，テーブル定義は変えられない。よって**パスワード列にソルト（32バイト固定長）＋hash(salt+password)を連結して保存**する **ア** が正解。イはソルトをどこにも保存しないので照合不能。ウ・エはパスワード自体を無ソルトでハッシュしているのでレインボーテーブルが効く。オは最後に無ソルトの結果を上書きしているうえソルトも保存していない。
